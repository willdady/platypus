# Deploy with Docker Compose

The fastest way to run Platypus is the one-line installer. It downloads the
release's `compose.yaml`, pins the images to that release, writes a `.env` with a
fresh secret and admin password, and starts the stack. Replace
`you@example.com` with your own email — it's how you sign in as the first admin:

```bash
curl -fsSL https://platypus.chat/install.sh | ADMIN_EMAIL=you@example.com bash
```

The stack pulls the published images, wires the services together on a private
network, and seeds an initial organization and admin user on first boot.

## The stack

`compose.yaml` defines three services on a private bridge network
(`platypus-network`):

| Service    | Image                               | Port (host:container) | Purpose                                        |
| ---------- | ----------------------------------- | --------------------- | ---------------------------------------------- |
| `database` | `pgvector/pgvector:pg17`            | _internal only_       | PostgreSQL 17 with the `pgvector` extension    |
| `backend`  | `willdady/platypus-backend:latest`  | `4000:4000`           | Hono REST API, auth, run lifecycle, schedulers |
| `frontend` | `willdady/platypus-frontend:latest` | `3000:3000`           | Next.js web app                                |

The services start in dependency order: the backend waits for the database to
become healthy, and the frontend waits for the backend. All three publish Docker
health checks so `docker compose` can gate startup and report status.

<Callout type="info">
  Postgres 18 is **not supported** (a Drizzle ORM incompatibility). Stay on the
  `pg17` image tag.
</Callout>

### Image tags

The compose file ships pointing at `:latest` for both application images; the
installer pins both to the exact release it installed. Every release publishes
three tags per image, and which one you pin decides how much moves under you on
the next `docker compose pull`:

| Tag           | Example                            | What a pull fetches                     |
| ------------- | ---------------------------------- | --------------------------------------- |
| Latest        | `willdady/platypus-backend:latest` | The newest release, major bump included |
| Major line    | `willdady/platypus-backend:4`      | The newest `4.x.y`, never `5.0.0`       |
| Exact version | `willdady/platypus-backend:4.0.0`  | That release and nothing else           |

**Pin something other than `:latest`.** It is the only tag that can carry a
breaking major change into a running deployment, and it leaves you unable to say
which version you are on.

Pin the **major line** for a deployment you want to keep current without
watching every release. Pin the **exact version** for one you upgrade
deliberately — it is the only tag that makes an upgrade a change you made rather
than a pull you ran.

Override the images in a `compose.override.yaml` alongside `compose.yaml`:

```yaml
services:
  backend:
    image: willdady/platypus-backend:4.0.0
  frontend:
    image: willdady/platypus-frontend:4.0.0
```

Compose merges `compose.override.yaml` automatically, so `docker compose up -d`
picks it up with no extra flags. Bump both together — the two images are
released as a pair and are only tested against each other.

<Callout type="warning">
  A major-line pin is not a record of what you deployed. Two hosts that pulled
  `:2` a month apart run different builds from identical compose files, so
  "we're both on 2" is not a statement anyone can act on during an incident.
  Read `docker compose images` for the digest a host actually has, and pin exact
  versions where that matters.
</Callout>

### Ports

- **Frontend** — `http://localhost:3000` (the URL you sign in at).
- **Backend** — `http://localhost:4000` (the REST API and `/auth/*` endpoints).

With Caddy on (see [Serve HTTPS with Caddy](#serve-https-with-caddy)), neither
port is published: the stack is reached at `https://<domain>`, and only Caddy's
`80` and `443` are open.

The frontend reaches the backend over the private network at
`http://backend:4000` (set via `INTERNAL_BACKEND_URL`) for server-side rendering,
while the browser talks to the backend at its public URL. See
[Configuration & environment](/self-hosting/configuration) for how these URLs fit
together.

Those ports carry traffic inward. For the other direction — the backend calling
a model server running on the host machine rather than in the stack — see
[Reaching a model server on the host machine](/self-hosting/providers-and-auth#reaching-a-model-server-on-the-host-machine).

### Volumes

- `postgres_data` — a named volume holding the database. Your data lives here;
  don't delete it unless you mean to start over.
- `./data` — a bind mount into the backend at `/data`. The backend image stores
  uploaded files at `/data/files`, so they arrive here on the host, under
  `./data/files`. Override
  [`STORAGE_DISK_PATH`](/reference/backend-configuration#storage) and your
  uploads follow it out of this mount.

#### File ownership on `./data`

The backend serves requests as an unprivileged account, uid **1001**, rather
than as root. Everything inside the image is already owned by it; a bind mount
is the exception, because it keeps whatever ownership the directory has on the
host.

You do not normally have to do anything about this. The container starts as
root, takes ownership of `/data` if it belongs to somebody else, and only then
drops to uid 1001 — so an existing `./data` full of uploads keeps working across
an upgrade, and a fresh one is created correctly.

Two cases do need you:

- **You pin the container to a user yourself** — a `user:` key in
  `compose.yaml`, `docker run --user`, or a Kubernetes `runAsUser`. The
  container can no longer change ownership of anything, so make the host
  directory writable by the uid you pinned it to:

  ```bash
  sudo chown -R 1001:1001 ./data
  ```

- **`./data` sits on a filesystem that does not carry Unix ownership** — an NFS
  export with root squash, or an SMB share. Ownership there is decided by the
  mount, not by the container, so set it at mount time.

Uploads failing with a permission error, on a stack that is otherwise healthy,
is the symptom of both.

## Install

Run the installer on the host that will serve Platypus. It needs Linux or macOS
(on Windows, run it inside WSL), `curl`, `openssl`, and Docker with the Compose
v2 plugin and a running daemon. It does not install Docker for you, and it exits
before writing anything if one of these is missing.

```bash
curl -fsSL https://platypus.chat/install.sh | ADMIN_EMAIL=you@example.com bash
```

The installer asks no questions. It creates a `platypus` directory in the
current directory holding `compose.yaml`, a `compose.override.yaml` that pins
both images to one exact version (and, with `PLATYPUS_DOMAIN`, adds the Caddy
block), a `.env` readable only by you, and a `README.md` listing the commands to
start, stop and restart the stack. Then it runs
`docker compose up -d --wait` and prints the sign-in URL, the admin email and the
admin password.

<Callout type="warning">
  **The printed credentials are temporary.** The password is generated fresh for
  each install, but it has been printed to your terminal and is saved in `.env`.
  Change it from the in-app account settings after you first sign in.
</Callout>

### Installer settings

Set these as environment variables on the `bash` side of the pipe:

| Variable           | Default                     | What it does                                                                                                                                                                                                                                |
| ------------------ | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PLATYPUS_VERSION` | the latest release          | The release to install, e.g. `3.13.0`.                                                                                                                                                                                                      |
| `PLATYPUS_DIR`     | `./platypus`                | The directory to install into.                                                                                                                                                                                                              |
| `PLATYPUS_HOST`    | `localhost`                 | The host the browser reaches Platypus on — a host name or IP address, with no scheme or port. Sets `FRONTEND_URL`, `BACKEND_URL` and `ALLOWED_ORIGINS` together.                                                                            |
| `PLATYPUS_DOMAIN`  | _(unset)_                   | The domain to serve HTTPS on — a host name such as `chat.example.com`, not an IP address. Writes the Caddy block into `compose.override.yaml` and points all three URLs at `https://<domain>`. Cannot be set together with `PLATYPUS_HOST`. |
| `ADMIN_EMAIL`      | `admin@example.com`         | The initial admin's email.                                                                                                                                                                                                                  |
| `ADMIN_PASSWORD`   | a random 24-character value | The initial admin's password. At least 8 characters.                                                                                                                                                                                        |

For example, on a server you reach as `platypus.internal`:

```bash
curl -fsSL https://platypus.chat/install.sh | PLATYPUS_HOST=platypus.internal bash
```

For an HTTPS install, point the domain's DNS at the host first:

```bash
curl -fsSL https://platypus.chat/install.sh | PLATYPUS_DOMAIN=chat.example.com bash
```

<Callout type="error">
  With `PLATYPUS_HOST` set to anything other than `localhost`, ports `3000` and
  `4000` serve plain HTTP, with no TLS, on every network interface of the host.
  That suits a trusted network, not the internet. Set
  [`PLATYPUS_DOMAIN`](#serve-https-with-caddy) instead to put the stack behind
  TLS. See [Running in production](/self-hosting/production) before exposing it
  further.
</Callout>

The installer refuses to run against a directory that already has a `.env`, and
changes nothing there: that file holds the secret your sessions are signed with
and can't be regenerated. To move an existing install to a new release, see
[Upgrading](#upgrading).

It also refuses when port `3000` or `4000` is already in use on the host, and
when a database from an earlier install into a directory of the
same name is still on the host, such as `platypus_postgres_data` after you
deleted `./platypus`. The new admin password would never sign in to that
database, because first boot doesn't run twice. Remove the volume with
`docker volume rm platypus_postgres_data` if you mean to start over, or keep it
and install into a directory with another name, such as
`PLATYPUS_DIR=./platypus2`.

## Serve HTTPS with Caddy

A `caddy` service in `compose.override.yaml` gives the deployment TLS on one
domain: the frontend at `/`, the backend at `/api`, automatic certificates, and
an HTTP → HTTPS redirect. Nothing is published on `3000` or `4000` once it is
on.

The installer writes this for you when `PLATYPUS_DOMAIN` is set. To add it to an
existing install instead, copy the entries below into `compose.override.yaml`
and replace `chat.example.com` with your domain.

The file already has a `services:` block holding the pinned image tags. Add the
`caddy` service and the two `ports: !reset []` lines to that block, keeping its
`image:` lines, and add the `volumes:` and `configs:` blocks beside `services:`
at the top level. There must be one `services:` key, not a second one. `!reset`
drops the `3000` and `4000` publishes inherited from `compose.yaml`, so Caddy is
the only way in.

```yaml
services:
  backend:
    ports: !reset []
  frontend:
    ports: !reset []
  caddy:
    image: caddy:2.11.7
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"
    configs:
      - source: caddyfile
        target: /etc/caddy/Caddyfile
    volumes:
      - caddy_data:/data
      - caddy_config:/config
    networks:
      - platypus-network

volumes:
  caddy_data:
  caddy_config:

configs:
  caddyfile:
    content: |
      chat.example.com {
        handle_path /api/* {
          reverse_proxy backend:4000 {
            header_up X-Forwarded-For {remote_host}
            flush_interval -1
          }
        }

        handle {
          reverse_proxy frontend:3000
        }
      }
```

It needs:

- **Docker Compose 2.24.0 or later** — `ports: !reset []` and an inline
  `configs:` entry arrived there. An older Compose refuses to load the file.
- **DNS pointed at this host** — an A or AAAA record for the domain must already
  resolve to it. The value is a host name, not an IP address: Let's Encrypt
  issues certificates by DNS name.
- **Ports 80 and 443 reachable from the internet** — Caddy answers the ACME
  challenge on port 80 and serves HTTPS on 443. A firewall or NAT that blocks
  either stops the certificate from issuing.

Then change all three URL variables in `.env` in one edit (a partial edit
signs you out straight after sign-in; see the warning under
[Clone and configure](#clone-and-configure)), and bring the stack up:

```dotenv
FRONTEND_URL=https://chat.example.com
BACKEND_URL=https://chat.example.com/api
ALLOWED_ORIGINS=https://chat.example.com
```

```bash
docker compose up -d
```

`BACKEND_URL` includes the `/api` path because that is where the browser reaches
the backend and Caddy strips the prefix before forwarding. This is the
one-origin layout, so no `AUTH_COOKIE_DOMAIN` is needed: a single host-only
cookie covers both.

<Callout type="warning">
  **Change the three URLs together**, as [Configuration &
  environment](/self-hosting/configuration#service-urls) warns. Updating only
  some of them gives you a sign-in that appears to succeed and then silently
  signs you out.
</Callout>

Two proxy details the backend depends on are already in the block: the real
client address arrives as a single-value `X-Forwarded-For` (the auth rate
limiter counts per address), and Chat runs on `/api` stream through instead of
being buffered, so a reply arrives incrementally.

Caddy here does **not** rate-limit: the stock image has no rate limiter. The
[rate-limit section](/self-hosting/production#put-a-rate-limiter-in-front) still
applies to a deployment anyone hostile can reach.

Caddy's `caddy_data` volume holds the issued certificates and account key, and
`caddy_config` holds its autosaved configuration. Keep both across recreates, or
every restart asks Let's Encrypt for a new certificate and can hit its rate
limit.

## Manual install

Install by hand when you want to edit `.env` before first boot, or run from a
clone of the repository.

<Steps>

### Clone and configure

```bash
git clone https://github.com/willdady/platypus.git
cd platypus
cp .example.env .env
```

Edit `.env`. At minimum set:

- `BETTER_AUTH_SECRET` — a secure random string (32+ characters).
- `ADMIN_EMAIL` / `ADMIN_PASSWORD` — credentials for the initial admin user.
  **Required on first boot**; the backend refuses to start without them.
- `ALLOWED_ORIGINS` — the origins the browser loads the frontend from. The
  backend reads this at module load and **throws before the HTTP server
  starts** if it is unset, so it is required whatever the value.
- `BACKEND_URL` — the URL the browser uses to reach the backend (e.g.
  `http://localhost:4000`).
- `FRONTEND_URL` — the URL the backend uses to build links back into the web
  app (resource links in tool output, MCP OAuth redirects).

The shipped `.example.env` sets all four URL-shaped values for `localhost`, so
on a laptop only `ADMIN_PASSWORD` needs a value before the stack will start.

If you serve the frontend and backend as two subdomains of one parent domain,
also set `AUTH_COOKIE_DOMAIN` to that shared parent (e.g. `example.com`). Two
hosts with different parent domains are not supported; the backend refuses to
start rather than serve pages whose server-rendered requests are silently
unauthenticated. See
[Supported topologies](/self-hosting/configuration#supported-topologies).

<Callout type="warning">
  **The three URL variables change together.** `ALLOWED_ORIGINS`,
  `FRONTEND_URL` and `BACKEND_URL` are one set — plus `BETTER_AUTH_URL`, which
  `compose.yaml` derives from `BACKEND_URL`. Moving off `localhost` and
  updating only some of them produces the hardest failure to diagnose in this
  stack: you sign in successfully and are immediately signed out again, because
  the cookie was issued against an origin the browser isn't on. Change all
  three in one edit.

That is separate from the hostname topology above: all four can be right and
the app still cannot authenticate server-side requests if the two origins are
on unrelated hosts, which is why the backend checks the topology and refuses to
start when no cookie can cover both.

</Callout>

Both services read the same root `.env` via `env_file`. The full set of
variables is documented in [Configuration & environment](/self-hosting/configuration)
and the [Reference](/reference).

### Start the stack

The clone's `compose.yaml` points at `:latest`, so pin a version first, as
[Image tags](#image-tags) describes. Then:

```bash
docker compose up -d
```

Compose pulls the images, starts PostgreSQL, runs the backend (which seeds the
database on first boot), then starts the frontend.

### Sign in

Open `http://localhost:3000` and sign in with the `ADMIN_EMAIL` /
`ADMIN_PASSWORD` you configured. You land in the **Default Organization**, ready
to create its first Workspace.

</Steps>

## First boot

### What first boot creates

This is the canonical account of first-boot seeding; other pages link here.

When the backend starts against a database with **no Organizations**, it seeds:

- a **Default Organization**,
- an **admin user** from `ADMIN_EMAIL` / `ADMIN_PASSWORD` (granted the platform
  `admin` role — the **Operator**), and
- that user's membership of the Default Organization.

No Workspace: a Workspace cannot run a Chat until it has a Provider, so you
create the first one yourself with **Add workspace**, which asks for a Provider
as part of creating it.

**The seeding rule, stated once:** the seed runs when the `organization` table
is empty, and only then. It is not "when no matching admin exists". Once one
Organization exists — however it got there — every subsequent boot skips the
seed silently, and editing `ADMIN_EMAIL` / `ADMIN_PASSWORD` afterwards changes
nothing. Manage users from the app after first boot.

<Callout type="warning">
  `ADMIN_EMAIL` and `ADMIN_PASSWORD` are **required on first boot and have no
  default in code**. With either unset the backend logs `... environment
  variable is required to seed the initial admin user` and exits non-zero
  without starting the HTTP server — it does not retry, because a missing
  variable fails the same way every time. The shipped `.example.env` leaves
  `ADMIN_PASSWORD` empty so a copied-and-forgotten deployment cannot start with
  a known password; choose one before first boot. A deployment that doesn't
  start from that file (Kubernetes, a hand-rolled env) must set both.
</Callout>

Nothing partial survives a failed seed. Configuration is checked before
anything is written; the Organization, membership and Workspace go in one
transaction; and the admin user — which better-auth writes outside that
transaction — is deleted again if the transaction fails. So a failed first boot
leaves an empty database, and fixing the cause and restarting is the whole
recovery.

### Recovering from a failed first boot

If the backend exits at startup, read `docker compose logs backend` — the fatal
line names the cause. Two of them need more than a restart:

- **"A user already exists for … in a database with no organizations"** — an
  earlier attempt left the admin user behind and compensation couldn't remove
  it. The seed refuses to promote an existing account to admin. Delete that one
  user, or point `ADMIN_EMAIL` at a different address, then restart.
- **"This database has an organization but no organization members"** — a
  deployment seeded by a release from before seeding was atomic. Nobody can
  sign in and the seed will never run again, because an Organization exists.

The escape hatch for both is to throw the database away and seed again:

```bash
docker compose down -v
docker compose up -d
```

<Callout type="error">
  `docker compose down -v` **destroys the `postgres_data` volume and every byte
  of data in it** — Chats, Agents, Providers, uploaded files. On a first boot
  that never completed there is nothing to lose, which is the only situation
  this page recommends it in. On any other deployment, back up first.
</Callout>

### The default admin

The installer generates a random password for `admin@example.com` unless you
set `ADMIN_EMAIL` / `ADMIN_PASSWORD`. A manual install starts from the shipped
`.example.env`, which leaves `ADMIN_PASSWORD` empty: **set it** in `.env`
before first boot. The old `admin@example.com` / `admin123` pair is refused in
production, and any password under 8 characters is refused everywhere. Either
way, the values in place at seed time are the ones that stick. Change the
password from the in-app account settings after you first sign in.

## Health checks

The backend image's health check polls its `GET /health` endpoint, the frontend
image's polls its home page, and the database health check runs `pg_isready`.
Inspect status with:

```bash
docker compose ps
docker compose logs -f backend
```

`GET /health` is **liveness**: it answers `ok` as long as the process is up,
without asking the database, so an orchestrator can restart a pod that is alive
but stuck. `GET /ready` is **readiness**: it answers `200` only when the backend
could actually serve a request — a `SELECT 1` against Postgres answered within
two seconds and the process is not shutting down. Once a stop signal has
started the shutdown drain, `/ready` answers `503` (new runs are refused), while
`/health` keeps answering `ok`; a load balancer should route traffic by
`/ready`, and remove the instance the moment it turns `503`, so in-flight work
finishes instead of arriving at a drain.

A backend stuck in `starting`/`unhealthy` is almost always a database connection
or a missing required env var — check `docker compose logs backend`. A backend
that **exited** rather than gone unhealthy is a startup failure: a seed that
couldn't complete, a `PLATYPUS_PLUGINS` entry that couldn't resolve, or an unset
`ALLOWED_ORIGINS`. All three name themselves in the log's last line.

## Upgrading

```bash
docker compose pull      # fetch the images your tags point at
docker compose up -d     # recreate containers with the new images
```

An installer-made deployment pins exact versions, so `pull` fetches nothing new
until you change both tags in `compose.override.yaml` to the release you want.
The backend applies any pending schema changes on startup. Your data persists in
the `postgres_data` volume across upgrades.

What a given version hop needs on top of that — and the `pg_dump` you should take
first — is on [Upgrading](/self-hosting/upgrading).

### Rolling back

Rollback is a **tag change**, not a git operation. Checking out an older git tag
and running `docker compose up -d` from there pulls `:latest` — the newest
release — and rolls nothing back, because the shipped compose file doesn't pin a
version.

Edit the pinned tags in your `compose.override.yaml` back to the version you
were on, and bring the stack up again. Use exact versions here even if you
normally pin the major line — `:2` has no way to express "the release before
this one":

```bash
docker compose up -d
```

<Callout type="warning">
  Image rollback does not roll the database back. Schema changes the newer
  release applied on startup are still in place, and an older backend is not
  tested against them. Take a database backup before upgrading if you need a
  rollback path you can rely on.
</Callout>
