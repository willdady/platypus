# Upgrading

An upgrade is a pull and a recreate:

```bash
docker compose pull
docker compose up -d
```

Everything else on this page is what to do around those two commands. Read the
section for the version you are **coming from** — the requirements accumulate, so
a 1.x deployment moving to the current release needs every section below it.

## What every upgrade does

**Pending database migrations run when the backend container starts**, before the
HTTP server comes up. You don't opt in and there is no flag to skip it, so treat
every upgrade as one that can change your schema.

**Migrations do not run backwards.** Putting an older image tag back leaves the
newer schema in place under a backend that was never tested against it.

<Callout type="warning">
  **Take a database backup first.** It is the only rollback path that works, and
  the `pg_dump` command is in [Running in
  production](/self-hosting/production#back-the-database-up-on-a-schedule-and-before-every-upgrade).
  Uploaded files are not in that dump — back those up from the same moment, or a
  restore gives you Chats whose File parts have vanished.
</Callout>

Two more things worth doing every time:

- **Pin your image tags** in a `compose.override.yaml`, so you know what you're
  running and what you'd be going back to. Rollback is a tag change, not a git
  checkout — see [Rolling back](/self-hosting/docker-compose#rolling-back).
- **Bump both images together.** The backend and frontend are released as a pair
  and are only tested against each other.

## Coming from 3.30

### Some MCP servers must be signed in to again

An MCP server using OAuth keeps the authorization server that issued its tokens,
so a later token refresh can be checked against the same one. Platypus used to
discover and record that server on the fly for servers authorized before it kept
the record. That repair is gone in 4.0.

If such a server is still connected, its stored token can no longer be
refreshed: the MCP fails the same way an expired token does. Sign in to it again
from its MCP page. A server authorized since Platypus started keeping the record
is unaffected.

### Kanban and Trigger write tools are split into create and update

Each create-or-update tool is now two tools: a create that requires every field a
new record needs, and an update that changes only the fields you pass.

| Tool set      | Before          | After                            |
| ------------- | --------------- | -------------------------------- |
| Kanban Cards  | `upsertCard`    | `createCard`, `updateCard`       |
| Kanban Cards  | `upsertComment` | `createComment`, `updateComment` |
| Kanban Boards | `upsertBoard`   | `createBoard`, `updateBoard`     |
| Kanban Boards | `upsertColumn`  | `createColumn`, `updateColumn`   |
| Triggers      | `upsertTrigger` | `createTrigger`, `updateTrigger` |

An Agent or Skill whose Instructions tell it to call one of the old tools no
longer has it, so rewrite those Instructions to name the right half. Chats that
already ran keep their record of the old names and still show them.

### Stranded Trigger schedules are repaired on upgrade

A Cron Trigger whose next run time was lost to the old scheduler is put back on
its schedule automatically when the backend container starts; there is nothing
to do. A Trigger whose cron expression no longer parses is left alone and named
in the backend log, so you can fix or delete it.

### Dashboards are removed

The upgrade deletes every Dashboard and its widgets, and there is no export.
Copy anything you want to keep before you upgrade.

The **Dashboards** Tool set is gone too, and every Agent that had it loses it.
An Agent or Skill whose instructions tell it to call `listDashboards`,
`listWidgets` or `updateWidgetData` no longer has those tools, so rewrite those
instructions.

To keep showing data your Agents produce, use a purpose-built dashboard tool such
as Grafana or Metabase, and have the Agent write to the store it reads from.

### Deployment URLs are required, and sign-up is invitation-only

Three settings that used to fall back silently must now be set, and the backend
refuses to start without them, naming the one at fault:

- **`DATABASE_URL`** — no fallback to node-postgres' `PG*` variables. Compose
  sets this for you; a hand-rolled environment must set it.
- **`BETTER_AUTH_URL`** — no fallback to `http://localhost:4001`. Compose
  derives it from `BACKEND_URL`.
- **`FRONTEND_URL`** — no fallback to `http://localhost:3001`. It must match the
  URL people load the app from, so check `.env` before you upgrade.

`REQUIRE_INVITATION_TO_SIGN_UP` now defaults to **true**: after the upgrade,
accounts can only be created by redeeming an invitation link. If you meant to
keep public sign-up open, set it to `false`. See
[Who can create an account](/self-hosting/users-and-access#who-can-create-an-account).

The example admin password no longer works in production. With
`NODE_ENV=production`, which the published image sets, first boot refuses the
well-known `admin@example.com` / `admin123` pair and exits, as it already did
for any password under 8 characters. The shipped Compose `.example.env` now
leaves `ADMIN_PASSWORD` empty, so set one before first boot. A deployment that
has already seeded its admin is unaffected: the seed never runs again, so
**change that account's password from the app** if it is still the example one.

### An unsupported cookie topology stops the backend

A backend and frontend on hosts no session cookie can cover — different parent
domains — used to log an error and start anyway, leaving every server-rendered
request unauthenticated. It now stops the backend at boot, naming both hostnames
and `AUTH_COOKIE_DOMAIN`, and so does a malformed `AUTH_COOKIE_DOMAIN`. Put both
services on one origin or on two subdomains of one parent domain; see
[Supported topologies](/self-hosting/configuration#supported-topologies).

### Session lifetimes are documented as fixed

Session lifetimes were never configurable, and there is nothing to change; the
lifetime and the revocation delay are now stated in
[Sessions](/reference/backend-configuration#sessions) rather than left implicit.

### The session read has a bound

`/auth/get-session` is no longer exempt from rate limiting: it allows 300 reads
per rolling 60 seconds, far above what reloading and tab-switching produce. Only
a runaway client reaches it. If you put your own limit on that path at the
proxy, keep it well above the number of reads a page load makes.

### Plugin authors: `frontendUrl` is never undefined

`ctx.frontendUrl` in the Plugin SDK is typed `string`, not `string | undefined`,
because the backend cannot boot without `FRONTEND_URL`. Drop any
`if (ctx.frontendUrl)` guard; it is always a frontend origin.

## Coming from 3.30

### The Docker Sandbox overlay is renamed

The overlay that enables the Docker Sandbox is now `compose.docker-sandbox.yaml`;
`compose.sandbox.yaml` is gone. If you run it:

1. Change `-f compose.sandbox.yaml` to `-f compose.docker-sandbox.yaml` in your
   `docker compose` commands, and in any script or systemd unit that names the
   old file.
2. Remove `@platypus/docker` from `PLATYPUS_PLUGINS` in `.env`. The overlay now
   adds it to your `.env` list instead of replacing that list, so listing it
   there as well names it twice, and the backend stops at boot because a Plugin
   is listed more than once.
3. If you edited the Plugin list inside the old overlay, move those Plugins to
   `PLATYPUS_PLUGINS` in `.env`. The new overlay keeps no list of its own.

See [Docker adapter](/self-hosting/sandbox/docker#enabling-it).

### PLATYPUS_PLUGIN_CONFIG is removed

Plugin config and credentials now come only from one
`PLATYPUS_PLUGIN_CONFIG_<NAME>` variable per Plugin. The backend won't start
while `PLATYPUS_PLUGIN_CONFIG` is still set to a value, so move its contents
before you upgrade.

For each key in the old JSON object, set a variable named after that key and
give it the key's value. `<NAME>` is the key without a leading `@platypus/`,
uppercased, with each `-` turned into `_`:

```bash
# Before
PLATYPUS_PLUGIN_CONFIG={"@platypus/docker":{"config":{"allowedNetworks":["shared-services"]}},"cloud-sandbox":{"credentials":{"apiToken":"dtn_live_…"}}}

# After
PLATYPUS_PLUGIN_CONFIG_DOCKER={"config":{"allowedNetworks":["shared-services"]}}
PLATYPUS_PLUGIN_CONFIG_CLOUD_SANDBOX={"credentials":{"apiToken":"dtn_live_…"}}
```

Then delete `PLATYPUS_PLUGIN_CONFIG`. See [Plugin config &
credentials](/self-hosting/configuration#plugin-config--credentials) for the
naming rule in full.

## Coming from 3.29

`/compact` is now a built-in Chat command, so `compact` is no longer a valid
Skill name. A Skill already called that keeps working when an Agent loads it,
but typing `/compact` runs the built-in instead, and the Skill can't be saved
again under that name. Rename it to keep invoking it by hand.

## Coming from 3.27

The backend image now sets `PORT` to `4000`, the port it has always exposed.
Under the shipped `compose.yaml` nothing changes. A backend container run any
other way with `PORT` unset used to serve on `4001` and now serves on `4000`, so
point its port mapping and health probes at `4000`, or set `PORT=4001` to keep
the old port.

With Compose, a `PORT` in your `.env` now takes effect where `compose.yaml` used
to override it. Remove it, or set it to `4000`.

## Coming from 3.26

The backend now checks its environment variables when it starts, and stops on a
value it can't use instead of quietly replacing it. A setting that booted before
can now stop the backend, so after upgrading, check that it came up; if it
didn't, its log names the variables to fix. The values most likely to catch an
existing deployment:

- A `STORAGE_BACKEND` other than `disk` or `s3`. It used to fall back to disk.
- A boolean such as `yes`, `no`, `on` or `off`. Only `true`, `false`, `1` and
  `0` are accepted; `EGRESS_ALLOW_PRIVATE_NETWORKS=no` used to _allow_ private
  networks.
- A timeout or interval of `0`, or one that isn't a whole number. A Chat or
  Trigger timeout used to fall back to its default.
- A `TIMEZONE` that isn't an IANA timezone name.
- `STORAGE_BACKEND=s3` without a bucket, or with only one of the two access
  keys. This used to fail only when a file was first stored.

See [Backend configuration](/reference/backend-configuration) for what each
variable accepts.

## Coming from 2.x

Configuration is stable across 2.x, and the migrations that run at container
start need no action from you. One behaviour change does.

**Triggers stop carrying Memory summaries.** Before 3.0 every Trigger run
carried your Memory summaries. 3.0 added **Include Memories** to the Trigger
form, and every existing Trigger has it **off**. A Trigger whose Instruction
quietly relied on a summary, such as "the project I mentioned" or "my usual
format", now has nothing to read it from. The run doesn't fail; it answers
differently. Turn **Include Memories** back on for those Triggers under
**Advanced settings**, or write the fact into the Instruction. See [Memories in
a run](/building-with-platypus/triggers#memories-in-a-run).

<Callout type="info">
  New **gate-able** core Plugins introduced in a later release are **not**
  auto-enabled. If a release adds one you want, add its name to
  `PLATYPUS_PLUGINS` yourself — a pinned list never grows on its own. Check
  **Organization settings → Plugins** after the restart to see what actually
  loaded.
</Callout>

## Coming from 1.x

Platypus 2.0 introduced the
[Plugin system](/extending/plugin-api-and-config#the-plugin-model). The web-fetch
tool set and the Docker Sandbox backend stopped having their own environment
variables and became **Plugins**, enabled through `PLATYPUS_PLUGINS` and
configured through `PLATYPUS_PLUGIN_CONFIG`. Since 4.0 each Plugin has its own
`PLATYPUS_PLUGIN_CONFIG_<NAME>` variable instead, and the steps below use that.

For that hop specifically the changes are **deployment configuration only** —
three variables removed, their behaviour moved onto the Plugin surface, no
application-data change. It is an edit to your `.env` and a restart. Later 2.x
releases do bring migrations, which is why the section above still applies.

<Callout type="warning">
  **The most common upgrade mistake: losing the web-fetch tool.** An unset or
  empty `PLATYPUS_PLUGINS` loads **only** the always-on core tool sets — there
  is no built-in default. A 1.x `.env` predates the Plugin system and has no
  `PLATYPUS_PLUGINS` line at all, so upgrading silently strips web-fetch from
  every Agent. Nothing errors; the tool is gone. To keep it you **must** add
  `@platypus/web-fetch` to `PLATYPUS_PLUGINS`.
</Callout>

### The three removed variables

| Removed in 2.0                             | Replaced by                                                                                |
| ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `PLATYPUS_SANDBOX_DOCKER_ENABLED`          | Listing `@platypus/docker` in `PLATYPUS_PLUGINS` (list membership _is_ the enable switch). |
| `PLATYPUS_SANDBOX_DOCKER_ALLOWED_NETWORKS` | `config.allowedNetworks` in `PLATYPUS_PLUGIN_CONFIG_DOCKER`.                               |
| `FETCH_TOOL_IGNORE_ROBOTS_TXT`             | `config.ignoreRobotsTxt` in `PLATYPUS_PLUGIN_CONFIG_WEB_FETCH`.                            |

All three are inert in 2.x. Delete them from your environment.

### Migration checklist

1. **Keep web-fetch.** Add `@platypus/web-fetch` to `PLATYPUS_PLUGINS`.
2. **If you ran the Docker sandbox** (`PLATYPUS_SANDBOX_DOCKER_ENABLED=true`):
   keep composing the overlay, now named `compose.docker-sandbox.yaml`. It adds
   `@platypus/docker` to `PLATYPUS_PLUGINS` for you, so don't list it in `.env`.
3. **If you set `PLATYPUS_SANDBOX_DOCKER_ALLOWED_NETWORKS`:** move the value into
   `config.allowedNetworks` in `PLATYPUS_PLUGIN_CONFIG_DOCKER`. The old
   comma-separated list becomes a JSON array of strings.
4. **If you set `FETCH_TOOL_IGNORE_ROBOTS_TXT=true`:** move it to
   `config.ignoreRobotsTxt` in `PLATYPUS_PLUGIN_CONFIG_WEB_FETCH`.
5. **Delete the three removed variables.**
6. **Restart the backend**, then confirm the result in **Organization settings →
   Plugins**, which lists everything loaded at boot.

Boot is **fail-loud**: a listed Plugin that can't be resolved, or a
`PLATYPUS_PLUGIN_CONFIG_<NAME>` variable that is malformed or matches no loaded
Plugin, aborts startup rather than degrading quietly. The error names the Plugin
or the variable to fix.

### Before and after

A 1.x deployment that enabled the Docker sandbox with a network allowlist and
skipped `robots.txt`:

```bash
# 1.x
PLATYPUS_SANDBOX_DOCKER_ENABLED=true
PLATYPUS_SANDBOX_DOCKER_ALLOWED_NETWORKS=shared-services,public-tools
FETCH_TOOL_IGNORE_ROBOTS_TXT=true
```

becomes:

```bash
# current
PLATYPUS_PLUGINS=@platypus/web-fetch,@platypus/docker
PLATYPUS_PLUGIN_CONFIG_DOCKER={"config":{"allowedNetworks":["shared-services","public-tools"]}}
PLATYPUS_PLUGIN_CONFIG_WEB_FETCH={"config":{"ignoreRobotsTxt":true}}
```

Treat each `PLATYPUS_PLUGIN_CONFIG_<NAME>` like any secret-bearing variable — it
can carry a Plugin's `credentials` block. Inject it from your secret manager; never commit it.

### Also new in 2.0

The **SSH** Sandbox backend, `@platypus/ssh` — the one Sandbox option viable in
horizontally-scaled deployments, where Docker cannot run. See
[SSH adapter](/self-hosting/sandbox/ssh).
