# Sandbox backends

A **Sandbox** is a persistent, per-Workspace execution environment. It exposes a
fixed set of shell and filesystem tools to Agents, and a **backend** is the
adapter that decides where those tools actually run — a local container, a remote
host, a hosted sandbox service.

Two reference backends ship: `@platypus/docker` and `@platypus/ssh`. Contributing
a third is one of the better-scoped things you can build against Platypus.

## The contract is closed

Your adapter implements `SandboxBackend` from
[`@platypuschat/plugin-sdk`](https://www.npmjs.com/package/@platypuschat/plugin-sdk):
five tools plus a teardown, and two optional members for
[moving whole files](#moving-whole-files). You **cannot** add, rename or re-sign a
tool. Read the exact signatures off the package you have installed — this page
states the rules those types don't encode.

| Method      | Does                                              |
| ----------- | ------------------------------------------------- |
| `shellExec` | Runs a command and returns stdout, stderr, exit code |
| `fsRead`    | Reads a file, optionally a line range             |
| `fsWrite`   | Creates or overwrites a file                      |
| `fsEdit`    | Replaces one exact string with another            |
| `fsList`    | Lists a directory, optionally recursive or globbed |
| `destroy`   | Tears the environment down                        |

That closure is the point: an Agent's Instructions must not depend on which
backend it runs on, which is what lets an Operator swap Docker for a hosted
service without re-prompting anything. A backend that can do more than these five
things exposes the extra through a
[Tool set](/extending/tool-sets), not by widening this interface.

## Rules your adapter must honour

- **Paths are relative to the workspace root**, and your adapter chooses where
  that root is. Platypus rejects absolute paths before your adapter sees them.
- **`shellExec` is stateless.** A fresh shell per call with an explicit working
  directory — no session state carried between calls. The default timeout is 60
  seconds and the hard cap is 600.
- **`fsWrite` takes an explicit mode**, `create` or `overwrite`. Never silently
  create-or-overwrite: `create` fails if the file exists. Either mode creates
  missing parent directories.
- **`fsEdit` replaces an exact old string with a new one.** It is not a patch or
  diff format. Fail if `oldString` is absent or appears more than once.
- **`fsRead` decodes strict UTF-8.** Fail on a file that isn't valid UTF-8
  rather than decode it lossily. `lineRange` is 1-indexed and inclusive.
- **Three of the five tool responses carry a `truncated` flag** —
  `shellExec`, `fsRead` and `fsList`. The caps are **100,000 bytes** per
  `shellExec` stream (stdout and stderr each), **1,000,000 bytes** per `fsRead`
  file and **1,000 entries** per `fsList`. Set the flag when output reaches a
  byte cap — output exactly at the cap counts — or when a listing had more
  entries than the cap. Truncate yourself if your environment can't honour a cap
  natively. `fsWrite` and `fsEdit` have no such flag; there is nothing to cut.
- **`destroy` must be idempotent.** It fires on row delete, on a backend change,
  and best-effort when a Workspace is deleted. Forcing the delete or the backend
  change skips it. It runs on a fresh adapter from `create`, not the one that ran the
  tools — Platypus calls `create` again every Chat turn — so find the resource
  from `ctx`, never from state held in memory. It need not destroy anything: the
  SSH adapter's `destroy` only disconnects, because the host belongs to the
  Operator, not to Platypus.
- **State persists across Chat turns**, keyed on the Organization and Workspace.
  That persistence is the whole value — long-running build-and-test workflows
  depend on it.

<Callout type="warning">
  **Tool calls are not serialised.** Platypus forwards them concurrently — there
  is no per-Sandbox lock and no queue — and a model that emits parallel tool
  calls does this routinely. Two `shellExec` calls, or a `shellExec` and an
  `fsWrite`, can be in flight against the same environment at once. The contract
  is "a Sandbox is a Linux box": racing commands are the caller's problem, but
  any connection or container handle your adapter caches must be safe for
  concurrent use, or you will corrupt state under a model you didn't write.
</Callout>

## Moving whole files

Two optional members sit beside the five tools. They move a whole file into or
out of the Sandbox, byte for byte, and the bytes never reach the model. Neither
is a Tool.

| Member         | Does                                                                                                                                   |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `fsReadBytes`  | Returns a whole file. Rejects a file larger than the `maxBytes` it is handed, a missing path, and anything that is not a readable file |
| `fsWriteBytes` | Writes a whole file. Always overwrites, and creates missing parent directories                                                         |

- **Move bytes, not text.** Nothing is decoded: a file full of NUL bytes and
  invalid UTF-8 comes back identical. The five tools' caps don't apply.
- **Size a file before you pull it.** You may reject an oversized file before
  transferring it.
- **`fsWriteBytes` never refuses an existing path.** There is no create-only
  mode to honour.

<Callout type="warning">
  **Handle every file up to 25 MiB, or leave the member out.** 25 MiB is the
  transfer bound on every backend, in both directions, exported as
  `SANDBOX_TRANSFER_MAX_BYTES`. Neither you nor the Operator can change it. If
  your service caps requests below the bound, chunk the transfer inside your
  adapter.
</Callout>

Leave a member out and Platypus moves no files in that direction on your
backend. There is no fallback through `fsRead` or `fsWrite`. The two members are
independent, so a backend can implement `fsReadBytes` alone.

## The signal your tool methods get

Every tool call gets a third argument carrying `{ signal }`, and so do the two
file-transfer members. Pass it to whatever actually runs the work — the exec
request, the HTTP call to your sandbox service — and the command stops when
Platypus stops waiting.

It fires for either of two reasons, and you do not need to tell them apart:

- someone in the Chat pressed stop, or their run was cancelled;
- the run hit its per-step or per-run timeout.

Honour it from your **first** await, not just once a command is streaming.
Resolving a workspace root, opening a connection and creating an exec are
usually unbounded calls to a daemon or a remote API, and they happen before any
per-command timeout of yours is armed — so they are exactly where an abort has
nothing else behind it. Reject when it fires rather than returning an exit code:
the command did not finish, and a fabricated result would go into the
transcript as though it had.

<Callout type="info">
  **Ignoring the signal is allowed, and it costs you a command you are no longer
  being paid for.** An adapter that never reads it behaves as every adapter did
  before the argument existed: Platypus stops waiting either way, the turn is
  never held open, and the chat returns to the person straight away. Your
  command runs on until its own timeout, holding a container, a connection or a
  billed sandbox minute for an answer nobody will read.
</Callout>

From `apiVersion: 3` the argument is required, so read `options.signal`
without a `?.`. An adapter written before it existed declares two parameters,
still satisfies `SandboxBackend`, and still works — Platypus passes the third
argument regardless and your method ignores it.

`AbortSignal` is a platform global rather than something the SDK declares, so a
`tsconfig.json` with `"lib": ["esnext"]` and no `@types/node` reports `Cannot
find name 'AbortSignal'`. Add `@types/node` — you are running on Node — or
`"dom"` to `lib`.

## Contributing one

Add an entry to `contributes.sandboxBackends`. A
`SandboxBackendContribution` declares:

- **`backend`** — the discriminator string persisted on the Sandbox row. Write
  it bare: a third-party Plugin's is stored as `<manifest name>.<backend>`,
  [prefixed like every contribution id](/extending/plugin-api-and-config#two-names-two-jobs).
- **`name`** — the label an Org Admin picks from.
- **`configSchema`** — a Zod schema for the non-secret per-Workspace settings
  (region, image, host). It may also be a **factory** taking the Plugin's
  deploy-time block, when the allowed shape depends on what the Operator
  configured. Read the allowed shape off `plugin.config`; `plugin.credentials`
  and `plugin.logger` are there too, so the factory can say why it refused a
  value.
- **`credentialsSchema`** — a Zod schema for the secret per-Workspace material
  (API tokens, private keys).
- **`create`** — returns your adapter, given the validated per-Workspace config
  and credentials, plus the Plugin's shared deploy-time block.

<Callout type="warning">
  **Both schemas must accept `{}`.** The **Workspace settings → Sandbox** form
  has fields only for the Docker and SSH backends; for yours it saves an empty
  `config` and `credentials`. A schema with a required field makes every save
  fail with a 400. Put what your backend needs — region, endpoint, API token —
  in your Plugin's
  [deploy-time config and credentials](/extending/plugin-api-and-config#deploy-time-config-and-credentials)
  and read them in `create`. That block is shared by every Workspace on the
  deployment.
</Callout>

Then list your Plugin in `PLATYPUS_PLUGINS`. List membership **is** the enable
switch — there is no separate per-backend flag. Leave the Plugin out and its
backend isn't offered in the **Backend** picker.

<Callout type="warning">
  **Removing the Plugin later strands every Sandbox already using its backend.**
  Their Agents lose the Sandbox tools, and deleting one fails until you list the
  Plugin again — or force the delete with **Delete anyway** and leak whatever
  the adapter created.
</Callout>

<Callout type="warning">
  If your backend gives a Sandbox reach into host networks or internal services,
  make that reach **default-deny and admin-curated**: the Operator declares the
  eligible set at deploy time, an Org Admin picks a subset per Sandbox, and a
  Workspace Owner cannot widen it. Skip this and a Workspace Owner can point an
  Agent at your internal network by editing a form. The Docker adapter's network
  allowlist is the worked example — see
  [Sandbox infrastructure](/self-hosting/sandbox).
</Callout>

<Callout type="info">
  The reference Docker adapter mounts the host Docker socket, which grants its
  container effective root on the host. It is scoped to development and
  single-node self-hosting, explicitly not to multi-tenant or hostile-tenant
  environments. Don't copy that trade-off into a backend meant for either.
</Callout>
