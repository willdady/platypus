# Installing plugins

The backend loads a third-party plugin by importing its npm package at boot, so
the package has to be installed where the backend can find it. Core plugins are
built in and need no install. How you install a third-party one depends on how
you run Platypus:

| You run                           | Install the plugin by                                         | For                                |
| --------------------------------- | ------------------------------------------------------------- | ---------------------------------- |
| A checkout of the repository      | [Adding it to the backend](#from-a-repository-checkout)       | Working on Platypus or on a plugin |
| The published images              | [Building a custom backend image](#in-a-custom-backend-image) | Every real deployment              |
| The published images, on one host | [Bind-mounting it](#bind-mounting-a-plugin-trying-out-only)   | Trying a plugin out                |

Every route ends the same way: [list it and recreate the
backend](#list-it-and-recreate-the-backend), then [confirm it
loaded](#confirm-it-loaded).

## From a repository checkout

Add the package to the backend, from the backend's package directory:

```bash
pnpm add @acme/platypus-plugin
```

The example plugin, `@platypus-examples/tool-set`, is already installed in a
checkout. Skip straight to listing it.

## In a custom backend image

The published backend image loads only the plugins it ships with. To add one,
build your own image `FROM` it and install the plugin at build time. The result
works under Compose and Kubernetes alike, survives every container recreate, and
its image digest records exactly which plugin code a deployment runs.

The repository has a complete, working version of this in
[`examples/custom-image`](https://github.com/willdady/platypus/tree/main/examples/custom-image):
it builds the example plugin into an image and runs it with a Compose override.

<Steps>

### Pin the plugin in a lockfile

Make a directory for the image and record the plugins you want, with their exact
dependency tree, in a `package.json` and `package-lock.json`:

```bash
mkdir platypus-plugins && cd platypus-plugins
echo '{"private":true}' > package.json
npm install --package-lock-only @acme/platypus-plugin@1.2.0
```

List every plugin you want on that one `npm install` line. Commit both files:
the image installs exactly what the lockfile says, so two builds of the same
commit get the same code.

### Write the Dockerfile

In the same directory:

```dockerfile
FROM willdady/platypus-backend:3.10.2

COPY package.json package-lock.json /opt/platypus-plugins/
RUN cd /opt/platypus-plugins && \
    npm ci --omit=dev --no-audit --no-fund --cache /tmp/npm-cache && \
    rm -rf /tmp/npm-cache && \
    chown -R platypus:platypus /opt/platypus-plugins

RUN ln -s /opt/platypus-plugins/node_modules /app/apps/node_modules && \
    chown -h platypus:platypus /app/apps/node_modules
```

- **Pin the base image** to an exact version, or to a digest
  (`willdady/platypus-backend:3.10.2@sha256:…`). Never `latest`: you rebuild
  this image for every release, and you need to know which one it is built on.
- **The plugins go in their own directory**, outside the application's own
  packages, and the link puts them where the backend looks when it imports a
  plugin. Don't run `npm install` in the application directory instead: npm
  tries to reinstall the whole application and fails.
- **The `chown` lines are required.** The backend runs as the unprivileged
  `platypus` account, uid 1001, and the files have to belong to it.
- **The entrypoint, command, health check and `/data` handling** all come from
  the base image unchanged.

Each plugin carries its own copy of `@platypuschat/plugin-sdk`, separate from
the backend's. That is expected.

### Build and boot it

Build the image, then start it once with the plugin listed (see
[List it and recreate the backend](#list-it-and-recreate-the-backend)) before
you ship it anywhere. A plugin that fails to load stops the backend from
booting, so a boot is the test.

</Steps>

### Rebuild for every release

Upgrading Platypus is now a rebuild: bump the `FROM` tag, rebuild, and bump the
frontend tag to the same version. The backend and frontend images are released
as a pair and only tested against each other.

A stale base image fails in a specific way. Core accepts plugins written for its
current plugin API version and the one before
([which core versions a plugin runs on](/extending/plugin-api-and-config#which-core-versions-your-plugin-runs-on)).
Upgrade a plugin without upgrading the base, and the new plugin version can need
an API the old core doesn't have. The backend then refuses to boot, naming the
plugin and both versions.

<Callout type="warning">
  The `/app/apps/node_modules` link points at a location inside the published
  image. A release that reorganises the image can move it, and the backend then
  refuses to boot with the plugin "failed to resolve", although nothing you
  control changed. Boot every rebuilt image before it replaces the running one.
</Callout>

## Running a custom image with Compose

Put the image in a `compose.override.yaml` next to `compose.yaml`. Compose merges
it automatically. The frontend, health check, `./data` mount and entrypoint all
carry on unchanged.

**Built on the host running Compose**, with the Dockerfile directory beside
`compose.yaml`:

```yaml
services:
  backend:
    build: ./platypus-plugins
    image: platypus-backend-custom
  frontend:
    image: willdady/platypus-frontend:3.10.2
```

The `image` line names what Compose builds. Leave it out and Compose tags your
build with the base file's `willdady/platypus-backend:latest`, replacing your
local copy of the published image.

**Pushed to a registry** by your own CI, override only the image:

```yaml
services:
  backend:
    image: registry.example.com/platypus-backend-custom:3.10.2
  frontend:
    image: willdady/platypus-frontend:3.10.2
```

Run `docker login` for that registry on the host first, or pulling it fails.

Either way, **pin the frontend to the version your backend image is built on**.
`docker compose pull` no longer moves the backend, so a frontend left on a
floating tag drifts ahead of it.

### Upgrading

<Callout type="warning">
  The usual `docker compose pull` fails when the backend is built on the host:
  Compose tries to pull `platypus-backend-custom` from Docker Hub and stops with
  an error suggesting `docker login`. Add `--ignore-buildable`.
</Callout>

After bumping the `FROM` tag and the frontend tag together:

```bash
docker compose pull --ignore-buildable
docker compose up -d --build
```

`--build` matters. Without it Compose reuses the image it built last time, and
the new frontend runs against the old backend.

With a registry image, push the rebuilt image under a new tag, bump both tags in
the override, and run the normal `docker compose pull` and `docker compose up -d`.
Always use a new tag. `pull` fetches from the registry, so an image you rebuilt
locally under an existing tag is replaced by the registry's copy on the next
pull.

## Bind-mounting a plugin (trying out only)

You can skip building an image by installing the plugin on the host and mounting
it into the published backend image.

<Callout type="error">
  **Not for production or for more than one replica.** This is for trying a
  plugin out on one host.

- **Pure-JavaScript plugins only.** The image runs Alpine Linux, which uses
  musl. A plugin with a native dependency built on a typical glibc host fails
  to load.
- **Mount the whole `node_modules`, not just the plugin's folder.** The
  plugin's dependencies, `@platypuschat/plugin-sdk` among them, have to come
  with it: the image doesn't provide them. Mounted on its own, the plugin fails
  to resolve the SDK.
- **One host only.** Every replica needs an identical copy of the directory on
  its own host, kept in step by hand. On Kubernetes that means a `hostPath`
  volume, which ties the pod to one node. Build an image instead.
- **The mount target is inside the image.** A release that reorganises the
  image can move it, and the backend then refuses to boot with the plugin
  "failed to resolve", although nothing on your host changed.

</Callout>

Next to `compose.yaml`, install the plugin into a directory of its own:

```bash
mkdir plugins && cd plugins
echo '{"private":true}' > package.json
npm install --omit=dev @acme/platypus-plugin@1.2.0
```

Then mount its `node_modules` read-only in `compose.override.yaml`:

```yaml
services:
  backend:
    volumes:
      - ./plugins/node_modules:/app/apps/node_modules:ro
```

## List it and recreate the backend

Add the **package specifier** to `PLATYPUS_PLUGINS`:

```bash
PLATYPUS_PLUGINS=@platypus/web-fetch,@acme/platypus-plugin
```

The variable is one comma-separated list, and setting it **replaces** the
previous value rather than adding to it. Keep every plugin you already run.

Keep the list in **one** place: `.env`, the `environment` of your
`compose.override.yaml`, or an `ENV` line in your Dockerfile. A value under a
Compose file's `environment` wins over `.env`, and `.env` wins over the image's
`ENV`. So a list baked into the image is ignored while `.env` still sets one;
remove it from `.env` if you bake it in. The Sandbox overlay
`compose.sandbox.yaml` sets its own list, so composing it discards whatever `.env`
says (see [Plugins](/self-hosting/configuration#plugins)). When you run that
overlay, its list has to be your complete set.

Then recreate the backend:

```bash
docker compose up -d
```

`docker compose restart` is not enough: it restarts the container with the
environment it was created with, so an edited `PLATYPUS_PLUGINS` never reaches
it.

## Confirm it loaded

The backend logs one line per plugin at boot:

```bash
docker compose logs backend | grep "Loaded plugin"
```

A third-party plugin's line is labelled with its manifest name and
`(third-party)`. A plugin that fails to load stops the backend from booting, and
the last log line names the plugin and the reason.

In the app, **Organization settings → Plugins** lists what loaded — see
[Inspecting installed plugins](/self-hosting/configuration#inspecting-installed-plugins).
