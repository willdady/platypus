# Plugin API & config

Read this once. It covers what a plugin is, how core decides whether to load
yours, and where its deploy-time settings come from.

## The plugin model

A **plugin** is a distributable bundle — one package, one version, one config
namespace, one enable/disable switch. An Operator installs it at deploy time and
core loads it **in-process, with no isolation**. The trust boundary is the
deployment, not an install step: there is no marketplace, no hot reload, and no
in-app install button.

A plugin exports a `plugin` manifest from its package entry point. The manifest
declares its identity, the API major it needs, optional deploy-time schemas, and
a `contributes` block naming what it fills.

### Two names, two jobs

| This                          | Is                                                                              | Example                  |
| ----------------------------- | ------------------------------------------------------------------------------- | ------------------------ |
| The **npm package specifier** | What you publish, what an Operator installs and lists                           | `@acme/platypus-widgets` |
| The manifest **`name`**       | The config namespace, and the prefix on every contribution id **and tool name** | `widgets`                |

A third-party manifest `name` must be a url-safe slug — lowercase letters, digits
and hyphens — of up to 24 characters. Both are validated at boot.

The cap is there because the name is also the namespace on every tool name the
plugin contributes (see
[Tool names](/extending/tool-sets#tool-names)), and the composed
`<name>__<toolName>` has to stay inside what a model provider allows.

<Callout type="warning">
  A scoped, npm-style manifest `name` such as `@acme/platypus-widgets` is
  **rejected and aborts startup**, because it becomes the prefix on every
  contribution id. The Operator's backend won't come up until you ship a slug.
  Core plugins are exempt: their `@platypus/*` names are logical ids resolved
  from a built-in map, not published packages.
</Callout>

A manifest `name` must also be unique across the plugins a deployment loads.
Two plugins declaring the same one abort startup, with an error naming both
package specifiers.

<Callout type="warning">
  Installing a fork or a vendored variant alongside the plugin it came from is
  the trap: both ship the same manifest `name`, and the name is the key for
  deploy-time config and credentials. One would be handed the other's API token.
  The backend refuses to start instead — rename one of them in its manifest.
</Callout>

<Callout type="warning">
  Don't reuse a core plugin's name without its `@platypus/` scope. `web-fetch`
  and `@platypus/web-fetch` both read `PLATYPUS_PLUGIN_CONFIG_WEB_FETCH`, so the
  backend refuses to start with both loaded. A plugin named `ssh`, `docker` or
  `web-fetch` can't run beside that core plugin, and one named `tools-basic` or
  `tools-platform` fails on every deployment, because those two always load.
</Callout>

## Boot is fail-loud and all-or-nothing

Before the HTTP server starts, core loads the always-on core plugins, then reads
`PLATYPUS_PLUGINS`, resolves each name, validates its manifest, and registers its
contributions.

Any of these aborts startup with an error naming your plugin:

- it can't be resolved,
- its manifest is invalid,
- its deploy-time config or credentials fail their own schema,
- a Sandbox backend's `configSchema` factory throws while resolving,
- its manifest `name` is already declared by another loaded plugin,
- its manifest `name` is longer than the cap above,
- a Tool set statically declares a tool name over
  [its own cap](/extending/tool-sets#two-length-caps),
- a contribution is missing a required field,
- its contribution ids collide with another plugin's.

A contribution is shape-checked too, so an incomplete one is refused up front
rather than failing later inside somebody's Chat. TypeScript already requires the
fields; this check is what catches a plugin shipped as plain JavaScript, and what
turns a missing field into an error with your plugin's name on it.

Runtime is the opposite posture. An Agent granted a Tool set that has since been
removed loses that set's tools for the turn; its other Tool sets still serve.
**Strict at boot, forgiving at runtime.**

## Which core versions your plugin runs on

Set `apiVersion` from the SDK's `PLUGIN_API_VERSION` constant. It declares the
**minimum** core API major you need — not an exact match.

Core supports the current major and one previous, **N and N−1**, at the same
time. Anything inside that window loads. Core rejects your plugin only when its
`apiVersion` is newer than core supports — the Operator fixes that by upgrading
core, which they control — or below core's oldest supported major, meaning you're
targeting a dropped one. The boot error names your plugin and both versions.

### Contracts grow by optional members only

Within a major, every Extension-point contract grows only by **optional**
members. A new capability arrives as an optional method or field, never a new
required one. That is what lets a plugin built against an older minor keep
working after a core upgrade: it never uses what it doesn't know about.
Adding a whole Extension point is likewise additive.

Removing or re-signing a required member is a **windowed major bump** — the major
increments and core runs both N and N−1 for a release, so you have time to
migrate.

The practical consequence for you: a two-argument `create` keeps working after
core started passing a third argument, and a single-argument factory keeps working
after core started passing a second. Consume the new argument when you want it.

## Moving to API v3

v3 is the current major, and core supports **2 and 3** together. A v1 Plugin no
longer loads: boot stops with an error naming your Plugin and the oldest version
core supports.

v3 does one thing: the `{ signal }` argument on a
[Sandbox backend's](/extending/sandbox-backends#the-signal-your-tool-methods-get)
five tool methods is now **required** rather than optional. Set your
`apiVersion` to 3 and drop any `options?.` guard — read `options.signal`
directly. An adapter that never reads the argument needs no change beyond the
number.

<Callout type="warning">
  Dropping the guard while your manifest still says 2 is the trap. Platypus 3.0
  to 3.7.3 accept 2 but never pass the argument, so a self-hoster on one of them
  loads your Plugin and the first unguarded `options.signal` throws inside
  somebody's Chat turn. Raising the number is what makes that core refuse the
  Plugin at boot instead.
</Callout>

## Moving from API v1

A v1 Plugin must move to 2 or later before it loads again. What v2 changed:
everything core had always supplied on every turn became **required** rather
than optional, so drop the guards on these:

- `ctx.registerCloser(close)` — register something to close when the turn ends,
  on a [Tool set](/extending/tool-sets#releasing-what-a-factory-opened) or a
  [Web-search backend](/extending/web-search-backends#releasing-what-you-opened).
- `plugin.logger.info(...)` — the [logger](#logging) core binds to your name.
- `plugin` itself, on all three contribution factories.

One member changed shape rather than optionality. A Sandbox backend's
`configSchema` **factory** receives the whole deploy-time block, where under v1
it received the `config` half on its own. Read `plugin.config` where the argument
used to be the config itself — and you can now reach `plugin.credentials` and
`plugin.logger` from there too.

## Deploy-time config and credentials

Some plugins need settings that belong to the **Operator**, not to an end user: a
region, an API token. Declare them as `configSchema` (non-secret) and
`credentialsSchema` (secret) on the manifest itself.

The Operator supplies the values through your Plugin's own
[`PLATYPUS_PLUGIN_CONFIG_<NAME>`](/self-hosting/configuration#plugin-config--credentials)
variable, named from your manifest `name`: `acme-search` reads
`PLATYPUS_PLUGIN_CONFIG_ACME_SEARCH`. Core validates them at boot and
injects the resolved block into **every one** of your contributions:

- a **Tool set** factory receives it as an appended second argument;
- a **Sandbox backend** `create` receives it as a third argument, alongside the
  per-Workspace config and credentials;
- a **Web-search backend** `createExecutors` receives it as a second argument,
  alongside the request context.

You can ignore the argument in all three. What you cannot do is receive nothing:
core always passes it.

**One block is shared** across all of a plugin's contributions and all tenants.
That is deliberate, and it is the mechanism that lets a plugin's Sandbox backend
and its management Tool set authenticate with the same credential — one vendor
token driving both.

<Callout type="warning">
  Because it is one block for the whole deployment, this is **not** a per-user
  or per-Workspace secret. Don't reach for it to hold a tenant's credential;
  every Workspace on the deployment would be using the same one. Genuinely
  tenant-specific values belong on the per-Workspace Sandbox row, which is a
  separate layer above this one — the two layer, they do not merge.
</Callout>

## Logging

The same block carries a `logger`, so your plugin writes into the Operator's own
log stream rather than shouting into `stdout` on its own terms. Four levels —
`debug`, `info`, `warn`, `error` — each taking a fields object with an optional
message, or a message on its own:

```ts
tools: (ctx, plugin) => {
  plugin.logger.info({ workspaceId: ctx.workspaceId }, "Resolving tool set");
  return {
    /* … */
  };
},
```

Three things core does for you, and one thing to get right yourself:

- **Your plugin's name is already on every line.** Core binds the manifest
  `name` to the logger before handing it over, so an Operator can filter their
  log pipeline down to your plugin. Don't put the name in your own fields.
- **[`LOG_LEVEL`](/reference/backend-configuration#core) governs your lines like
  core's.** A `debug` line writes nothing on a deployment left at the default
  `info`, and appears the moment the Operator raises the level. Put the detail
  that only matters while diagnosing at `debug`; keep `warn` and `error` for
  what an Operator should act on.
- **The format matches core's.** Structured JSON in production, pretty-printed
  in development — you get both without configuring either.
- **Prefer the fields object to an interpolated string.** `{ workspaceId }`
  stays queryable in the Operator's pipeline; `` `for ${workspaceId}` `` does
  not.

<Callout type="warning">
  Reaching for `console.log` instead is the trap. Its output bypasses
  `LOG_LEVEL`, so it cannot be turned down on a busy deployment; it carries no
  plugin name, so nobody can tell it is yours; and it is unstructured, so it
  lands in the Operator's pipeline as an unparseable line between two JSON ones.
</Callout>

Both the block and its logger are required, so write `plugin.logger.` — no
chaining, no fallback.

Deploy-time scope is all a logger line carries. Workspace, Agent and run ids are
not bound for you; include the ones you have from your own context, as the
example above does with `workspaceId`.
