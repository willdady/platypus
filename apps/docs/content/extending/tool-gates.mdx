# Tool gates

A **Tool gate** sees every tool call the backend runs, before it runs, and
answers with a **Verdict**: `allow`, `ask` or `deny`, with an optional reason. A
gate only gates. It cannot change a call's arguments or its result.

An enabled gate applies to the whole deployment: every Organization, every
Chat, Trigger run, A2A call and Sub-Agent run, and every tool, whether it came
from a core Tool set, a third-party Plugin or an MCP server. A gate can be a
plain rule list or a call to a classifier; Platypus sees only the Verdict. One
ships in the box — the decision-model gate, enabled as described in
[Configuration → Tool gates](/self-hosting/configuration#tool-gates). This page
is for writing your own.

## What a gate is given

Your contribution's `evaluate` is called once per tool call with the call, your
Plugin's deploy-time block, and a signal. Read the exact shapes off
[`@platypuschat/plugin-sdk`](https://www.npmjs.com/package/@platypuschat/plugin-sdk).

| Field                             | What it holds                                                                                                           |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `toolName`                        | The name the model called, namespacing included — an MCP tool reads `<slug>__<tool>`.                                   |
| `toolDescription`                 | The description the model was given, when the tool has one.                                                             |
| `args`                            | The arguments the model sent.                                                                                           |
| `toolSetId`                       | The Tool set or MCP server the tool came from. Absent for the tools Platypus adds itself, such as Sub-Agent delegation. |
| `orgId`, `workspaceId`, `agentId` | Where the call is made. `agentId` is absent in a Chat with no Agent.                                                    |
| `attended`                        | `true` only in a top-level Chat turn someone is watching. Trigger runs, A2A calls and Sub-Agent runs are unattended.    |
| `readOnlyHint`                    | `read-only` or `writes` when the tool declared which, `undeclared` when it didn't. Only MCP servers declare it today.   |

A gate sees nothing else: no credentials, and no message history. Treat
`undeclared` as a tool that writes.

```ts
export const plugin: PlatypusPlugin = {
  name: "acme-gates",
  version: "0.1.0",
  apiVersion: PLUGIN_API_VERSION,
  contributes: {
    toolGates: [
      {
        id: "no-drop", // registers as `acme-gates.no-drop`
        name: "No DROP",
        timeoutMs: 2_000,
        evaluate: (call, plugin, { signal }) =>
          JSON.stringify(call.args).includes("DROP TABLE")
            ? { verdict: "deny", reason: "Drops a table." }
            : { verdict: "allow" },
      },
    ],
  },
};
```

## What each Verdict does

- **`allow`** — the call runs. Nothing is recorded about the gate.
- **`deny`** — the call does not run, and no one can override that. The model
  receives a tool error that names your gate and carries your `reason`, and the
  run continues, so the Agent can try something else or explain itself. The
  Chat's tool card shows **Denied** with the reason, and the Run timeline shows
  the call as cancelled with the reason.
- **`ask`** — a person may decide. Platypus cannot put the question to anyone
  yet, so for now `ask` stops the call exactly as `deny` does, in Chats too.
  Return it where a person's approval is what you mean; your gate will not need
  to change when asking arrives. It will only ever reach a person in a
  top-level Chat turn — wherever `attended` is `false` there is no one to ask, and
  `ask` stays a `deny`.

Write `reason` for the model, the User and the Operator at once: it is shown to
all three.

With several gates enabled they all run, at the same time, and the most
restrictive Verdict wins: `deny` over `ask` over `allow`.

## Your gate fails closed

<Callout type="warning">
  A gate that throws, returns something that is not a Verdict, or doesn't answer
  within its `timeoutMs` counts as `ask` — so the call does not run. A gate that
  never answers stops every tool call on the deployment. That is deliberate: a
  gate that times out under load must not let through the calls it exists to
  stop. Budget your timeout for your slowest honest answer, and honour the
  `signal`.
</Callout>

`timeoutMs` defaults to **10 000** ms and is capped at **30 000**. A
contribution declaring a `timeoutMs` that is not a positive, finite number of at
most 30 000 **fails startup** with an error naming your Plugin, rather than
being clamped. The `signal` fires when that time is up or the run is stopped.

Every enabled gate adds its wait to every tool call. Platypus does not remember
your answers: the same call made twice is judged twice. An unattended run that
retries a call you denied gets the same refusal each time, and is halted the way
any run repeating the same call for the same result is.

## What a gate cannot see

Tools the Provider runs itself — a Provider's built-in web search, for one —
run on the Provider's side and never reach Platypus, so no gate sees them. If an
Operator needs those stopped too, the place to do it is the Provider's settings,
not a gate.
