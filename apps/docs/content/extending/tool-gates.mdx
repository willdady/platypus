# Tool gates

A **Tool gate** sees every tool call the backend runs, before it runs, and
answers with a **Verdict**: `allow`, `ask` or `deny`, with an optional reason. A
gate may also see a tool's result before the model does and withhold it. A gate
only gates: it cannot change a call's arguments, and it cannot rewrite, redact
or annotate a result.

An enabled gate applies to the whole deployment: every Organization, every
Chat, Trigger run, A2A call and Sub-Agent run, and every tool, whether it came
from a core Tool set, a third-party Plugin or an MCP server. A gate can be a
plain rule list or a call to a classifier; Platypus sees only the Verdict. One
ships in the box — the decision-model gate, enabled as described in
[Configuration → Tool gates](/self-hosting/configuration#tool-gates). This page
is for writing your own.

## What a gate is given

Your contribution's `evaluate` is called once per tool call with the call, your
Plugin's deploy-time block, and a signal. Read the exact shapes off
[`@platypuschat/plugin-sdk`](https://www.npmjs.com/package/@platypuschat/plugin-sdk).

| Field                             | What it holds                                                                                                           |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `toolName`                        | The name the model called, namespacing included — an MCP tool reads `<slug>__<tool>`.                                   |
| `toolDescription`                 | The description the model was given, when the tool has one.                                                             |
| `args`                            | The arguments the model sent.                                                                                           |
| `toolSetId`                       | The Tool set or MCP server the tool came from. Absent for the tools Platypus adds itself, such as Sub-Agent delegation. |
| `orgId`, `workspaceId`, `agentId` | Where the call is made. `agentId` is absent in a Chat with no Agent.                                                    |
| `attended`                        | `true` only in a top-level Chat turn someone is watching. Trigger runs, A2A calls and Sub-Agent runs are unattended.    |
| `readOnlyHint`                    | `read-only` or `writes` when the tool declared which, `undeclared` when it didn't. Only MCP servers declare it today.   |

A gate sees nothing else: no credentials, and no message history. Treat
`undeclared` as a tool that writes.

```ts
export const plugin: PlatypusPlugin = {
  name: "acme-gates",
  version: "0.1.0",
  apiVersion: PLUGIN_API_VERSION,
  contributes: {
    toolGates: [
      {
        id: "no-drop", // registers as `acme-gates.no-drop`
        name: "No DROP",
        timeoutMs: 2_000,
        evaluate: (call, plugin, { signal }) =>
          JSON.stringify(call.args).includes("DROP TABLE")
            ? { verdict: "deny", reason: "Drops a table." }
            : { verdict: "allow" },
      },
    ],
  },
};
```

## What each Verdict does

- **`allow`** — the call runs. Nothing is recorded about the gate.
- **`deny`** — the call does not run, and no one can override that. The model
  receives a tool error that names your gate and carries your `reason`, and the
  run continues, so the Agent can try something else or explain itself. The
  Chat's tool card shows **Denied** with the reason, and the Run timeline shows
  the call as cancelled with the reason.
- **`ask`** — a person may decide. In a top-level Chat turn the reply stops
  once the model's current step is done, and the Workspace Owner sees the call
  with your `reason` and **Approve** / **Deny** buttons. An approved call runs
  without any gate being asked about it again; a denied one reaches the model
  as a denial by the User. Wherever `attended` is `false` there is no one to
  ask, and `ask` stops the call exactly as `deny` does.

Write `reason` for the model, the User and the Operator at once: it is shown to
all three.

With several gates enabled they all run, at the same time, and the most
restrictive Verdict wins: `deny` over `ask` over `allow`.

## Withholding a result

A gate may also declare `evaluateResult`, an optional second stage that sees a
tool's result before the model does. It is handed the same fields as `evaluate`
plus `result` — the value the tool returned, after Platypus has normalised it.
Declare it only when you want that stage; a gate that leaves it out behaves
exactly as it always did.

```ts
export const plugin: PlatypusPlugin = {
  name: "acme-gates",
  version: "0.1.0",
  apiVersion: PLUGIN_API_VERSION,
  contributes: {
    toolGates: [
      {
        id: "screener",
        name: "Injection screener",
        timeoutMs: 2_000,
        evaluate: () => ({ verdict: "allow" }),
        evaluateResult: (call, result, plugin, { signal }) =>
          String(result).includes("IGNORE PREVIOUS INSTRUCTIONS")
            ? {
                verdict: "deny",
                reason: "Looks like a prompt injection.",
              }
            : { verdict: "allow" },
      },
    ],
  },
};
```

A result Verdict is `allow` or `deny`, with an optional reason. There is no
`ask`, because a result the tool already produced has nothing for a person to
approve.

- **`allow`** — the result is passed to the model unchanged.
- **`deny`** — the result is withheld entirely. It is never stored, streamed to
  the Chat or recorded on the Run timeline. The model receives a tool error
  naming your gate and carrying your `reason`; the Chat's tool card shows its
  error state, and the Run timeline closes the call as failed. The tool has
  already run, so its side effects stand — write `reason` so the model
  understands that the call happened and only its result was withheld.

The result stage fails closed in the same way as the call stage: a gate that
throws, returns something that is not a result Verdict, or outruns the same
`timeoutMs` withholds the result. With several result-evaluating gates they all
run in parallel, any `deny` wins, and the first denying gate's reason is the one
used.

Your gate receives the whole normalised result. If yours sends it somewhere
else — a decision model, for example — bound it first; Platypus does not shorten
it for you.

## Your gate fails closed

<Callout type="warning">
  A gate that throws, returns something that is not a Verdict, or doesn't answer
  within its `timeoutMs` counts as `ask` — so the call does not run unless a
  person in a Chat approves it. A gate that never answers stops every unattended
  tool call on the deployment, and asks about every attended one. That is
  deliberate: a gate that times out under load must not let through the calls it
  exists to stop. Budget your timeout for your slowest honest answer, and honour
  the `signal`. On the result stage the same failure withholds the result, and a
  gate that never answers leaves every tool result withheld across the
  deployment.
</Callout>

`timeoutMs` defaults to **10 000** ms and is capped at **30 000**. A
contribution declaring a `timeoutMs` that is not a positive, finite number of at
most 30 000 **fails startup** with an error naming your Plugin, rather than
being clamped. The `signal` fires when that time is up or the run is stopped.

Every enabled gate adds its wait to every tool call. Platypus does not remember
your answers: the same call made twice is judged twice. An unattended run that
retries a call you denied gets the same refusal each time, and is halted the way
any run repeating the same call for the same result is.

## What a gate cannot see

Tools the Provider runs itself — a Provider's built-in web search, for one —
run on the Provider's side and never reach Platypus, so no gate sees their calls
or results and their results cannot be withheld. If an Operator needs those
stopped too, the place to do it is the Provider's settings, not a gate.
