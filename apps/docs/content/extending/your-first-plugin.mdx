# Your first Plugin

The repository ships a runnable third-party Plugin:
[`packages/example-plugin`](https://github.com/willdady/platypus/tree/main/packages/example-plugin),
package name `@platypus-examples/tool-set`, not published to npm. It contributes
one Tool set with one
tool, and it exists so you can prove the whole path — install, list, load,
grant, call, log — before you write anything of your own.

Do this first. Then copy the package and replace its contents.

## What the example contains

```ts
export const plugin: PlatypusPlugin = {
  name: "example", // the namespace, not the package specifier
  version: "0.1.0",
  apiVersion: PLUGIN_API_VERSION,
  contributes: {
    toolSets: [
      {
        id: "greeting", // bare — core prefixes it to `example.greeting`
        name: "Greeting",
        category: "Examples",
        tools: (ctx, plugin) => {
          // Core's logger, already tagged with `example`
          plugin.logger.debug({ workspaceId: ctx.workspaceId }, "Resolving");
          return {
            // bare — core namespaces it to `example__greet`
            greet: tool({
              description: "Return a friendly greeting for the given name.",
              inputSchema: z.object({ name: z.string() }),
              execute: ({ name }) => `Hello, ${name}!`,
            }),
          };
        },
      },
    ],
  },
};
```

Two names, doing two different jobs. `@platypus-examples/tool-set` is the **npm
package specifier** — what you install and what the Operator lists. `example` is
the manifest **`name`** — the config namespace, and the prefix core puts on every
contribution id and every tool name, so the `greet` tool above reaches the model
as `example__greet`. Get them the wrong way round and boot fails naming your
Plugin.

## Load it

<Steps>

### Install the package into the deployment

How depends on how you run Platypus — see [Installing Plugins](/extending/installing-plugins).

In a checkout of the Platypus repository this is already done — the example is a
workspace package and the backend already depends on it. Skip to the next step.

The published images don't contain the example, and it isn't on npm to install.
Build it into a custom backend image instead: the repository's
[`examples/custom-image`](https://github.com/willdady/platypus/tree/main/examples/custom-image)
does exactly that, and its README lists the Plugin and starts the stack in the
same commands. Follow it, then go to Checkpoint 1.

### List it

Add the **package specifier** to `PLATYPUS_PLUGINS` in the backend's `.env`. The
variable is one comma-separated list, and it replaces rather than appends, so
keep whatever was already there:

```bash
PLATYPUS_PLUGINS=@platypus/web-fetch,@platypus-examples/tool-set
```

### Restart the backend

Stop `pnpm dev` and start it again.

Plugin loading happens once, before the HTTP server starts. There is no in-app
install button — this is a deploy-time trust boundary.

</Steps>

## Checkpoint 1: it loaded

Sign in as an Org Admin and open **Organization settings → Plugins**. You should
see a row reading **example**, version `0.1.0`, badged **Third-party**, with
`example.greeting` listed under **Tool sets**.

<Callout type="warning">
  The row is labelled with the manifest **`name`** — `example` — not the package
  specifier you installed. Scanning the list for
  `@platypus-examples/tool-set` and concluding the Plugin didn't load is the
  usual first confusion.
</Callout>

If the backend didn't come back up at all, that is the intended behaviour for a
Plugin that couldn't be resolved: boot is fail-loud and all-or-nothing. Read the
backend's log — the `pnpm dev` terminal in a checkout, `docker compose logs
backend` on a custom image. The startup error names your Plugin and the reason.

## Checkpoint 2: an Agent can use it

Open any Agent in a Workspace and find the **Tools** card. Under an **Examples**
heading there is a **Greeting** switch. Flip it, click **Update**, then start a
Chat on that Agent and ask it to greet someone by name.

The reply comes back through an **Example greet** tool call you can expand in the
transcript. That is the loop closed: your code ran inside a Chat turn.

## Checkpoint 3: it can log

The factory writes one line every time it resolves, at `debug`. The default
`LOG_LEVEL` is `info`, so you saw nothing during Checkpoint 2. Raise it,
restart the backend, and send another message:

```bash
LOG_LEVEL=debug
```

- **In a checkout**, set it in the backend's `.env` and restart `pnpm dev`. The
  `pnpm dev` terminal now prints a `DEBUG` line reading `Resolving`, with
  `plugin: "example"` among the fields under it.
- **On a custom image**, set it in `.env` and run the same `docker compose up -d`
  command you started the stack with. `docker compose logs backend` now carries
  a JSON `Resolving` line with `"plugin":"example"`.

Either way it is core's own stream, core's format, and the name bound for you
without your code passing it. Put `LOG_LEVEL` back when you're done; `debug` is
loud on a busy deployment.

## When it doesn't work

| What you see                                                          | What it means                                                                            | Fix                                                                                                                    |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Backend exits at boot, log names your Plugin and "failed to resolve"   | The package isn't installed where the backend can `import()` it                          | Install it into the deployment, not only the repository, and check the specifier for typos                              |
| Backend exits, log complains about the manifest `name`                 | A third-party `name` must be a url-safe slug — lowercase letters, digits, hyphens         | Use `widgets`, not `@acme/platypus-widgets`. The package specifier stays scoped; the manifest name doesn't              |
| Backend exits, log says your manifest `name` is over its cap           | A third-party `name` is capped — it is the namespace on every tool name this Plugin adds  | The error states the cap and your length. Shorten it in the manifest; the package specifier can stay as long as you like |
| Backend exits, log names a tool over its cap                           | A tool name in a statically-declared tool map is capped for the same reason               | Rename the tool. See [Tool names](/extending/tool-sets#two-length-caps)                                                 |
| Backend starts, but a tool from your factory never reaches the model; the log warns "Tool set's tool cannot enter a turn: its name is N characters, over the 32-character cap" | A factory's tool names are only known per turn, so an over-cap one is dropped from each turn rather than failing boot | Rename the tool. See [Tool names](/extending/tool-sets#two-length-caps)                                                 |
| Backend exits, log says your Plugin "needs API v…, but core supports up to v…" | The Plugin was built against a newer Plugin API than this core supports          | Upgrade core. If the log instead says the Plugin targets an API "below the oldest core supports", rebuild it against a current SDK. See [Which core versions your Plugin runs on](/extending/plugin-api-and-config#which-core-versions-your-plugin-runs-on) |
| Backend exits, log says your manifest `name` is declared by two Plugins | Another loaded Plugin ships the same manifest `name` — often a fork installed alongside the original | Rename one of them in its manifest. The two would otherwise share one deploy-time config and credential block |
| Backend starts, but **Plugins** doesn't list it and nothing is logged   | It isn't in `PLATYPUS_PLUGINS` — most often a `compose.sandbox.yaml` overlay replaced the list | The overlay sets `PLATYPUS_PLUGINS` under `services.backend.environment`, which wins over `.env`. Put your full list in the overlay |

<Callout type="info">
  A Tool set that appears in **Plugins** but not on the Agent form is a
  different problem: the **Tools** card only renders when the Workspace has at
  least one Tool set to grant, and it lists the Tool set **name** under its
  **category**. Look under `Examples`, not under `example.greeting`.
</Callout>
