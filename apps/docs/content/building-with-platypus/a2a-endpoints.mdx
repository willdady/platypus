# A2A endpoints

An **A2A endpoint** makes one Agent in your Workspace reachable from outside
Platypus over [A2A](https://a2a-protocol.org), the open protocol one agent uses
to talk to another. A client such as a messaging gateway or another agent
discovers the Agent through the endpoint's **Agent Card**, and authenticates
with a token you issue to it.

You'll find them under **Workspace settings → A2A endpoints**. Only the
Workspace Owner creates, edits and deletes endpoints and tokens. An Org Admin
opening your Workspace sees them read-only, and no Agent Tool can read or
change them. An Org Admin can
[revoke](/administering#see-and-revoke-endpoints) any endpoint or token in the
Organization, and you get a notification when they do.

## Before you start

Your Organization decides which Workspaces may have A2A endpoints, and it is
off until an Org Admin turns it on (see
[A2A endpoints](/administering#a2a-endpoints)). While it is off for your
Workspace, the screen says so and every endpoint answers **Not Found**. You can
still create endpoints and tokens in the meantime.

## Runs act as you

<Callout type="warning">
  Anyone holding a token can talk to the Agent, and every run acts as you, with
  every Tool the Agent has. A token is only as safe as the Agent's Tools are
  narrow. To expose less, make a narrower Agent and give the endpoint that one.
</Callout>

## Create an endpoint

<Steps>

### Open the form

Go to **Workspace settings → A2A endpoints** and click **Add endpoint**.

### Fill it in

- **Agent** — the Agent callers talk to. Any Agent in the Workspace, including
  an attached Shared Agent. You can't change it later.
- **Name** — what callers see as the agent's name, up to 100 characters.
  Picking the Agent fills in its name, unless you've already typed one. Left
  blank, the Agent's name is used.
- **Description** — what callers see in place of the Agent's description, up to
  1000 characters. Picking the Agent fills in its description, unless you've
  already typed one. Left blank, the Agent's description is used. Rewrite it
  for outsiders: the Agent's description is written for you and for other
  Agents.
- **Enabled** — when off, the endpoint answers every call with **Not Found**.
- **Include Memories** and **Extract Memories** — whether the endpoint's runs
  read your Memories and its Chats write to them. Both are off by default; see
  [Memories](#memories).

Click **Save**. The new endpoint's page opens at its **Agent card URL** and
**Tokens**.

### Add a token for each client

Under **Tokens**, name the token after the client it's for, up to 100
characters, pick how long it lasts — 30, 90,
180 or 365 days, 90 by default — and click **Add token**. Copy the token from
the dialog. It's shown once and Platypus keeps only a hash of it, so if you lose
it, regenerate it.

Give each client its own token. Deleting one stops only that client.

</Steps>

An Agent can have several endpoints. Give clients that should see a different
name or description their own endpoint, or retire one client's URL without
touching the others.

## Tokens

Each token on the endpoint's page shows its standing — **Active**, **Expiring
soon** (within 7 days) or **Expired** — when it expires, and when it was
**Last used** and **Last rejected**. **Last rejected** moves when a call with
the expired token is refused. Both times update at most once a minute.

- **Every token expires** after the lifetime you picked. A call with an expired
  token, like one with a missing or wrong token, gets `401 Unauthorized`.
- **You get a notification** 30 days and 7 days before a token expires (a
  30-day token only gets the 7-day one), and the first time a client uses it
  after it expires.
- **Regenerate** issues a new value for the token, with the same name and
  lifetime, and stops the old value at once, along with any Task it started
  that is still running. The new value is shown once. Use it when a token is
  about to expire, is lost, or may have leaked, then update the client.

<Callout type="warning">
  Rotating a token usually means updating the client's configuration, so act on
  the 30-day reminder, not the 7-day one.
</Callout>

## The Agent Card

Each endpoint has its own **Agent card URL**, shown on its page. The address is
generated for the endpoint, so it reveals nothing about the Agent or the
Workspace. Anyone with the URL can fetch the card, without a token:

```bash
curl https://platypus.example.com/a2a/<endpoint-id>/.well-known/agent-card.json
```

The card carries the endpoint's **Name** and **Description**, says the client
authenticates with an HTTP bearer token, names the address the client sends
requests to, and says the endpoint offers streaming and push notifications. It
never carries the Agent's own description, Tool sets or Skills. A client may
cache the card for up to five minutes, so a change to the Name or Description
can take that long to reach it.

An endpoint that is disabled or deleted, in a Workspace the Organization doesn't
allow, or whose Workspace Owner has left the Organization or been banned answers
**Not Found**, exactly like one that never existed. A Super Admin who owns the
Workspace keeps its endpoints answering without being a member of the
Organization, but not while banned. A ban with an expiry stops counting once it
runs out, and the endpoints answer again.

A client that authenticates can also fetch the **extended Agent Card**
(`GetExtendedAgentCard`). It adds one skill, built from the same Name and
Description.

## Conversations

A client talks to the Agent by sending JSON-RPC requests to the endpoint's
address, with its token in an `Authorization: Bearer` header. A missing or
wrong token gets **401 Unauthorized**. The endpoint speaks A2A 1.0: a request
whose `A2A-Version` header asks for another version is refused with a "version
not supported" error, and a request without the header is answered as 1.0.

Each conversation is an ordinary Chat in your Chat list, labelled with the
token's name, so you can read what the client asked and what the Agent did. You
can continue the Chat yourself, and the client's next message follows your
turns.

**Each token sees only the conversations it started.** A `contextId` naming
any other Chat — one you started yourself, another client's, or one started on
another endpoint for the same Agent — is answered with a "task not found"
error, exactly as an id that doesn't exist, and nothing is written to it. The
same goes for every Task method: a client can read, follow, cancel and register
push URLs on its own Tasks only. A Chat id appears in your browser's address
bar and in screenshots, so it is not a secret; this is what keeps a client that
learns one out of your Chats.

- **`SendMessage` without a `contextId`** starts a new Chat with the endpoint's
  Agent. The answer's `contextId` is that Chat; send it with later messages to
  continue the conversation.
- **Each message is a Task.** `SendMessage` answers with the Task once the run
  has started. A client that sets `returnImmediately` gets it at once;
  otherwise the request waits up to **30 seconds** for the run to end, then
  answers with the Task as it stands. Runs can take far longer than that, so a
  client follows the Task with **`GetTask`** until it is `completed`, `failed`
  or `canceled`, [streams it](#streaming), or registers for a
  [push notification](#push-notifications) when it ends. The Agent's final
  reply is the Task's artifact. A Task that has ended keeps its state, even
  after you or the client continue the Chat. It also keeps the reply it ended
  with: regenerating that reply in the Chat doesn't change the artifact, and
  deleting it leaves the Task with its state and no artifact.
- **A retry is safe.** The client's `messageId` becomes the message's id in the
  Chat, so sending the same `messageId` again answers with the Task it already
  started, never a second run. That holds even when the retry arrives while
  the first copy is still starting, as it does when a client retries on a
  timeout.
- **One run at a time.** A message sent while the Chat still has a run going,
  including one you started in the Chat yourself, is refused with an
  "unsupported operation" error. When the client started that run, the error's
  data carries its Task's id as `taskId`, and the client can follow that Task.
  A run you started has no Task, so the error carries none. Either way, the
  client sends again once the run ends.
- **A Task takes no further messages.** A message that names a `taskId` is
  refused, whether the Task is still running or has ended. To continue the
  conversation, the client sends the Task's `contextId` and no `taskId`.
- **A busy server says so.** Your Operator caps how many A2A runs can be going
  at once across the server. A message that would start one past the cap gets
  `429 Too Many Requests` with a `Retry-After` header, and nothing is written:
  the client waits and sends it again.
- **Calls have a size limit.** Your Operator sets the largest call a client
  may send, 1 MB unless they change it. A larger one gets
  `413 Payload Too Large`, and nothing is written.
- **Text and data parts.** Data parts reach the Agent as labelled JSON, with
  the same note Inbound Trigger inputs carry: the values come from the caller
  and are data, not instructions. A message with a file part is refused with an
  error rather than sent without it.

The Agent is told the conversation arrives over A2A from the client the token
is named after, and that the caller may not be you.

A client can stop a Task it no longer needs with
[`CancelTask`](#cancelling-a-task).

## Listing Tasks

`ListTasks` answers with the Tasks **the calling token** started, newest first.
A client never sees another client's Tasks, even on the same endpoint, and
Tasks started with a token you've deleted are listed to no one. Turns you add
to a client's Chat yourself aren't Tasks, so they aren't listed.

- **Pages of up to 100.** A page holds **50** Tasks unless the client asks for
  a `pageSize` between 1 and 100; anything outside that is refused. Pass the
  answer's `nextPageToken` back as `pageToken` for the next page. It is empty on
  the last page, and `totalSize` counts every match.
- **Newest first** means the Task's status timestamp: when it ended, or when it
  started if it is still running.
- **Filters.** `contextId` lists one Chat's Tasks, `status` the Tasks in one
  state, and `statusTimestampAfter` the Tasks whose status changed after that
  time.
- **Replies are left out** unless the client sets `includeArtifacts`. With it,
  each Task carries the same artifact `GetTask` answers with.

## Streaming

A client with someone waiting on the reply can watch it arrive over
server-sent events instead of polling.

- **`SendStreamingMessage`** takes the same message as `SendMessage` and
  answers with a stream: first the Task, then the Agent's reply as it is
  written, as artifact updates that each add to the last, then the finished
  reply as one artifact and the Task's final status. The stream ends with the
  Task.
- **`SubscribeToTask`** rejoins a Task that is still running, for example
  after the client's connection dropped. It sends the Task as it stands, any
  change of status, and once the Task ends its finished reply and final
  status. It doesn't send the reply word by word: only the connection that
  started the run does. A Task that has already ended is refused with an
  "unsupported operation" error; read it with `GetTask` instead.
- **A dropped connection doesn't stop the run.** It goes on, and the client
  can rejoin with `SubscribeToTask` or read the result with `GetTask`.
- **A retried `SendStreamingMessage`**, with a `messageId` already sent,
  follows the Task it already started, like `SubscribeToTask`, rather than
  starting a second run.
- A message the endpoint refuses (a file part, a Chat with a run still going)
  is answered with a plain JSON-RPC error, not a stream.
- **Following has a limit.** Your Operator caps how many streams can follow
  Tasks at once, 100 unless they change it, and each token can hold at most 10
  of them. The stream that started a run doesn't count, but `SubscribeToTask`,
  a retried `SendStreamingMessage`, and a retried `SendMessage` that waits for
  its Task do. One past the cap gets `429 Too Many Requests` with a
  `Retry-After` header. The client closes a stream it no longer needs, or
  waits and tries again. A stream frees its place when the Task ends or the
  client disconnects.

A stream sends a comment line every 15 seconds while the Agent is quiet, so a
proxy with an idle timeout doesn't cut it off.

## Cancelling a Task

**`CancelTask`** stops a running Task's run and answers with the Task,
`canceled`. The run stops whichever server it is running on, so the Agent stops
working and stops spending.

- **The Task reads `canceled` straight away**, in `GetTask` and in a
  [push notification](#push-notifications).
- **A stream following the Task ends** with the `canceled` status.
- **Anything the Agent wrote before the cancel stays in the Chat**, but the Task
  has no artifact.
- **A Task that has already ended** keeps its state, and the cancel is refused
  with a "task not cancelable" error that stops nothing. The client reads the
  Task's final state with `GetTask`.
- **The Chat takes the next message once the run has stopped.** A message sent
  in the moment before then is refused like any other sent while a run is
  going.

## Push notifications

A client that doesn't want to hold a connection open or poll for hours can give
Platypus a URL to call when a Task ends. Register it with the message, in
`SendMessage`'s `taskPushNotificationConfig`, or afterwards on the Task with
`CreateTaskPushNotificationConfig`. `GetTaskPushNotificationConfig`,
`ListTaskPushNotificationConfigs` and `DeleteTaskPushNotificationConfig` read
and remove what a Task has. A client reaches only the configs on its own
Tasks, so another client on the same endpoint never sees the credentials it
registered.

- **Only the end is pushed.** When the Task becomes `completed`, `failed` or
  `canceled`, Platypus POSTs it to each URL registered on it, as
  `{ "task": { ... } }` with content type `application/a2a+json`. The Task is
  the one `GetTask` would answer, with the Agent's final reply as its artifact.
  Nothing is sent while it runs.
- **A Task that has already ended** when a URL is registered on it is pushed
  straight away, so a run that finishes before the client registers is not
  missed.
- **A run lost to a server crash** ends `failed` within about a minute, once
  Platypus notices it has gone quiet, and that is pushed like any other end. A
  run stopped by a server shutting down cleanly ends `canceled`. An end that
  a crash kept from being pushed is pushed within about a minute.
- **Your credentials come back to you.** A request carries the
  `authentication` the client registered as an `Authorization` header (for
  example `Authorization: Bearer <credentials>`), and its `token`, if any, as
  `X-A2A-Notification-Token`. Check them on the receiving side to know the
  request came from this endpoint. An `authentication` without both a scheme
  and credentials is refused when it is registered.
- **Delivery works like a [Webhook](/building-with-platypus/webhooks#delivery-and-retries)'s**,
  with the same timeout and retries.
- **Push URLs must be public.** Platypus never pushes to a loopback,
  cloud-metadata or private-network address, unless your server administrator
  allows private networks for clients on their own network. Any `http` or
  `https` URL is accepted when it is registered; one that leads somewhere not
  allowed is skipped when the Task ends, so check your URL is reachable from
  the internet.
- **Each URL is pushed once.** Once a Task has ended, a config can't be pointed
  at a different URL: registering its `id` with a new `url` is refused.
- **Up to 5 URLs per Task.** Registering a URL that is already on the Task,
  without naming its `id`, replaces it rather than adding a second. So does
  registering an `id` the Task already has, even when two registrations of it
  arrive at once.
- **At most 5 pushes per Task**, counting pushes to URLs you have since
  deleted.
- **Credentials aren't read back.** `GetTaskPushNotificationConfig` and
  `ListTaskPushNotificationConfigs` return the `authentication` scheme, but
  never its credentials or the `token`. Keep your own copy.

<Callout type="warning">
  The push carries the Agent's reply, so the receiving URL sees the
  conversation. Use an `https` URL you control, and check the credentials before
  trusting the body. A retry after a timeout can deliver the same Task twice, so
  handle a repeat of a Task id you've already seen. A push a server restart
  interrupts mid-delivery isn't sent again, so a client that must not miss an
  end should still poll `GetTask` now and then.
</Callout>

## Memories

Two switches on the endpoint decide how its conversations touch your Memories.
Both are **off** by default, because whoever holds a token may not be you.

- **Include Memories** adds your recent Memory summaries to the Agent's system
  prompt on the endpoint's runs, and lets an Agent with the **Memory** Tool set
  use its memory tools there. Off, the runs carry no summaries and the Agent
  gets no memory tools, so a client can't ask it to look your Memories up. It
  covers your own turns in the endpoint's Chats too: a reply you get there sits
  in the history the client reads next.
- **Extract Memories** lets the endpoint's Chats feed your Memories. Off,
  Platypus never reads them for Memories — including any turns you add to them
  yourself in the Chat.

<Callout type="warning">
  A messaging gateway can put a stranger in front of the Agent: anyone in a
  group chat the client sits in. With **Include Memories** on, the Agent can
  repeat your personal context to them; with **Extract Memories** on, what they
  say lands in your Memories. Turn either on only for an endpoint whose tokens
  are held by you alone.
</Callout>

**Include Memories** applies from the endpoint's next run, in its existing
Chats as well as new ones. Turning **Extract Memories** on applies to the
endpoint's existing Chats too, not only new ones. A Chat started on an endpoint
you later delete stays out of your Memories, and its turns read as **Include
Memories** off.

## Deleting

- **Delete** on the endpoint's page removes it. Its URL and every one of its
  tokens stop working at once.
- Deleting or regenerating a token, or deleting or disabling an endpoint, also
  stops the work its clients already started. Their running Tasks are
  canceled, an open `SendStreamingMessage` or `SubscribeToTask` stream ends
  with an error, and no push notification is sent for those Tasks, however
  they end. Other tokens' Tasks on the same endpoint keep running.
- Deleting the Agent deletes its endpoints and their tokens.
- Detaching a Shared Agent from the Workspace deletes the Workspace's endpoints
  for it, and their tokens.
- Running Tasks on an endpoint deleted with its Agent, or whose Workspace
  Owner leaves the Organization or is banned, are canceled within a few
  seconds rather than at once.
- A Chat stays when its endpoint or token is deleted, still labelled with the
  token's name. No client can reach it or its Tasks over A2A again, not even
  with another token on the same endpoint. Deleting a Chat ends its Tasks: `GetTask` answers that they
  don't exist.
