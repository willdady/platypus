# Webhooks

A **Webhook** delivers Workspace events to a URL you control. Whenever something
happens in the Workspace — a card is created, a notification is dismissed —
Platypus sends an HTTP `POST` with a JSON body describing the event, so an
external system can react to it.

Where a [Trigger](/building-with-platypus/triggers) runs an Agent _inside_
Platypus in response to an event, a Webhook sends that same event _out_ to your
own service. Both subscribe to the same `card.*` and `notification.*` events.
Only a Webhook can subscribe to the `trigger_run.*` events, which report a
Trigger run ending.

You'll find Webhooks under **Workspace settings → Webhooks**.

## Subscribable events

A Webhook subscribes to one or more events. The available events are:

| Event                    | Fires when                                                    |
| ------------------------ | ------------------------------------------------------------- |
| `card.created`           | A card is added to a [Board](/building-with-platypus/boards). |
| `card.updated`           | A card's fields, column, or position change.                  |
| `card.moved`             | A card's column changes — fires alongside `card.updated`.     |
| `card.deleted`           | A card is deleted; not sent when its column or board is.      |
| `notification.created`   | An Agent posts a notification.                                |
| `notification.updated`   | A notification is edited.                                     |
| `notification.read`      | A notification is marked read.                                |
| `notification.dismissed` | A notification is dismissed.                                  |
| `trigger_run.succeeded`  | A Trigger run ends `success`.                                 |
| `trigger_run.failed`     | A Trigger run ends `failed`, including a run that timed out.  |
| `trigger_run.cancelled`  | A Trigger run ends `cancelled` — someone stopped it.          |
| `trigger_run.suppressed` | The run-rate breaker drops a firing, so no Agent ran.         |

The form groups them under **Notifications**, **Cards** and **Trigger runs**.
Every event starts selected on a new Webhook; turn off the ones you don't want.
A Webhook needs at least one, so the last switch won't turn off.

## Create a Webhook

<Steps>

### Open the Webhook form

Go to **Workspace settings → Webhooks** and click **Add webhook**.

### Configure the endpoint

- **Name** — a label for the Webhook.
- **URL** — where the `POST` is sent. **Must be HTTPS**, and must pass the
  deployment's [egress guard](/self-hosting/configuration#the-egress-guard):
  loopback and cloud-metadata addresses are refused, and so are private
  networks if your Operator has turned them off. A refused URL fails on save, and
  so does a hostname that doesn't resolve yet.
- **Enabled** — leave on to start delivering immediately.
- **Events** — which events to subscribe to (all start selected).
- **Custom Headers** — optional headers sent with every delivery (e.g. an
  `Authorization` header your endpoint expects). Click **Add header** for each
  one.

### Save, then reopen to get the signing secret

On save, Platypus generates a **signing secret** for the Webhook. Every delivery
is signed with it so you can verify the request really came from Platypus — see
[Verifying the signature](#verifying-the-signature).

The create form does **not** show it. Saving returns you to the Webhooks list;
open the Webhook again and the **Signing Secret** field appears, with buttons to
reveal, copy, and **Regenerate** it. The secret was generated at save time — a
create form that showed you nothing hasn't failed.

</Steps>

## The payload

Platypus sends a `POST` request with `Content-Type: application/json`. The body
is the same envelope for every event:

```json
{
  "event": "card.created",
  "timestamp": "2026-06-26T09:30:00.000Z",
  "orgId": "g7Qw3pLm9xRt2nK5vB8dY",
  "workspaceId": "k4Tn2pXqRf7Lm9sWvB3dY",
  "data": {
    "id": "V1StGXR8_Z5jdHi6B-myT",
    "boardId": "lbfQ0p7xKmR2nT4vZ8wYs",
    "columnId": "9zHcN3eW1qoP5rUaB7dKt",
    "title": "Review onboarding flow",
    "body": "Check the new sign-up steps.",
    "labelIds": [],
    "assignees": [],
    "dueDate": null,
    "priority": "none",
    "position": 1024,
    "createdByUserId": "x6Ym2Qp9LrT4nW8sVdB1k",
    "createdByAgentId": null,
    "lastEditedByUserId": null,
    "lastEditedByAgentId": null,
    "createdAt": "2026-06-26T09:30:00.000Z",
    "updatedAt": "2026-06-26T09:30:00.000Z"
  }
}
```

The envelope fields are always present:

| Field         | Description                                                                       |
| ------------- | --------------------------------------------------------------------------------- |
| `event`       | The event name, e.g. `card.created`.                                              |
| `timestamp`   | ISO 8601 time the event was dispatched. Matches the `X-Webhook-Timestamp` header. |
| `orgId`       | The Organization the event belongs to.                                            |
| `workspaceId` | The Workspace the event belongs to.                                               |
| `data`        | The event's payload. Its shape depends on the event (see below).                  |

### `data` by event

The shape of `data` varies by event. For example, `notification.created` carries
the full notification record:

```json
{
  "event": "notification.created",
  "timestamp": "2026-06-26T09:31:00.000Z",
  "orgId": "g7Qw3pLm9xRt2nK5vB8dY",
  "workspaceId": "k4Tn2pXqRf7Lm9sWvB3dY",
  "data": {
    "id": "Hs8dK2pQ9mRnL7wT4vYx1",
    "workspaceId": "k4Tn2pXqRf7Lm9sWvB3dY",
    "agentId": "Jf3kP9xR2mLqN7wT4vYsZ",
    "title": "Daily summary ready",
    "body": "Your daily summary has been generated.",
    "createdAt": "2026-06-26T09:31:00.000Z",
    "updatedAt": "2026-06-26T09:31:00.000Z"
  }
}
```

`notification.updated` carries the same record, as it stands after the edit:

```json
{
  "event": "notification.updated",
  "timestamp": "2026-06-26T09:33:00.000Z",
  "orgId": "g7Qw3pLm9xRt2nK5vB8dY",
  "workspaceId": "k4Tn2pXqRf7Lm9sWvB3dY",
  "data": {
    "id": "Hs8dK2pQ9mRnL7wT4vYx1",
    "workspaceId": "k4Tn2pXqRf7Lm9sWvB3dY",
    "agentId": "Jf3kP9xR2mLqN7wT4vYsZ",
    "title": "Daily summary ready",
    "body": "Your daily summary has been regenerated.",
    "createdAt": "2026-06-26T09:31:00.000Z",
    "updatedAt": "2026-06-26T09:33:00.000Z"
  }
}
```

`card.moved` carries the full card record plus `previousColumnId`, so a handler
can tell where the card came from without a separate lookup:

```json
{
  "event": "card.moved",
  "timestamp": "2026-06-26T09:31:30.000Z",
  "orgId": "g7Qw3pLm9xRt2nK5vB8dY",
  "workspaceId": "k4Tn2pXqRf7Lm9sWvB3dY",
  "data": {
    "id": "V1StGXR8_Z5jdHi6B-myT",
    "boardId": "lbfQ0p7xKmR2nT4vZ8wYs",
    "columnId": "9zHcN3eW1qoP5rUaB7dKt",
    "previousColumnId": "3mYtQ8vNc1RpZ7wLdB4sK",
    "title": "Review onboarding flow",
    "body": "Check the new sign-up steps.",
    "labelIds": [],
    "assignees": [],
    "dueDate": null,
    "priority": "none",
    "position": 1024,
    "createdByUserId": "x6Ym2Qp9LrT4nW8sVdB1k",
    "createdByAgentId": null,
    "lastEditedByUserId": "x6Ym2Qp9LrT4nW8sVdB1k",
    "lastEditedByAgentId": null,
    "createdAt": "2026-06-26T09:30:00.000Z",
    "updatedAt": "2026-06-26T09:31:30.000Z"
  }
}
```

Moving a card to a different column always fires both `card.moved` and
`card.updated`. Reordering a card within the same column fires only
`card.updated` — `card.moved` means the card changed columns.

`card.updated` also carries `changedFields` — the names of the attributes that
actually changed, e.g. `["body"]` for a body edit or `["columnId"]` for a
cross-column move. It's a value comparison, not a report of which fields the
update submitted: resending a field with the same value (an Agent that echoes
the whole card back) doesn't add it to `changedFields`, and re-ordering
`labelIds` or `assignees` without changing the set doesn't either. A pure
reorder within a column emits `card.updated` with `changedFields: []`.

```json
{
  "event": "card.updated",
  "timestamp": "2026-06-26T09:31:30.000Z",
  "orgId": "g7Qw3pLm9xRt2nK5vB8dY",
  "workspaceId": "k4Tn2pXqRf7Lm9sWvB3dY",
  "data": {
    "id": "V1StGXR8_Z5jdHi6B-myT",
    "boardId": "lbfQ0p7xKmR2nT4vZ8wYs",
    "columnId": "9zHcN3eW1qoP5rUaB7dKt",
    "title": "Review onboarding flow",
    "body": "Check the new sign-up steps and confirm the copy.",
    "labelIds": [],
    "assignees": [],
    "dueDate": null,
    "priority": "none",
    "position": 1024,
    "createdByUserId": "x6Ym2Qp9LrT4nW8sVdB1k",
    "createdByAgentId": null,
    "lastEditedByUserId": "x6Ym2Qp9LrT4nW8sVdB1k",
    "lastEditedByAgentId": null,
    "createdAt": "2026-06-26T09:30:00.000Z",
    "updatedAt": "2026-06-26T09:31:30.000Z",
    "changedFields": ["body"]
  }
}
```

Other events carry only the affected IDs. For example, `card.deleted`:

```json
{
  "event": "card.deleted",
  "timestamp": "2026-06-26T09:32:00.000Z",
  "orgId": "g7Qw3pLm9xRt2nK5vB8dY",
  "workspaceId": "k4Tn2pXqRf7Lm9sWvB3dY",
  "data": {
    "cardId": "V1StGXR8_Z5jdHi6B-myT",
    "boardId": "lbfQ0p7xKmR2nT4vZ8wYs",
    "columnId": "9zHcN3eW1qoP5rUaB7dKt"
  }
}
```

The two notification lifecycle events are the ones most likely to catch a handler
out, because their `data` is neither the full record nor a single fixed shape.

**`notification.dismissed`** carries the notification ID **and nothing else** —
there is no `userId`. The same shape is sent whether a person deleted the
notification or an Agent did through the `deleteNotification` tool, so there is
nothing to attribute it to:

```json
{
  "data": {
    "notificationId": "Hs8dK2pQ9mRnL7wT4vYx1"
  }
}
```

**`notification.read`** has **two** shapes. Marking one notification read sends
the singular form:

```json
{
  "data": {
    "notificationId": "Hs8dK2pQ9mRnL7wT4vYx1",
    "userId": "x6Ym2Qp9LrT4nW8sVdB1k"
  }
}
```

**Mark all as read** sends one bulk event instead of one event per notification —
`notificationIds` (plural, an array), plus `bulk: true`:

```json
{
  "data": {
    "notificationIds": ["Hs8dK2pQ9mRnL7wT4vYx1", "Jf3kP9xR2mLqN7wT4vYsZ"],
    "userId": "x6Ym2Qp9LrT4nW8sVdB1k",
    "bulk": true
  }
}
```

<Callout type="warning">
  Handle both `notification.read` shapes. A handler written against
  `data.notificationId` alone reads `undefined` on every bulk event and drops
  the whole batch silently. Branch on `data.bulk`, or normalise with
  `data.notificationIds ?? [data.notificationId]`. Nothing is emitted at all
  when **Mark all as read** finds nothing unread.
</Callout>

<Callout type="info">
  Treat `data` defensively — read the fields your integration needs rather than
  assuming a fixed set, since the underlying records can gain fields over time.
</Callout>

### Trigger run events

A `trigger_run.*` event is sent once when a run of any Trigger type — Cron,
Event or Inbound — reaches its final status. The event name says how it ended,
and `data.status` carries the same word the run history and the Inbound poll
use:

| `data.status` | Event                    |
| ------------- | ------------------------ |
| `success`     | `trigger_run.succeeded`  |
| `failed`      | `trigger_run.failed`     |
| `cancelled`   | `trigger_run.cancelled`  |
| `suppressed`  | `trigger_run.suppressed` |

```json
{
  "event": "trigger_run.failed",
  "timestamp": "2026-06-26T09:41:00.000Z",
  "orgId": "g7Qw3pLm9xRt2nK5vB8dY",
  "workspaceId": "k4Tn2pXqRf7Lm9sWvB3dY",
  "data": {
    "runId": "Qm7tR2xLp9wN4vB8dYsK1",
    "status": "failed",
    "startedAt": "2026-06-26T09:30:00.000Z",
    "completedAt": "2026-06-26T09:41:00.000Z",
    "errorMessage": "Run 'Qm7tR2xLp9wN4vB8dYsK1' exceeded per-step timeout of 600000ms",
    "triggerId": "Tz4nW8sVdB1kx6Ym2Qp9L",
    "triggerName": "Triage new cards",
    "triggerType": "event",
    "agentId": "Jf3kP9xR2mLqN7wT4vYsZ",
    "eventType": "card.created",
    "entityId": "V1StGXR8_Z5jdHi6B-myT"
  }
}
```

The other three carry the same fields. A `trigger_run.succeeded` from a Cron
Trigger:

```json
{
  "data": {
    "runId": "Wd2kP8xT4mLqR7nV9sYbZ",
    "status": "success",
    "startedAt": "2026-06-26T09:00:00.000Z",
    "completedAt": "2026-06-26T09:02:10.000Z",
    "errorMessage": null,
    "triggerId": "Nb6vC3xZ9qLm2wT8rYpK4",
    "triggerName": "Daily summary",
    "triggerType": "cron",
    "agentId": "Jf3kP9xR2mLqN7wT4vYsZ",
    "eventType": null,
    "entityId": null
  }
}
```

A `trigger_run.cancelled` from an Inbound Trigger someone stopped:

```json
{
  "data": {
    "runId": "Lr5tY1wQ8nK3mV7bX2cZd",
    "status": "cancelled",
    "startedAt": "2026-06-26T10:00:00.000Z",
    "completedAt": "2026-06-26T10:03:00.000Z",
    "errorMessage": null,
    "triggerId": "Hp9sD4fG7jK2lZ5xC8vBn",
    "triggerName": "Investigate CI failure",
    "triggerType": "inbound",
    "agentId": "Jf3kP9xR2mLqN7wT4vYsZ",
    "eventType": null,
    "entityId": "PLAT-42"
  }
}
```

A `trigger_run.suppressed` never ran, so it has no `completedAt`:

```json
{
  "data": {
    "runId": "Ux3hJ6kL9pQ2rS5tV8wYa",
    "status": "suppressed",
    "startedAt": "2026-06-26T11:00:00.000Z",
    "completedAt": null,
    "errorMessage": null,
    "triggerId": "Tz4nW8sVdB1kx6Ym2Qp9L",
    "triggerName": "Triage new cards",
    "triggerType": "event",
    "agentId": "Jf3kP9xR2mLqN7wT4vYsZ",
    "eventType": "card.updated",
    "entityId": "V1StGXR8_Z5jdHi6B-myT"
  }
}
```

| Field          | Description                                                                                   |
| -------------- | --------------------------------------------------------------------------------------------- |
| `runId`        | The run. For an Inbound Trigger, the same id the call returned.                               |
| `status`       | `success`, `failed`, `cancelled` or `suppressed`.                                             |
| `startedAt`    | When the run started — for `suppressed`, when the firing was dropped.                         |
| `completedAt`  | When the run ended. `null` for `suppressed`, since nothing ran.                               |
| `errorMessage` | Why a `failed` run failed, for a person to read — don't match on it; `null` otherwise.        |
| `triggerId`    | The Trigger that fired.                                                                       |
| `triggerName`  | The Trigger's name when the run ended.                                                        |
| `triggerType`  | `cron`, `event` or `inbound`.                                                                 |
| `agentId`      | The Agent the Trigger runs.                                                                   |
| `eventType`    | For an Event Trigger, the event that fired it; `null` otherwise.                              |
| `entityId`     | The card or notification an Event Trigger ran for, or an Inbound Trigger's record; or `null`. |

The Agent's output is never sent — no final answer, no stats, no event data.
Read those in [run history](/building-with-platypus/triggers#review-run-history).

A run that was still going when the server restarted is failed once it has
been running for longer than the run timeout, with `errorMessage` set to
`Server restarted during execution`, and sends `trigger_run.failed` then — not
when the server comes back up. A run whose Trigger is deleted while it is
running sends nothing.

<Callout type="warning">
  A `trigger_run.*` event is best-effort, like every delivery. A server restart
  at the wrong moment can lose one, and nothing resends it. Cron and Event runs
  have no fallback, so don't build anything that waits forever on the event. An
  Inbound caller can [poll the
  run](/building-with-platypus/triggers#check-on-a-run) with its token until
  **Max Runs to Keep** prunes it.
</Callout>

## Headers

Every delivery includes:

| Header                | Value                                                    |
| --------------------- | -------------------------------------------------------- |
| `Content-Type`        | `application/json`                                       |
| `X-Webhook-Signature` | HMAC-SHA256 of the raw request body, hex-encoded.        |
| `X-Webhook-Timestamp` | ISO 8601 timestamp, identical to the body's `timestamp`. |

Any **Custom Headers** you configured on the Webhook are sent alongside these.
A custom header with the same name replaces Platypus's own, so don't reuse
`X-Webhook-Signature` or `X-Webhook-Timestamp` — verification then fails.

## Verifying the signature

The signature is an HMAC-SHA256 of the **exact raw request body**, keyed with the
Webhook's signing secret and hex-encoded. Recompute it on your end and compare —
if it doesn't match, reject the request.

```js
import crypto from "node:crypto";

function verify(rawBody, signatureHeader, signingSecret) {
  const expected = crypto
    .createHmac("sha256", signingSecret)
    .update(rawBody)
    .digest("hex");

  // Constant-time comparison
  return (
    expected.length === signatureHeader.length &&
    crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signatureHeader))
  );
}

// In your handler, compute over the raw body BEFORE JSON parsing:
const ok = verify(rawBody, req.headers["x-webhook-signature"], signingSecret);
```

<Callout type="warning">
  Compute the signature over the raw, unparsed body bytes. Re-serializing the
  parsed JSON can change whitespace or key order and produce a different
  signature.
</Callout>

## Delivery and retries

- Deliveries are **fire-and-forget** — a slow or failing endpoint never blocks
  the action that produced the event.
- A delivery counts as successful on any **2xx** response. Each attempt times out
  after **10 seconds**.
- On failure (non-2xx, timeout, or connection error) Platypus retries up to
  **3 times** with a backoff of **1s, 2s, then 4s**. After that the delivery is
  given up.
- Redirects are **not followed**. A `3xx` response counts as a failure, so point
  the Webhook at the final URL.
- Every attempt re-checks the URL against the egress guard. If the hostname
  doesn't resolve, or resolves somewhere the guard refuses, the delivery is
  dropped without retrying.
- Disabled Webhooks, and Webhooks not subscribed to the event, are skipped.

<Callout type="info">
  Your endpoint should be idempotent. A retry sends the identical body, with the
  same `timestamp` and signature, so processing the same body twice must be
  safe. For `trigger_run.*`, deduplicate on `data.runId` plus `event`: a run
  ends once, so a second delivery with the same pair is a retry.
</Callout>
