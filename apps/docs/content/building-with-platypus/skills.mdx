# Skills

A **Skill** is packaged know-how you attach to an Agent: a name, a description,
a body of instructions for doing one thing well, and optionally a **bundle** of
reference files, scripts and assets that travel with it. The Agent sees only the
name and description up front and pulls in the full body _on demand_ — keeping
the system prompt short. For the concept, see [Skills](/concepts/skills); this
page is how to author, import or install one.

## Author a Skill

<Steps>

### Open the Skill form

From your Workspace, go to the **Skills** section and click **Create skill**.

### Fill in the fields

- **Name** — a kebab-case identifier, e.g. `write-release-note` (lowercase
  letters, numbers, and hyphens; up to 64 characters). This is the name the
  model uses to request the Skill.
- **Description** — a brief summary of what the Skill does and when to reach for
  it (up to 1024 characters). The model reads this to decide _whether_ a request
  is relevant, so make it specific.
- **Body** — the full instructions, up to **50,000 characters**. This is what
  the model receives only after it loads the Skill, so be as detailed as you
  like: step-by-step procedures, examples, formatting rules, edge cases.
- **Argument hint** _(optional)_ — up to **120 characters** describing what text
  should follow the command when a person invokes this Skill. It is shown beside
  the name in the Chat input's [command list](/building-with-platypus/chat#invoking-a-skill-yourself).
- **User-invocable only** — keep this Skill out of the model's catalogue while
  leaving it available for a person to invoke by name.

</Steps>

<Callout type="info">
  Write the **description** for triage and the **body** for execution. The
  description is always in context (so keep it tight); the body is fetched only
  when needed (so it can be long). Use the **argument hint** to tell people what
  to type after the command name.
</Callout>

Name, description and body can't be empty; there is no other minimum.

## Import a Skill from a zip

Skills published in the [Agent Skills](https://agentskills.io) format — a
folder holding a `SKILL.md` and any other files it refers to — import as they
are. Zip the folder, then click **Import zip** beside **Create skill** and pick
the file. An Org Admin can do the same from **Organization settings → Skills**
to create a Shared Skill.

Platypus reads the Skill from `SKILL.md`:

- `SKILL.md` must sit at the root of the zip, or inside a single top-level
  folder. The folder's name doesn't matter.
- It must open with a YAML frontmatter block between `---` lines. `name` and
  `description` are required. `disable-model-invocation` sets **User-invocable
  only**, and `argument-hint` sets **Argument hint**.
- Everything after the frontmatter becomes the **Body**, with blank lines and
  spaces at its start and end trimmed.
- Every other frontmatter key, such as `license` or `compatibility`, is kept
  as-is and shown read-only on the Skill. Platypus doesn't act on them.
- Every other file in the zip is stored with the Skill at its path inside the
  folder. `__MACOSX/` and `.DS_Store` entries aren't stored, but they still
  count toward the entry and size limits below.

Importing always creates a new Skill. If a Skill with that name already exists
in the Workspace (or, for a Shared Skill, in the Organization), the import is
refused — use **Replace bundle** on the existing Skill instead.

### Limits

| Limit                    | Value                      |
| ------------------------ | -------------------------- |
| Zip size                 | 10 MiB                     |
| Total size once unpacked | 25 MiB                     |
| Entries in the zip       | 500, folders included      |
| Frontmatter              | 16 KiB, and a YAML mapping |

A zip is also refused if any entry has an absolute path, a `..` segment or a
backslash, if it contains a symlink or an encrypted entry, if an entry is
compressed with anything other than Deflate (or stored uncompressed), or if two
entries name the same path. A zip
inside the zip is stored as an ordinary file. Any problem rejects the whole
import with a message naming it, and nothing is saved.

## Install Skills from GitHub

You can install Skills straight from a public GitHub repository, such as
[`anthropics/skills`](https://github.com/anthropics/skills), without zipping
them yourself. Click **Install from GitHub** beside **Create skill**. An Org
Admin can do the same from **Organization settings → Skills** to install
Shared Skills.

<Steps>

### Enter the source

Type the repository, or a folder in it, into **GitHub repository**, in either
form:

- a GitHub link: `https://github.com/anthropics/skills`, or one to a folder,
  `https://github.com/anthropics/skills/tree/main/skills`
- the short form `owner/repo[/path][@ref]`: `anthropics/skills`, or
  `anthropics/skills/skills@main`

Leave out the ref to use the repository's default branch. In a link the ref is
the part straight after `tree/`, so a branch whose name contains `/` has to go
in the short form, after `@`.

### Review what was found

Click **Find skills**. Every folder under the path that holds a `SKILL.md` is
listed, with the commit the ref points at now, as `owner/repo@abc1234`. Expand
a Skill to read its `SKILL.md` and see its files and their sizes before you
pick it. A **Needs Sandbox** badge marks a Skill with scripts or binary files.

A Skill you can't pick says why: its name is already taken here, or it breaks
one of the [zip import rules](#limits), such as malformed YAML in its
frontmatter.

### Install

Tick the Skills you want, up to **50** at a time, and click **Install**. Each
one is installed on its own and the page shows how each went: one that fails
leaves the others installed.

</Steps>

Platypus installs exactly the commit you reviewed, even if the branch has moved
on since. Each Skill's files are checked against the same rules as **Import
zip**, and the folder holding `SKILL.md` becomes the Skill's root.

<Callout type="warning">
  Ticking a Skill marked **Needs Sandbox** shows a warning before you install:
  its scripts were written by someone else. If an Agent with a Sandbox runs
  them, they run with the Workspace's [default environment
  variables](/concepts/sandboxes#default-environment-variables) and can send
  them anywhere the Sandbox can reach. Read the files in the review step before
  installing.
</Callout>

An installed Skill's **Bundle** card says where it came from, for example
**Installed from anthropics/skills/skills/pdf @ abc1234**, linking to that
folder on GitHub. Editing the Skill in the form keeps that record; **Replace
bundle** with a zip clears it.

### Limits on installing from GitHub

- **Repository size.** Platypus downloads the whole repository at that commit,
  then reads only the Skills you picked. A repository whose download is larger
  than **100 MiB** can't be installed from, even if the Skill itself is small.
  Zip the Skill's folder and use **Import zip** instead.
- **Public repositories only.**
- **GitHub's rate limit.** Each **Find skills** costs one request to GitHub's
  API, however many Skills the repository holds. Without a token, every install
  on your deployment shares GitHub's anonymous limit of 60 requests an hour.
  When it runs out, the page says when it resets. An Operator can raise it by
  setting [`GITHUB_TOKEN`](/reference/backend-configuration#skills).

## Who can import Skills

An Org Admin decides which Workspaces may import Skill bundles, in
**Organization settings → Skills → Importing in workspaces**. The setting
covers **Import zip**, **Replace bundle** and **Install from GitHub** in a
Workspace:

- **All workspaces** _(the default)_ — every Workspace can import.
- **Selected workspaces** — only the Workspaces switched on in the list below
  it.
- **No workspaces** — none can.

Where importing isn't allowed, those buttons don't show. Skills already
imported stay, and Org Admins can always import Shared Skills in
**Organization settings → Skills**.

<Callout type="info">
  The setting stops bundles of files, not instructions. A Workspace Owner can
  still create a Skill and type or paste anything into its body.
</Callout>

## Bundled files, export and Replace bundle

Open a Skill to see its **Bundle** card:

- It lists every bundled file other than `SKILL.md`, with its size.
  Files are view-only; download one to read it.
- **Frontmatter** shows the keys kept from the imported `SKILL.md`.
- **Export** downloads the Skill as a zip: a folder named after the Skill
  holding `SKILL.md` and every bundled file. Importing that zip gives back the
  same Skill.
- **Replace bundle** takes a zip in the same format as **Import zip** and
  replaces the whole Skill with it — name, description, body, frontmatter and
  every file. If the zip is refused, the Skill is left as it was. A Skill
  installed from GitHub no longer shows where it came from afterwards.

Editing the form still changes the name, description, body and the other
fields; the bundled files stay as they are.

## How an Agent reads bundled files

When an Agent loads a Skill that has bundled files, the result also lists each
file's path, and whether it is text. The Agent reads a text file through the
**`readSkillFile`** tool, passing the Skill's name and the file's path relative
to the Skill's folder — for example `references/forms.md`. In Chat this shows as
**Reading skill file: pdf/references/forms.md**.

`readSkillFile` returns text files of up to **1 MiB**. Whether a file is text is
decided from its content when it is imported, not from its extension. Binary
files, such as images or fonts, can't be read this way: running a bundled script
or using a binary asset needs a Sandbox — see [Skills in a
Sandbox](#skills-in-a-sandbox).

The same rules apply as for `loadSkill`: the Agent can read files only from
Skills attached to it, and not from a Skill marked **User-invocable only**.

<Callout type="info">
  An Agent that manages your Skills can't create a Workspace version of a Shared
  Skill that has bundled files: the new version would have none of the files.
  Ask an Org Admin to change the Shared Skill instead.
</Callout>

## Skills in a Sandbox

When an Agent with the **Sandbox** Tool set loads a Skill that has bundled
files, and the Workspace has a [Sandbox](/concepts/sandboxes), Platypus copies
the Skill into the Sandbox at `.platypus/skills/<name>/`: its `SKILL.md` and
every bundled file at its path. The Agent is told the folder, and relative paths
in the Skill resolve against it, so it can run `scripts/extract.py` from there.
Invoking the Skill with `/` copies it the same way.

The copy is refreshed only when the Skill changes. Loading an unchanged Skill
again writes nothing; after an edit or **Replace bundle**, the next load
rewrites the whole folder, and files no longer in the Skill are removed.

<Callout type="warning">
  The copy belongs to Platypus. Editing a file under `.platypus/skills/` is lost
  the next time the Skill changes and is loaded. Change the Skill itself
  instead.
</Callout>

If the Agent has no Sandbox Tool set, the Workspace has no Sandbox, or the copy
fails (for example because the Sandbox is stopped), the Skill still loads: the
Agent is told why it wasn't copied and reads text files with `readSkillFile`.

Some Sandbox backends can't receive binary files. With one of those, only the
Skill's text files are copied, and the Agent is told which files were left out.

Keep in mind:

- **Any Agent with a shell can read a copied Skill.** The Sandbox belongs to the
  Workspace, so an Agent with the Sandbox Tool set can read every Skill copied
  there, including Skills that aren't attached to it.
- **Bundled scripts run with the Sandbox's [default environment
  variables](/concepts/sandboxes#default-environment-variables).** Read a
  third-party Skill's scripts before you attach it to an Agent with a Sandbox.
- **Copies stay behind.** Deleting, renaming or detaching a Skill doesn't remove
  its folder from the Sandbox.
- **Nothing is written to `.agents/skills/` or `.claude/skills/`.** If you run a
  coding agent such as Claude Code inside the Sandbox and want it to find these
  Skills, symlink the folder yourself, for example
  `ln -s ../.platypus/skills .agents/skills`.

### Needs Sandbox

A Skill shows a **Needs Sandbox** badge in the Skills list and on its **Bundle**
card when it has a file under `scripts/`, a text file whose first line starts
with `#!`, or a binary file. Platypus decides this from the files' content, not
their extensions. These Skills are still offered to Agents without a Sandbox,
which can read their text files but can't run their scripts.

If a Skill has binary files and the Workspace's Sandbox can't receive them, its
**Bundle** card warns: **Some files in this Skill can't be copied to this
Workspace's Sandbox.**

## Attach a Skill to an Agent

A Skill does nothing until an Agent can use it. There are two equivalent ways to
wire them up:

- **From the Skill form** — the **Agents** section lists the Agents in your
  Workspace. Flip a switch to enable this Skill for that Agent.
- **From the [Agent form](/building-with-platypus/agents)** — the **Skills** card
  lists available Skills. Flip a switch to attach one to that Agent.

You can't delete a Skill while any Agent still has it enabled. Turn it off for
those Agents and click **Update** first; **Delete** stays unavailable while the
**Agents** switches have changes you haven't saved.

## Find a Skill

The **Skills** section of your Workspace lists every Skill alphabetically. To
narrow it, type part of a name into **Search skills…** above the list; the
letters only need to appear in order, so `wrn` finds `write-release-note`. The
menu beside it reads **Any agent** by default: pick an Agent to see only the
Skills it uses, or **Unattached** to find the Skills no Agent uses yet.

A long list is split into pages; use the arrows under the list to move
between them. Changing the search or the Agent goes back to the first page.

## How `loadSkill` surfaces a Skill

When an Agent has Skills attached, Platypus puts just their names and
descriptions into the Agent's instructions, with guidance to **use the
`loadSkill` tool** when a request matches one. The model then calls `loadSkill` with the Skill's name, and the tool returns that
Skill's full **body** — which the model reads before responding. Nothing in the
body costs context until the moment it's actually needed.

A Skill marked **User-invocable only** is left out of this catalogue entirely:
the model is never told its name, and cannot load it by name. The flag narrows
the model's view only, never the user's — see below.

## Invoking a Skill by name

Anyone using the Chat can ask for a Skill directly: type `/` at the start of the
input and pick from the list of the Agent's Skills. The Skill's body is loaded
before the Agent answers, exactly as if the model had called for it. The full
behaviour — what the list shows, what happens to a name that matches nothing —
is in [Chat](/building-with-platypus/chat#invoking-a-skill-yourself).

Every Skill attached to the Agent is offered, **User-invocable only** ones
included. That is the point of the setting: a Skill nobody wants the model
choosing on its own stays one keystroke away for the person driving.

## Workspace vs Shared scope

A Skill lives at exactly one scope:

- **Workspace scope** — private to your Workspace. This is what you get when you
  create one from the Skills section above.
- **Organization scope** — a [Shared resource](/concepts/sharing) defined once
  by an Org Admin and attached to many Workspaces. Shared Skills appear with an
  **Organization** badge and are read-only in your Workspace: you can attach
  them to your Agents and the Agent can `loadSkill` them, but only an Org Admin
  can edit the Skill itself. An Org Admin gets a three-dot menu on the card:
  **Edit in org settings** opens the Skill where it is edited, and **Detach**
  removes it from this Workspace without deleting it.

An Org Admin can turn a Workspace Skill into a Shared one with **Promote to
organization** in the Skill's menu — see [Promote](/concepts/sharing#promote).

<Callout type="info">
  An Agent can load only the Skills attached to it — including a Shared Skill,
  once that Skill is attached to your Workspace.
</Callout>
