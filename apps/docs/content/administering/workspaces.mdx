# Workspace settings

Most of what makes a Workspace behave the way it does is one form:
**Workspace settings**, opened from **Workspace** in the gear menu at the top
right of any page in the Workspace. It is shorter than it looks — a name, some text, three
Provider dropdowns, a number, and two switches.

## Creating a Workspace

**Add workspace**, from the Organization page or the Workspace switcher in the
sidebar. Only an Org Admin can create one. It takes three steps, and **Back**
keeps what you entered; nothing is created until **Save** on the last one.

1. **Workspace**
   - **Name** — what to call it (3–30 characters).
   - **Owner** — the member who will own it. Defaults to you.
   - **Context** — optional text about the Workspace.
2. **Provider** — required, because a Workspace cannot run a Chat without one.
   Either turn on one or more of the Organization's Shared Providers under
   **Shared provider**, or switch to **New provider** and fill in one scoped to
   this Workspace. The step opens on **Shared provider** when the Organization
   has any, and on **New provider** when it has none.
3. **Sandbox** — optional. Turn on **Configure a sandbox** to set one up now,
   or leave it off and add one later from the Workspace's settings. The switch
   is unavailable when the deployment has no Sandbox backend installed.

<Callout type="warning">
  **There is no owner field on the settings form afterwards.** Only the owner
  can chat in a Workspace — an Org Admin or Super Admin can change its settings
  but only read its Chats. To give it to someone else, use
  [Transfer](#transferring-a-workspace), which switches off everything that ran
  as the old owner.
</Callout>

## The Context field

**Context** is text about the **Workspace**, included in every Chat anyone runs
there — up to 1,000 characters.

Use it for standing facts about the work: what this Workspace is for, what the
service is called, which team owns it, house terminology.

<Callout type="warning">
  This is not the same thing as a user's own **Workspace Context** under **My
  settings → Contexts**, even though both land in the prompt. This field is the
  Workspace's and reaches everyone in it; theirs is private to them. Personal
  preferences ("answer terse, no preamble") belong in theirs — putting them here
  imposes them on every Chat in the Workspace. See [Memory &
  context](/concepts/memory-and-context#three-different-things-are-called-context).
</Callout>

## The three Provider dropdowns

These only appear once the Workspace exists, and each lists Providers available to
that Workspace.

- **Task Model Provider** — the Provider used for the small one-shot jobs, such as
  naming a Chat and generating its tags. Leave it as **None (use chat provider)**
  and each Chat uses its own. Point it at something cheap and fast if your chat
  models are expensive.
- **Memory Extraction Provider** — **this is the switch that turns Memory on.**
  Leave it **Disabled** and nothing new is extracted. Summaries already written
  stay in the prompt until they age out — see [Turning Memory
  on](/concepts/memory-and-context#turning-memory-on).
- **Memory Embedding Provider** — needed for semantic memory search. Without
  one, an Agent with the **Memory** Tool set gets `memoryGet` but not
  `memorySearch`. Separate from extraction; you can have one without the other.

<Callout type="warning">
  The two memory dropdowns only list Providers that have the relevant model
  configured — a memory-extraction model, or an embedding model id. An empty
  dropdown is not a Workspace problem: go and set that model on the Provider
  first, then come back.
</Callout>

## Memory Summary Retention

How many daily memory summaries to keep for each member, from **7** to **365**,
defaulting to **90**. The oldest past that number are deleted the next time
Memory writes a summary for that member.

<Callout type="warning">
  Lowering it deletes nothing on its own. While **Memory Extraction Provider**
  is **Disabled**, or for a member who hasn't chatted since, the old summaries
  stay. It doesn't change what goes into the prompt either: older summaries
  reach an Agent only through the **Memory** Tool set — see [Memory &
  context](/concepts/memory-and-context).
</Callout>

## The two delegation switches

Both are visible only to an Org Admin, and both are **off** by default. Off means
only Org Admins may configure that resource in this Workspace.

- **Owner-managed providers** — lets the Workspace Owner create and edit
  Workspace-scoped Providers. Turn it on where the owner legitimately holds their
  own vendor key.
- **Owner-managed MCP servers** — lets the Workspace Owner register and authorize
  their own MCP servers. Turn it on for personal-credential integrations, where
  requiring an admin for every connection is friction with no safety benefit.

<Callout type="warning">
  These switches hand out real reach, per Workspace. An owner with
  **Owner-managed MCP servers** on can point an Agent at any MCP server they can
  reach, with credentials you never see, and you will not be asked. Turn it on
  deliberately, for Workspaces whose owner you'd trust with that, and not as a
  blanket default to stop people filing tickets.
</Callout>

The switches only cover **Workspace-scoped** resources. An owner can never edit a
Shared one, and never touch the Sandbox — that stays admin-only whatever these
say.

## Allow Inbound Triggers

Visible only to an Org Admin, and **off** by default. It lets this Workspace's
[Inbound Triggers](/building-with-platypus/triggers#inbound-triggers) take
calls, and it only matters while the Organization's **Inbound Triggers** setting
is **Selected workspaces** — see [Inbound Triggers](/administering#inbound-triggers).
Under **No workspaces** or **All workspaces** the switch is locked, and its description
says which applies and links to the Organization's **Inbound Triggers** screen,
which lists the same switch for every Workspace.

## Transferring a Workspace

**Transfer**, beside **Delete**, makes another member of the Organization the
Workspace's owner. Only an Org Admin or Super Admin sees it. The new owner must
be a member and not banned. When nobody qualifies, **Transfer** is disabled and
points you to inviting someone.

Pick the **New owner**, and whether to **Keep history** (on by default):

- **Keep history** on — Chats stay, and the old owner's Memories in this
  Workspace move to the new owner.
- **Keep history** off — the Workspace's Chats, with their files, A2A tasks and
  Trigger run transcripts, its Memories and its Notifications are deleted.

Either way, Boards, cards, Sandbox files and Dashboards are kept. **Next**
shows what the transfer does before you confirm it.

Every transfer, whichever you pick:

- switches off every Trigger, and revokes every Inbound Trigger token and A2A
  token;
- clears MCP sign-ins and bearer tokens on this Workspace's own MCP servers,
  and the environment the owner set on its Sandbox;
- switches off **Owner-managed providers** and **Owner-managed MCP servers**;
- stops any Chat, Trigger run or A2A task running in it;
- takes the Workspace away from the old owner at once;
- posts a Notification in the Workspace telling the new owner what happened.

The new owner turns on the Triggers and issues the tokens they want, and
authorizes the MCP servers again. Nothing starts running as them until they do.

<Callout type="warning">
  **Workspace-scoped Provider keys stay.** Platypus cannot tell a key an Org
  Admin entered from one the old owner entered, so it keeps them all rather than
  stop every Agent. The confirm step lists the Workspace's own Providers:
  replace any key that was the old owner's personal one.
</Callout>

Some things keep naming the old owner: their own Workspace Context for this
Workspace stays theirs, and the new owner never sees it. Card authors,
assignees and card history are left as they were.

## Deleting a Workspace

**Delete** asks you to type `Delete workspace` to confirm, and takes everything
scoped to the Workspace — including each member's own **Workspace Context** for
it. Shared resources are only detached, not deleted. Its Sandbox is torn down
too. With the Docker backend that removes the container and its volume, so any
files an Agent left in `/workspace` are gone. With SSH the host is left alone.
It is not recoverable from inside the product — only from a database backup.
