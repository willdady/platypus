# Getting Started

Platypus is a self-hosted platform for AI agents that use tools, run on
schedules and events, and connect to your data through the Model Context
Protocol. This guide takes you from nothing to your first streamed reply.

The fastest path is the Docker quick start below, then a five-step loop:
**create a Workspace → configure a Provider → create an Agent → start a Chat →
send a message**.

## Before you start

- **Linux or macOS.** On Windows, run everything inside WSL.
- **Docker Engine with the Compose v2 plugin, running.** Every command here is
  `docker compose` (a space, not a hyphen). If `docker compose version` fails,
  install the Compose v2 plugin before going further.
- **`curl` and `openssl`**, which the installer uses to download the release and
  generate secrets.
- **Ports `3000` and `4000` free on the host.** The frontend publishes `3000`
  and the backend `4000`. Postgres stays on the private network and publishes
  nothing.

## Quick start (Docker)

Run the installer, with your own email in place of `you@example.com`:

```bash
curl -fsSL https://platypus.chat/install.sh | ADMIN_EMAIL=you@example.com bash
```

It installs the latest release into a `platypus` directory, generates a secret
and an admin password, and brings up the backend, frontend, and a Postgres 17
database with pgvector. When the stack is healthy it prints where to sign in:

```text
  Sign in at:  http://localhost:3000
  Email:       you@example.com
  Password:    <generated>
```

Open [http://localhost:3000](http://localhost:3000) and sign in with those
credentials.

<Callout type="warning">
  **The printed credentials are temporary.** Change the password from the in-app
  account settings after your first sign-in, especially on any network-reachable
  deployment.
</Callout>

Installing on a server rather than your laptop, choosing the version, or setting
your own admin email? See
[Installer settings](/self-hosting/docker-compose#installer-settings). To edit
`.env` by hand before first boot, use the
[manual install](/self-hosting/docker-compose#manual-install) instead.

Sign-in is **email and password**. There is no SSO, no OIDC and no SAML, and no
configuration that adds them — see
[Users & access](/self-hosting/users-and-access) if that is a go/no-go question
for you.

For a production-grade deployment — TLS, a reverse proxy, persistent storage,
and configuration hardening — see
[Running in production](/self-hosting/production).

## When the stack doesn't come up

The three failures that account for almost all of them, and what each looks
like. Run the commands from the `platypus` directory the installer created.

| Symptom                                                                   | Cause                                                                                                                               | Fix                                                                                                                                                                                               |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `docker compose ps` shows `backend` as **exited**                         | A required variable is unset, first-boot seeding failed, or the backend gave up reaching Postgres after about 30 seconds of retries | `docker compose logs backend` — the last line names the variable, the seeding problem, or the database error. Fix it and `docker compose up -d` again.                                            |
| `docker compose up` reports **dependency failed to start** for `database` | Postgres never became healthy, so the backend was not started                                                                       | `docker compose logs database`.                                                                                                                                                                   |
| Port already allocated on `3000` or `4000`                                | Something else on the host holds the port                                                                                           | Stop the other process, or remap the host side in a `compose.override.yaml`. Remapping `3000` means updating `ALLOWED_ORIGINS` and `FRONTEND_URL`; remapping `4000` means updating `BACKEND_URL`. |

You sign in successfully and are immediately signed out again? That is the URL
variables disagreeing, not a password problem — see
[Service URLs](/self-hosting/configuration#service-urls).

Deeper diagnosis, including recovering from a first boot that never completed,
is in
[Deploy with Docker Compose](/self-hosting/docker-compose#recovering-from-a-failed-first-boot).

## First run & the default admin

First boot creates a **Default Organization** and an admin account from
`ADMIN_EMAIL` / `ADMIN_PASSWORD`. That account is the **Operator** — the platform
super-admin. It creates no Workspace: you create the first one yourself, and
connect it to a model as you do.

Editing `ADMIN_EMAIL` / `ADMIN_PASSWORD` after first boot changes nothing —
change the password from within the app. The full rule, and the recovery path
for a first boot that failed, are in
[what first boot creates](/self-hosting/docker-compose#what-first-boot-creates).

For day-to-day work, add regular users — see
[Users & access](/self-hosting/users-and-access).

## Your first agent

Once you're signed in, here's the end-to-end loop to a working agent reply.

<Steps>

### Create your Workspace

After signing in you land on the **Default Organization**, which has no
Workspaces yet. Click **Add workspace**, give it a **Name**, leave yourself as
the **Owner**, and click **Next**.

> A **Workspace** is your scoped environment — it holds your Chats, Agents,
> Skills, MCP servers, and Providers. See [Concepts](/concepts) for how
> Organizations, Workspaces, and Agents fit together.

### Configure a Provider

A Workspace can't run an agent until it can reach a model, so the next step asks
for a Provider. Stay on **New provider** and fill in the form:

- **Provider Type** — your AI vendor. Exactly five: OpenAI, OpenRouter,
  Anthropic, Google, Bedrock. Running Ollama, vLLM or Azure OpenAI? Pick
  **OpenAI** and set **Base URL** — see
  [Supported vendors](/self-hosting/providers-and-auth#supported-vendors).
  Running that model server on this machine while Platypus runs in Docker? See
  [Reaching a model server on the host
  machine](/self-hosting/providers-and-auth#reaching-a-model-server-on-the-host-machine)
  for what **Base URL** takes.
- **Name** — a label for this connection.
- **API Key** — your credential from that vendor. The field is required: for a
  model server with no key, such as Ollama, enter any placeholder value.
- **Region** _(Bedrock only)_ — the AWS region, e.g. `us-east-1`. Required for
  Bedrock.
- **Models** — a repeatable list, not a text box. Click **Add model** for each
  one and type its id into the **Model ID** field (e.g. `gpt-4o`). Leave
  **Alias** empty, **Context window** on **Not set**, and **Advanced** collapsed
  for now — every one of them is optional, and you can come back to them.
- **Task Model ID** — one of the model ids you just added. Platypus uses it to
  name your Chats; left empty, every Chat stays _Untitled_.

Click **Next**. The last step offers a Sandbox; leave **Configure a sandbox**
off for now and click **Save**. Nothing is created until you do — the Workspace
and its Provider are saved together, and you land on the Workspace dashboard.

<Callout type="info">
  Don't have a key yet? [OpenRouter](https://openrouter.ai) gives you a single
  key that reaches many vendors and is a quick way to try Platypus.
</Callout>

### Create an Agent

From the dashboard's **Agents** section, click **Create agent**.

- **Name** — what to call the agent.
- **Model** — pick one of the models you enabled on your Provider (the dropdown
  groups models under each Provider).
- **Instructions** _(optional)_ — how the assistant should behave, e.g. _"You are
  a concise, helpful assistant."_ Platypus composes the system prompt around
  this; see [The system prompt](/concepts/system-prompt).

Click **Save**. An **Agent** pins a Provider, model, and Instructions (and,
later, Tools, Skills, and Sub-Agents) into a reusable preset.

### Start a Chat and send a message

Open a new Chat from the Workspace, then click the model selector and choose
your Agent under **Agents** (or pick a Provider + model directly).

Type a message in the input box and press **Enter**. The assistant's reply
streams back token by token — that's a **Chat turn** running end to end:
resolving your Agent's Provider and model, rendering its system prompt, and
streaming the model's response.

</Steps>

That's the full loop.
