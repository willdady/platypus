# Providers & models

## Provider

A **Provider** is a configured connection to an AI vendor. It's what lets
Platypus actually talk to a model on your behalf.

There are five Provider types — OpenAI, OpenRouter, Bedrock, Google,
Anthropic — and no others. Ollama, vLLM, Azure OpenAI and any other
OpenAI-compatible endpoint are reached through the **OpenAI** type with its
**Base URL** overridden; see [Supported
vendors](/self-hosting/providers-and-auth#supported-vendors).

A Provider carries:

- the **credentials** (such as an API key) for that vendor,
- an optional **base URL** for self-hosted or proxied endpoints,
- the list of **models** that have been enabled for use,
- and a default **task model** used for quick one-shot jobs (like generating a
  title for a Chat) rather than full conversations.

When you run a Chat turn, you either pick a Provider and one of its models
directly, or you select an **[Agent](/concepts/agents)** that already points at a
Provider and model for you.

## Where Providers live

A Provider lives at one of two levels:

- **Organization scope** — set up once and made available across many Workspaces
  (a [Shared resource](/concepts/sharing)).
- **Workspace scope** — private to a single Workspace.

<Callout type="info">
  Providers carry credentials, so they're usually configured by an **Org
  Admin**. A Workspace Owner can manage them only where an Org Admin has
  delegated that. See [Providers &
  authentication](/self-hosting/providers-and-auth) for setup.
</Callout>

Stored credentials — the API key and any custom headers — are readable only by
someone who can manage the Provider. Everyone else still sees the Provider and
can select its models; the credential fields come back empty, flagged only as
set or unset.

**Why this matters to you:** the models you can pick on a Chat or an Agent come
from the Providers available in your Workspace. If a model you expect isn't
there, it's because no available Provider has it enabled — an Org Admin controls
that list.

## Model aliases

A **Model alias** is a stable name a Provider gives one of its models — `fast`,
or `flagship` — that an Agent or a Chat selects instead of the vendor's model
id. Point the alias at a newer model and every Agent and Chat using it moves
with it, on their next turn, with no edits to any of them.

An Org Admin sets one in the **Alias** field beside a model on the Provider.
From then on, that model appears in the Agent and Chat model pickers under its
alias rather than its model id.

Alias names share one list with the model ids on the same Provider, so no alias
may repeat another alias or any model id there — including in different casing.
Repointing an alias takes effect immediately: the next turn of every Agent and
Chat using it runs on the new model, and nothing pins an in-progress
conversation to the model it started on.

<Callout type="warning">
  Aliases work on the **Agent and Chat model only**. A Provider's own **Task
  Model ID**, **Memory Extraction Model ID** and **Embedding Model ID** must
  each name a real model id; entering an alias there is rejected when you save.
  Those three point at one model from one Provider, so an alias would save you
  no edits — and on the embedding model it would hide a change that has to
  invalidate every stored memory embedding.
</Callout>

Once a model has an alias, the picker offers the alias and not the underlying
model id, so you can no longer pin an Agent to that exact id. An Agent that
already stored the id keeps running unchanged and now shows the alias; saving it
switches it to the alias.

An Agent that builds other Agents sees the same list you do, so the Agents it
creates use the alias and move with your repoints too.

**Renaming an alias is not a rename.** An alias is only its name, so changing it
removes the old name and creates a new one. Platypus handles this for you:
clearing or renaming an alias points every Agent and Chat that used it back at
the concrete model id, so each keeps running on the same model as before, and
the Provider form tells you how many moved. Delete the model itself at the same
time and there is no id left to fall back to — those Agents and Chats fail their
next turn, exactly as they would if you removed a model they named directly.

## Attaching files

Not every model can read every file. A file you attach to a message is a **File
part**, carried alongside the message's text. Which types a model takes
**natively** is declared per model on the Provider, and what happens to each
File part follows from that:

- **It's a type the model reads natively** (usually images, and PDFs on the
  frontier vendors) — the file goes through untouched.
- **It's a text or code file** — `.md`, `.csv`, `.json`, `.py`, and friends — its
  contents are inlined into the message, labelled with the filename. This works
  regardless of what the model natively accepts.
- **It's a PDF or DOCX the model can't take natively** — the text is extracted
  and sent in the file's place, marked as extracted text. This is what makes
  File parts usable with local and proxied models.
- **It's anything else** — the turn is refused before it runs, naming the file,
  and nothing is saved to the Chat. You can remove the file or switch to a model
  that accepts it.

<Callout type="info">
  Extracted text is **lossy**: tables, layout, and embedded images don't
  survive, and a long document is truncated with a note saying so. If fidelity
  matters, use a model that reads the format natively. There's no OCR, so a
  scanned (image-only) PDF has no text to extract and is refused.
</Callout>

**Why this matters to you:** attaching a PDF to a small self-hosted model still
works, but the model is reading a text rendering of it, not the document. The
Chat warns you when the model you've selected can't read a File part natively,
and refuses up front rather than failing mid-turn. Org Admins configure the
per-model types — see [Self-Hosting → Providers &
authentication](/self-hosting/providers-and-auth).

## Web search

Whether the Chat **Search** toggle finds anything is a property of the Provider,
decided by one **Web search** field under **Advanced settings**.

Choices: **None** (no web search at all), **the provider's built-in search**
(offered only on a Provider whose model has one — Anthropic, Google,
OpenRouter, and OpenAI on the Responses API), and any Web-search backend
plugins your deployment has installed — SearXNG, a headless browser, whatever
the Operator added. Selecting a backend gives the Search toggle to Providers
that never had it otherwise: a self-hosted vLLM or LiteLLM endpoint, or
Bedrock.

<Callout type="warning">
  **Selecting a backend can grant page reading as well as search.** A backend
  supplies its own search, and optionally a page reader; where it supplies both,
  a searching turn on that Provider lets the model fetch pages by URL. The
  vendors' built-in search does not — it returns results only. There is no
  separate setting for it: the reader comes with the backend, so the decision is
  which backend you select. What a fetch may reach is bounded by [the egress
  guard](/self-hosting/configuration#the-egress-guard), and a backend's reader
  ignores `robots.txt` — whereas the **Web Fetch** Tool set honours it unless an
  Operator has turned that off.
</Callout>

Three things the field tells you about a selection:

- **A selection whose plugin is gone** stays in the list, marked **(not
  installed)**, rather than quietly reading as None — so you can see what the
  Provider points at and change it. Such a selection runs no search.
- **Platypus couldn't load the installed backends** — the field says so and
  leaves your stored selection alone; the list may be missing entries.
- **The provider's built-in search, on a Provider that has none** — Bedrock, or
  OpenAI on the Completions API — is marked **(unavailable here)**. It runs no
  search, but the selection is kept rather than rewritten: switch that Provider
  to a type or API mode that does have built-in search and it applies again. To
  retire it instead, pick something else yourself.

Results are cited the same way whichever search ran: the pages used appear as
**Sources** under the reply. Adding a backend to a deployment is an Operator task
— see [Extending → Web-search
backends](/extending/web-search-backends).

## Security guardrails

A Provider carries an optional free-text **security guardrails** field. Whatever
you write there is appended **last** in the system prompt — the final
instructions the model reads before the conversation — for **every** run on that
Provider, including sub-agent runs that resolve to it.

It is provider-scoped on purpose: how susceptible a model is to prompt injection
is a property of the endpoint. Frontier hosted models resist most attacks
out of the box; smaller self-hosted or quantized models need more explicit
steering. Put the guarding where the weakness is.

<Callout type="warning">
  Guardrails are a **floor, not a guarantee**. A capable model follows them most
  of the time, but a determined multi-turn injection can still occasionally slip
  — especially on smaller self-hosted models. For hard guarantees (blocking
  exfiltration, enforcing tool policy) pair the prompt-level layer with a proxy
  in front of the Provider's `baseUrl`. See [Self-Hosting → Providers &
  authentication](/self-hosting/providers-and-auth) for the three-layer model.
</Callout>

The field is **append-only and non-suppressible**: an Agent's own **Instructions**
cannot opt out of it — they are the _first_ fragment of the composed system
prompt, and this is the last (see [The system
prompt](/concepts/system-prompt)). The escape hatch is to point the Agent at a
different Provider.

There is no fixed catalog — you write plain prose. Wordings you can paste in as-is,
one per injection class, are in
[Starter snippets](/self-hosting/providers-and-auth#starter-snippets).

<Callout type="info">
  Not to be confused with an Organization's **identity / context** field, which
  is framing rendered *early* in the prompt — see [Memory &
  context](/concepts/memory-and-context). Identity says *who the assistant is*;
  guardrails say *what it must not be tricked into doing*.
</Callout>
