# Providers & models

## Provider

A **Provider** is a configured connection to an AI vendor. It's what lets
Platypus talk to a model on your behalf.

There are five Provider types — OpenAI, OpenRouter, Bedrock, Google,
Anthropic — and no others. Ollama, vLLM and any other OpenAI-compatible
endpoint are reached through the **OpenAI** type with its
**Base URL** overridden, and **API Mode** set to **Chat Completions** where the
server has no Responses API; see [Supported
vendors](/self-hosting/providers-and-auth#supported-vendors).

A Provider carries:

- the **credentials** for that vendor — an API key, and any custom headers a
  proxy needs,
- an optional **base URL** for self-hosted or proxied endpoints,
- the list of **models** that have been enabled for use,
- a default **task model** used for background jobs — naming a Chat and
  summarising a long conversation — rather than full turns. Choose a fast,
  inexpensive model with a large context window: a summary can send it most of
  a conversation. If it cannot take that much, the Chat's own model writes the
  summary instead. Give the task model's entry a **Context window**: a summary
  that would fill more than half of it goes straight to the Chat's model, so a
  server that silently cuts off an overlong prompt never summarises half a
  conversation,
- and the models used for memory extraction and embeddings, plus per-model
  settings such as the context window,
- and the [Job settings](#job-settings) sent with the task model and the memory
  extraction model.

When you run a Chat turn, you either pick a Provider and one of its models
directly, or you select an **[Agent](/concepts/agents)** that already points at a
Provider and model for you.

## Where Providers live

A Provider lives at one of two levels:

- **Organization scope** — set up once and made available across many Workspaces
  (a [Shared resource](/concepts/sharing)).
- **Workspace scope** — private to a single Workspace.

<Callout type="info">
  Providers carry credentials, so they're usually configured by an **Org
  Admin**. A Workspace Owner can manage Workspace-scoped ones only where an Org
  Admin has turned on **Owner-managed providers** for that Workspace. See
  [Providers & authentication](/self-hosting/providers-and-auth) for setup.
</Callout>

Stored credentials — the API key and any custom headers — are readable only by
someone who can manage the Provider. Everyone else still sees the Provider and
can select its models, but opens it read-only with **API Key** and **Headers**
empty. A Shared Provider's credentials are hidden inside every Workspace, Org
Admins included; an Org Admin reads them from the Organization.

**Why this matters to you:** the models you can pick on a Chat or an Agent come
from the Providers available in your Workspace. If a model you expect isn't
there, it's because no available Provider has it enabled — whoever manages that
Provider controls the list.

## Header placeholders

A custom header is entered in the Provider's **Headers** section, under
**Advanced settings**: choose **Add header** for each name and value pair. A
header name is stored once — if it appears in more than one row, the last
row's value is the one saved.

A custom header's **value** can carry a placeholder, replaced on every request
with a value from the work being done. The only one is `${SESSION_ID}`:

| Placeholder     | Replaced with                                                                                                                                                                                                                                                                        |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `${SESSION_ID}` | The **Chat**'s id, for anything done in that Chat — its turns, the Sub-Agents they delegate to, its title, its Memories and its Transcript summary. For a headless **Trigger** run, that run's id instead, so a Chat keeps one session upstream and each Trigger run starts its own. |

A value may contain the placeholder more than once, and header _names_ are never
substituted. A `$` not followed by `{` is sent as written. Any other
`${…}` token is rejected when the Provider is saved.

## Model aliases

A **Model alias** is a stable name a Provider gives one of its models — `fast`,
or `flagship` — that an Agent or a Chat selects instead of the vendor's model
id. Point the alias at a newer model and every Agent and Chat using it moves
with it, on their next turn, with no edits to any of them.

Whoever manages the Provider sets one in the **Alias** field of the model's
**Add model** or **Edit model** dialog.
From then on, that model appears in the Agent and Chat model pickers under its
alias rather than its model id.

Alias names share one list with the model ids on the same Provider, so no alias
may repeat another alias or any model id there — including in different casing.
Repointing an alias takes effect immediately: the next turn of every Agent and
Chat using it runs on the new model, and nothing pins an in-progress
conversation to the model it started on.

<Callout type="warning">
  Aliases work on the **Agent and Chat model only**. A Provider's own **Task
  Model**, **Memory Extraction Model** and **Embedding Model ID** name a real
  model id and don't resolve aliases. The first two offer the model ids from the
  **Models** list, never an alias. **Embedding Model ID** is typed: typing
  `flagship` there saves, is sent to the vendor as if it were a model id, and
  the job fails.
</Callout>

<Callout type="warning">
  Changing a Provider's **Embedding Model ID** or **Embedding Dimensions**
  invalidates the memory embeddings of every Workspace using it. Semantic memory
  search is unavailable there until summaries are re-embedded.
</Callout>

Once a model has an alias, the picker offers the alias and not the underlying
model id, so you can no longer pin an Agent to that exact id. An Agent that
already stored the id keeps running unchanged and now shows the alias; saving it
switches it to the alias.

An Agent that builds other Agents sees the same list you do, so the Agents it
creates use the alias and move with your repoints too.

**Renaming an alias is not a rename.** An alias is only its name, so changing it
removes the old name and creates a new one. Clearing or renaming an alias points
every Agent and Chat that used it back at the concrete model id, so each keeps
running on the same model as before, and the Provider form tells you how many
moved. Delete the model itself at the same time and there is no id left to fall
back to — those Agents and Chats fail their next turn, exactly as they would if
you removed a model they named directly.

## Job settings

The **Task Model** and **Memory Extraction Model** are each chosen from
the Provider's **Models** list, or set to **None**. With no task model, Chats
stay _Untitled_. A Provider with no memory extraction model can't be chosen for
memory extraction. **Settings**, beside each one, opens that model's Job
settings: the Reasoning controls and sampling parameters sent with its
background jobs. The task model's settings apply when it names a Chat
and when it writes a Transcript summary. The memory extraction model's apply
when it pulls memories from a Chat. **Settings** is greyed out until a model is
chosen.

| Field                                                                                        | What it does                                                                                                                      |
| -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Thinking**, **Effort**, **Thinking budget**                                                | The Agent's [Reasoning controls](/building-with-platypus/agents#reasoning-controls). Each appears only where the model offers it. |
| **Temperature**, **Seed**, **Top-p**, **Top-k**, **Presence Penalty**, **Frequency Penalty** | The Agent's sampling parameters, with the [same ranges](/building-with-platypus/agents#tune-generation).                          |

Leave a field empty to send nothing, so the model's own default applies. A
Provider whose settings are all empty sends its jobs exactly as it did before
Job settings existed, and setting only sampling parameters sends no reasoning
fields. A value you set beats the job's own default: memory extraction normally
sends a **Temperature** of `0.3`, and only a **Temperature** you set replaces
it. Nothing is stored until you save the Provider.

A reasoning control you set stays saved when you switch to a model that
doesn't offer it, and does nothing there. Switch back, and it applies again.

<Callout type="warning">
  **A self-hosted thinking model thinks through every Chat title too.** The task
  model runs at its server's default, so a model that thinks by default spends a
  long reasoning pass on a five-word title and on every Transcript summary,
  where a long pass can use up the summary's room, so the summary is thrown away
  and written again by the Chat's model. Turn **Thinking** off in the task
  model's **Settings**. The control appears only once the model's Reasoning map
  declares it — see [Declaring a Reasoning
  map](/self-hosting/providers-and-auth#declaring-a-reasoning-map).
</Callout>

A Transcript summary falls back to the Chat's own model when the task model
fails. That fallback sends none of the task model's Job settings, which were
chosen for a different model. Where the task model is the Chat's own model, there
is nothing to fall back to: the summary is written once, with the task model's
Job settings.

A **Task Model** or **Memory Extraction Model** saved before it was chosen
from a list may name a model that is not on it. It keeps working, and the form
marks it **not in the model list** until you add that model or choose another.

## Testing a model

Each card in the **Models** list has a plug icon beside its pencil and bin. It
runs one small real completion — a request for the single word `ok` — against
that card's model, using the Provider settings as they currently stand in the
form, unsaved edits included. Nothing is saved, and the test leaves nothing
behind.

Use it after setting up a Provider. It finds a wrong API key, Base URL, API mode
or model id in one click, instead of on a Chat's first turn. You can test before
the form is finished: the test needs the API key and the model list, not a Name
or a task model.

The test gives up after **20 seconds**. A server that accepts the connection and
never answers is therefore reported as **Base URL unreachable**, not waited on.

The verdict appears on the card itself and never as a toast. Changing any
Provider-level field clears every verdict, and so does removing a model, because
the later cards shift. Editing one model clears only that card's verdict. A
request the API refuses before it reaches the Provider — typically a field the
form has not filled in yet — is reported as **Could not run the test**, with the
reason; it says nothing about the connection.

| The test says                            | What it means                                                                                                                                             |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Connection successful**                | The Provider answered on that model.                                                                                                                      |
| **API key rejected**                     | The key in the form was refused. Check it, and any custom header the vendor needs for authentication.                                                     |
| **Model not available on this Provider** | The model id is not one this Provider serves.                                                                                                             |
| **API mode wrong for this server**       | The server does not implement the selected **API Mode**. OpenAI-compatible servers such as vLLM or Ollama usually need **Chat Completions**.              |
| **Base URL unreachable**                 | Platypus could not reach the server: a wrong URL, a DNS failure, a TLS certificate problem, a refused connection, or no answer before the test's timeout. |
| **Reachable but rate limited**           | The connection works; the Provider is refusing requests for now. This is a warning, not a configuration error — try again later.                          |
| **Unknown error**                        | The Provider rejected the request for a reason Platypus does not recognise. The Provider's own message is shown with it.                                  |

Every Provider failure shows the Provider's own message verbatim, so a proxy's
or a vendor's explanation is not lost.

A test has no Chat or Trigger run behind it, so a `${SESSION_ID}` placeholder in
a custom header value is replaced with a fixed test id. The verdict on the card
says when that happened.

Close a verdict with the **×** in its corner. Editing the Provider or the model
clears it too.

The plug icon follows the same rule as saving the Provider: an Org Admin, or a
Workspace Owner where an Org Admin has turned on **Owner-managed providers**. It
is absent from a read-only Provider, such as a Shared Provider opened from a
Workspace.

## Attaching files

Not every model can read every file. A file you attach to a message is a **File
part**, carried alongside the message's text. Which types a model takes
**natively** is declared per model on the Provider, and what happens to each
File part follows from that:

- **It's a type the model reads natively** — the file goes through untouched.
- **It's a text or code file** — `.md`, `.csv`, `.json`, `.py` and the like — its
  contents are inlined into the message, labelled with the filename. This works
  regardless of what the model natively accepts.
- **It's a PDF or DOCX the model can't take natively** — the text is extracted
  and sent in the file's place, marked as extracted text. This is what makes
  File parts usable with local and proxied models.
- **It's anything else** — the turn is refused before it runs, naming the file,
  and nothing is saved to the Chat. You can remove the file or switch to a model
  that accepts it.

<Callout type="info">
  Extracted text is **lossy**: tables, layout, and embedded images don't
  survive, and a long document is truncated, with a note telling the model so. A
  PDF or DOCX over **25 MiB** is refused rather than extracted. If fidelity
  matters, use a model that reads the format natively. There's no OCR, so a
  scanned (image-only) PDF has no text to extract and is refused.
</Callout>

**Why this matters to you:** attaching a PDF to a small self-hosted model still
works, but the model is reading a text rendering of it, not the document. The
Chat warns you when the model you've selected can't read a File part natively,
and refuses up front rather than failing mid-turn. Whoever manages the Provider
sets the per-model types — see [Self-Hosting → Providers &
authentication](/self-hosting/providers-and-auth).

## Web search

Whether a Chat offers the **Search** toggle, and what it searches with, is a
property of the Provider, decided by one **Web search** field under **Advanced
settings**.

Choices: **None** (no web search at all), **The provider's built-in search**
(offered only on a Provider type that has one — Anthropic, Google, OpenRouter,
and OpenAI with **API Mode** set to **Responses**), and any Web-search backend
Plugins the Operator has installed. Selecting a backend gives the Search toggle
to Providers that never had it otherwise: a self-hosted vLLM or LiteLLM
endpoint, or Bedrock.

<Callout type="warning">
  **Selecting a backend that reads pages lets the model fetch any URL your
  deployment can reach, short of what the egress guard blocks.** A backend
  supplies its own search, and optionally a page reader; where it supplies both,
  every searching turn on that Provider can fetch pages by URL from your
  deployment. The vendors' built-in search runs on the vendor's side — some open
  pages as part of searching, but nothing is fetched from your deployment. There
  is no separate setting for it: the reader comes with the backend, so the
  decision is which backend you select. What a fetch may reach is bounded by
  [the egress guard](/self-hosting/configuration#the-egress-guard). Platypus
  does not check `robots.txt` for a backend's reader, though the backend itself
  may; the **Web Fetch** Tool set honours it unless an Operator has turned that
  off.
</Callout>

Three things the field tells you about a selection:

- **A selection whose Plugin is gone** stays in the list, marked **(not
  installed)**, rather than quietly reading as None — so you can see what the
  Provider points at and change it. Such a selection runs no search: the Chat
  still offers **Search**, and each reply says _Search was unavailable — this
  reply was written without it._
- **Platypus couldn't load the installed backends** — the field says so and
  leaves your stored selection alone; the list may be missing entries.
- **The provider's built-in search, on a Provider that has none** — Bedrock, or
  OpenAI with **API Mode** set to **Chat Completions** — is marked
  **(unavailable here)**. It runs no search, but the selection is kept rather
  than rewritten: switch that Provider to a type or API mode that does have
  built-in search and it applies again. To retire it instead, pick something
  else yourself. A new Provider starts on built-in search, so a new Provider
  of either kind shows this from the start, and runs no search until you pick
  **None** or a backend.

Results are cited the same way whichever search ran: the pages used appear in a
collapsible **Used N sources** row above the reply. Adding a backend to a
deployment is an Operator task — see [Extending → Web-search
backends](/extending/web-search-backends).

## Security guardrails

A Provider carries an optional free-text **Security guardrails** field. Whatever
you write there is appended **last** in the system prompt — the final
instructions the model reads before the conversation — for **every** run on that
Provider, including Sub-Agent runs that resolve to it.

It is provider-scoped on purpose: how susceptible a model is to prompt injection
is a property of the endpoint, and smaller self-hosted or quantized models need
more explicit steering. Put the guarding where the weakness is.

<Callout type="warning">
  Guardrails are a **floor, not a guarantee**. A capable model follows them most
  of the time, but a determined multi-turn injection can still occasionally slip
  — especially on smaller self-hosted models. For hard guarantees (blocking
  exfiltration, enforcing tool policy) pair the prompt-level layer with a proxy
  in front of the Provider's **Base URL**. See [Self-Hosting → Providers &
  authentication](/self-hosting/providers-and-auth) for the three-layer model.
</Callout>

The field is **append-only and non-suppressible**: an Agent's own **Instructions**
cannot opt out of it — they are the _first_ fragment of the composed system
prompt, and this is the last (see [The system
prompt](/concepts/system-prompt)). The escape hatch is to point the Agent at a
different Provider.

There is no fixed catalog — you write plain prose. Wordings you can paste in as-is,
one per injection class, are in
[Starter snippets](/self-hosting/providers-and-auth#starter-snippets).

<Callout type="info">
  Not to be confused with an Organization's **Organization identity / context**
  field, which is framing rendered *early* in the prompt — see [Memory &
  context](/concepts/memory-and-context). Identity says *who the assistant is*;
  guardrails say *what it must not be tricked into doing*.
</Callout>
