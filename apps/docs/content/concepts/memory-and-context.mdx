# Memory & context

Two related ideas control what an **Agent** knows about _you_ and your past
activity, beyond the messages in the current Chat: **Memory** and **Context**.

## Memory

**Memory** is a running summary of your prior activity that an Agent can recall.
It's kept per person, per **Workspace**, and it is folded into the
[system prompt](/concepts/system-prompt) automatically — you don't put it in the
Agent's Instructions yourself.

**Why you'd use it:** so the assistant doesn't start from scratch every time.
With Memory, an Agent can carry forward what it learned about your preferences,
your projects, and earlier conversations — without you repeating yourself.

### Turning Memory on

Memory is a **Workspace-level** setting, not a per-Agent one. It is switched on
by choosing a **Memory Extraction Provider** in the Workspace form (an Org Admin
task); leaving it unset is what "Memory is off" means. Only Providers with a
memory-extraction model configured appear in that dropdown, so if it looks empty,
set one on the Provider first. A **Memory Embedding Provider** is a separate
choice, needed for semantic memory search.

<Callout type="warning">
  Granting an Agent the **memory** Tool set does not enable Memory. Without a
  Memory Extraction Provider on the Workspace, nothing is ever extracted, so
  there is nothing for the tools to find and nothing to inject — the Agent looks
  broken when the setting is simply off. The Tool set and the Workspace setting
  are two different switches, and Memory needs the Workspace one.
</Callout>

### What the model sees

Once Memory is on, the retrieved summaries are injected into **every** Chat turn
in that Workspace, for every Agent, whether or not the Agent has the memory Tool
set. It is not opt-in per Agent and there is no way to exclude one Agent from it.

The memory Tool set adds something different: the `memorySearch` and `memoryGet`
tools, which let the model look up older or more specific memories beyond the
summaries already in the prompt. Granting it widens what the model can reach;
withholding it does not hide the summaries.

## Context

**Context** is free-text notes _you_ write and attach for the assistant to read.
You'll find them under **Settings → Contexts**, at two levels:

- **Global Context** — notes that apply everywhere you work, and
- **Workspace Contexts** — notes specific to one Workspace.

Whatever you put there is rendered into the [system
prompt](/concepts/system-prompt), so it's a direct way to tell the assistant
standing facts: who you are, how you like answers formatted, what a project is
about. It reaches every Agent you use, so there's no need to repeat it in any
Agent's Instructions.

### Three different things are called Context

<Callout type="warning">
  Your Workspace Context and the Workspace's **Context** field are not the same
  thing, and mixing them up is easy because both end up in the prompt.

  Your Workspace Context is **yours**, written under **Settings → Contexts**, and
  nobody else's chats see it. The **Context** field on the Workspace settings form
  belongs to the **Workspace**, is written by whoever administers it, and reaches
  every Chat anyone runs there.

  So: put "I prefer terse answers with no preamble" in your own Context. Put "this
  Workspace supports the payments team; the service is called Ledger" in the
  Workspace's field. Writing the first one into the second inflicts your
  preferences on everyone.
</Callout>

The third is the model's own **Context window**: how many tokens a model can be
sent at once, which an Org Admin declares on the Provider's model entry because
no vendor publishes it in a form Platypus can read. It has nothing to do with
either of the two above — it is a capacity, not something you write. Where one is
declared, a Chat shows how much of it the last turn used; see [How full the
conversation is](/building-with-platypus/chat#how-full-the-conversation-is) and
[What each model entry
holds](/self-hosting/providers-and-auth#what-each-model-entry-holds).

**Memory vs. Context:** Memory is built up automatically from your activity;
Context is written deliberately by you. They work together — Memory remembers,
Context instructs.

## Organization identity

An **Organization** carries an optional free-text **identity / context** field,
set by an Org Admin. Whatever you write there is folded into the system prompt
**early** — as framing, alongside the Workspace context — for every chat across
the Organization.

Use it for standing facts about the organization itself: who you are, what you
do, house tone, standard terminology. It's the org-wide counterpart to the
per-Workspace Context above.

**This is framing, not a security control.** It shapes _who the assistant is_,
not _what it must refuse_. Because it's rendered early (where the model reads it
as setup, not as final orders), it is deliberately **not** the place for
injection defenses. Those belong in a Provider's **security guardrails**, which
render last — see [Providers & models](/concepts/providers#security-guardrails).
