# Sandboxes

## Sandbox

A **Sandbox** is an environment where an **Agent** can
run shell commands and work with files. It's registered in a **Workspace**, and
when it's available, the Agent gains shell and filesystem tools that operate
_inside_ that environment — not inside the Platypus backend itself.

**Why you'd use one:** lots of useful work involves actually executing
something — running a script, building a project, inspecting files. A Sandbox
runs that work in its own environment — a container, or a remote host you point
it at. How isolated that environment is depends on the backend; see [Sandbox
infrastructure](/self-hosting/sandbox).

Like an MCP, a Sandbox resolves to a **[Tool set](/concepts/tools)** at Chat-turn
time — the shell and filesystem tools it provides.

## Two switches, both required

Getting shell tools in front of an Agent takes two independent things, and
neither one alone does anything:

1. **The Workspace has a Sandbox** — one per Workspace, set up by an Org Admin
   under **Workspace settings → Sandbox**, whose backend is registered on this
   deployment (the Operator has to have listed its Plugin).
2. **The Agent is granted the Sandbox Tool set** — the **Sandbox** switch in the
   Agent form's **Tools** card.

<Callout type="warning">
  The half-configured case fails **quietly**. Grant the Tool set to an Agent in
  a Workspace with no Sandbox, and the turn gets zero shell tools, with no error
  in the UI and nothing in the backend log — yet the Agent is still told it has
  a Sandbox, so it may try to run a command and fail, or improvise around it.
  The same happens when the Sandbox names a backend whose Plugin isn't loaded,
  or when its config or credentials no longer validate; those two cases do log a
  warning. If an Agent won't run commands, open **Workspace settings → Sandbox**
  first: it reads **No sandbox configured** when there is none.
</Callout>

## Pluggable backends

The same Agent-facing tools can be powered by different backends. Platypus
ships **Local Docker** and **SSH (Remote Host)**; others come from Plugins. Which
backends a deployment offers is an Operator decision — see [Extending → Sandbox
backends](/extending/sandbox-backends).

## Default environment variables

A Sandbox can also carry **environment variables** that are merged into every
shell command it runs — API keys, or configuration a command needs. The values
are applied directly to the execution **without being sent through the model**,
so a value never appears in the conversation unless a command prints it. The
Agent is told the variable _names_ and asked not to echo them, but a command that
prints one — `echo $API_KEY`, a debug dump — hands the value to the model.

## Moving files in and out

Files move in and out of the Sandbox unaltered, so images, archives and other
binary files work, up to **25 MiB** each way. Their contents never pass through
the model.

- **Upload**: choose **+ → Upload to Sandbox** in the chat input. The file
  lands in the workspace root when you send the message — see [Uploading to the
  Sandbox](/building-with-platypus/chat#uploading-to-the-sandbox).
- **Download**: ask the Agent for a file as a download. Its `fsDownload` tool
  puts a **Download** button in the Chat. The file always downloads, and never
  opens in the browser.

Not every backend supports file transfer. When the Sandbox's backend can't take
uploads, the composer doesn't offer **Upload to Sandbox**; when it can't serve
downloads, the Agent doesn't get `fsDownload`. Local Docker and SSH support both
directions.

<Callout type="info">
  Setting up a Sandbox is an infrastructure task. See [Sandbox
  infrastructure](/self-hosting/sandbox) for how an Operator and Org Admin
  configure the available backends, and [what a Workspace Owner can
  change](/self-hosting/sandbox#who-can-configure-what).
</Callout>
