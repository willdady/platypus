# Model aliases are Provider-scoped marked strings

## Context

`agent.modelId` and `chat.modelId` each store a concrete model id as a plain string. Upgrading a model means editing every Agent and Chat that references the old id by hand. A Model alias lets a Provider name one of its `modelIds` entries so those references repoint at once. Originates from [#386](https://github.com/willdady/platypus/issues/386).

## Decision

A Model alias is **Provider-scoped only** — it does not span Providers. It is stored as a new optional field on the existing per-model config object inside `modelIds` (no new table, no new column on Agent/Chat/Provider).

Aliases apply to **`agent.modelId` and `chat.modelId` only** — the fields a User selects a Provider model through. The Provider's own pointer-settings (`taskModelId`, `memoryExtractionModelId`, `embeddingModelId`) are **out of scope and must hold a concrete id**; see Considered options.

An in-scope field stores either a concrete id or an alias reference, disambiguated by an explicit `alias:` prefix (e.g. `alias:default`) rather than a lookup-with-fallback scheme. The prefix lives on the **reference**, never the **definition**:

- `modelIds[].alias` stores the bare name (`default`). This field is unambiguous by construction, so carrying the prefix would be redundant and invite strip-before-compare bugs.
- `agent.modelId` / `chat.modelId` store `alias:default`. These are the only fields where a string could mean either thing, so they are the only ones that need marking.

Resolution strips the `alias:` prefix from the reference and matches the remainder against `modelIds[].alias`.

The prefix is **never user-visible**. It is a storage disambiguator, not user vocabulary: an Org Admin types `default` into an "Alias" field on the provider form, and model-select fields render `default` as the option label while submitting `alias:default` as the value.

## Considered options

- **Aliasing the Provider pointer-settings** (`taskModelId`, `memoryExtractionModelId`, `embeddingModelId`) — rejected, and the rejection is the load-bearing part of this ADR. The value of an alias is _many references, one repoint_; each of those three fields is referenced by exactly **one** row — the very Provider row that defines the alias — so aliasing them saves zero edits. Meanwhile `embeddingModelId` carries real danger: `handleEmbeddingConfigChange` decides whether to null every stored embedding by string-comparing the incoming `embeddingModelId` against the stored one, and the provider form gates its confirmation dialog on the same comparison. Repointing an alias leaves that string byte-identical, so **both** the invalidation and the warning would be skipped — leaving vectors from a superseded embedding model in place, either erroring on dimension mismatch or, worse, silently comparing two incompatible embedding spaces with no signal at all. Even a correct alias-aware fix would not help a user: repointing an embedding model also requires updating `embeddingDimensions` on that same Provider row, so the edit was never avoidable. Zero benefit, high cost. The prohibition is **schema-enforced** (the three fields reject an `alias:`-prefixed value), not conventional, so the hazard cannot return latently.
- **Cross-Provider (Workspace/Org-scoped) aliases** — rejected. An Agent already pins exactly one Provider via `providerId`; a cross-Provider alias would have to resolve which Provider too, reopening a question the Agent already answers. Cross-Provider model routing/fallback is a distinct feature with its own failure modes (mismatched credentials, provider outages) and is left for a separate design if ever needed.
- **`@` prefix** — rejected. Several real vendor model ids legitimately start with `@`, so it wouldn't be unambiguous.
- **Lookup-with-fallback (try alias match, else treat as literal id)** — rejected in favor of an explicit marker. An unmarked string is unreadable in isolation (e.g. looking directly at a database row) — you can't tell whether `"default"` is an alias or someone's literal model id without cross-referencing the Provider's `modelIds`. The `alias:` prefix makes every reference self-describing and resolution a deterministic prefix check, not a two-step lookup.
- **Giving an alias a stable identity of its own**, so references survive renaming — rejected. It would make every reference opaque (`alias:a7f3…`) and destroy the read-it-straight-from-the-database property that motivated the explicit marker in the first place. An alias's name _is_ its identity; see the orphaning consequence below.

## Consequences

- **Resolution failure is a hard error.** A reference that matches no `modelIds` entry fails the Chat turn visibly — same error class as a dangling literal id today. No silent fallback to another model. This remains the resolution-time contract, but de-migration (below) is what keeps the ordinary orphaning flow from ever reaching it; the hard error is the backstop for a reference that arrives some other way, such as an API client naming an alias that does not exist.
- **No reproducibility pinning.** Aliases always re-resolve on every Chat turn; repointing an alias changes behavior on the very next turn for every Agent/Chat using it. This matches existing behavior for literal ids — `chat.modelId` already has no per-turn pinning mechanism today, and no message currently records which concrete model actually produced it — so this introduces no new asymmetry.
- **The display rule is per-picker, not global.** Only the pickers whose field may hold an alias show one:

  | Picker                                                                  | An aliased entry displays | Submits          |
  | ----------------------------------------------------------------------- | ------------------------- | ---------------- |
  | Agent / Chat model                                                      | the alias (`flagship`)    | `alias:flagship` |
  | Provider `taskModelId` / `memoryExtractionModelId` / `embeddingModelId` | the concrete id (`gpt-4`) | `gpt-4`          |

  So one model can read as `flagship` in the Agent picker and `gpt-4` in the task-model picker on the same screen. That is correct rather than inconsistent — the fields genuinely differ in what they may store — and no hint text is added, since the provider form is where the Org Admin defined the alias.

- **Names form one flat namespace per Provider.** The union of every entry's `id` and every entry's `alias` must contain no duplicates. Because the `alias:` prefix is hidden in the UI, an alias named after a real model id would render a second, identical-looking option in the picker pointing somewhere else entirely (`alias:gpt-4` → `gpt-3` displayed as `gpt-4`, alongside the genuine `gpt-4`). Note this constraint is forced by the hidden-prefix choice, not by resolution: the prefix alone keeps resolution unambiguous. The stricter flat-namespace rule is preferred over merely requiring distinct display labels, since the looser rule still permits a misleading label when the colliding concrete id carries its own alias.
- **Alias name validation:** non-empty, non-whitespace, and may not itself begin with `alias:` (no `alias:alias:foo`). Surrounding whitespace is trimmed on input; comparison for the namespace rule is **case-insensitive**. An earlier draft of this ADR specified exact, case-sensitive comparison, reasoning that the concrete model ids sharing the namespace are themselves case-sensitive vendor strings; the maintainer ruled the other way before implementation, because a picker showing both `Fast` and `fast` reads as duplicated to a human, and the display name is the thing an alias exists to provide. Alias _resolution_ is case-insensitive to match, so a stored `alias:FLAGSHIP` still resolves — the namespace rule guarantees at most one candidate. Concrete ids continue to match exactly. Enforced with the namespace rule in a `.superRefine` on `modelIdsSchema`, after the existing `.transform` so it sees normalized objects — a whole-array invariant, so it cannot live on `modelConfigSchema`. The rule covers alias-vs-alias and alias-vs-id only: duplicate concrete ids remain legal at the schema and are collapsed by `dedupeModelConfigs` on the route, exactly as before aliases existed.
- **An unresolved reference is kept out of id-keyed code by the type system, not by review.** Every bug found while designing this was one shape: logic that answers "did the model change?" or "which entry is this?" by string-comparing a stored reference. Three instances surfaced (the Agent picker, the embedding guard, the frontend capability lookup), none by reasoning about the design and all by grepping for the shape — so manual auditing is not trusted to have been exhaustive. A nominal `ConcreteModelId` type is introduced, produced **only** by the resolver and **required** by every capability helper (`providerHasModel`, `passthroughFileTypesForModel`, `maxExtractedTextCharsForModel`, and the frontend's `getPassthroughFileTypes` / `classifyAttachment`). Passing a raw `agent.modelId` into any of them is then a compile error, and `pnpm typecheck` is already a CI gate. Storage types stay plain `string`: branding the reference side too would mean `z.string().brand<…>()` surviving both Zod and Drizzle row inference, which is real friction for no added guarantee.

  In implementation the brand was extended to `OpenedProvider.languageModel` / `embeddingModel` as well, which immediately surfaced a fourth instance the design audit had missed: sub-Agent turns resolve `subAgent.modelId` directly against their own Provider and never pass through the Chat-turn resolver, so an aliased sub-Agent would have sent `alias:flagship` to the vendor SDK. This is the mechanism working as intended, and is the reason the audit was not trusted. The Provider's three pointer-settings reach the SDK through a single deliberately long-named `pointerSettingModelId` helper — sound because the schema already rejects an alias in those fields, and greppable because it is the one hole in the brand. `apps/frontend` gained a `typecheck` script in the same change so the brand is enforced on the frontend capability helpers too, rather than only at `next build`.

- **Value and label diverge in the frontend for the first time.** `getModelIds` (`apps/frontend/lib/model-config.ts:43`) returns one string used as React key, option value, and visible label at `agent-form.tsx:643` and `model-selector-dialog.tsx:92`; aliases split these, so an options helper returning `{ value, label }` is needed. The composite `provider:<id>:<modelId>` select value needs no change — `agent-form.tsx` and `use-model-selection.ts` already parse it with a rest element and `join(":")`, so an `alias:`-prefixed value round-trips intact.
- **Aliasing a model that is already referenced concretely is safe at run time, but selection matching must be entry-based.** Adding an alias does not change the entry's `id`, and resolution keys on `id`, so every existing `agent.modelId` / `chat.modelId` holding the bare id keeps resolving to the same model — no migration, no backfill, no behavioural change to any running Chat turn. The UI is what breaks, silently and in two places, because both compare model strings for equality: the Agent form builds its option values from the model list, so a stored `gpt-4` matches no option once the entry is labelled `flagship` and the Select renders its "Select a model" placeholder over an Agent that is in fact configured; and the persisted chat selection is validated by membership against that same list, so it fails and falls through to the first Provider's first model — a different model entirely. The fix is to resolve **both** the stored reference and each option to a `modelIds` **entry** and match on the entry, not the string: a stored bare `gpt-4` selects the entry now labelled `flagship`, a stored `alias:flagship` selects the same entry, and an un-aliased entry still matches by `id`. A reference matching no entry at all keeps today's behaviour (the model was genuinely removed from the Provider).
- **References migrate from concrete to alias opportunistically, on save.** Because an option's value is the alias reference, entry-based matching means editing and saving an Agent that stored `gpt-4` writes `alias:flagship`. This is deliberate: once a model is aliased the picker no longer offers the concrete id, so "pin to exactly `gpt-4`" is not an expressible choice — an Org Admin adding the alias _is_ the declaration that the model should be referenced by name. Rejected the alternative of **backfilling every reference when an alias is created**: there, doing nothing is harmless because run time is unaffected, so the write would be cosmetic.
- **Orphaning an alias de-migrates its references instead of breaking them.** An alias has no identity apart from its name, so "renaming" one is indistinguishable from deleting it and creating another; the precise trigger is _an alias name that existed before this save no longer exists after it_, which covers rename, clearing the field, and deleting a model entry that carried an alias as one case. On that trigger, every affected reference is rewritten back to the entry's concrete id (`alias:flagship` → `gpt-4`), and the provider form reports what happened ("4 Agents repointed to `gpt-4`"). Without this, orphaning would hard-fail every affected Agent across every attached Workspace of a Shared Provider, discovered only when turns start failing. Note this _is_ a bulk reference rewrite triggered by a config edit — rejected above for alias creation — because the trade inverts: doing nothing here causes hard failures rather than leaving a cosmetic inconsistency. It also means the reference-count query deferred as a browsable "what's using this alias" view is needed after all, in this narrower reporting role. Two caveats: the rewrite mutates Agents owned by Workspace Owners as a side effect of an Org Admin editing a Provider, accepted because it moves in the safe direction of preserving the model each Agent already runs; and where the alias and its model entry are removed in the _same_ save there is no concrete id to fall back to, which is the pre-existing dangling-id case that keeps today's behavior.

## Amended by ADR-0043

The cross-Provider fallback this ADR left "for a separate design" is ADR-0043:
an optional **Fallback model** on an Agent, used only by Trigger runs and only
when the primary Provider is unavailable. Resolution failure is still a hard
error here; ADR-0043 never switches models because a reference failed to resolve.
