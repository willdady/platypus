# Agents are reachable over A2A, and Platypus ships no messaging Gateway

> State of the code today: no A2A endpoint, Agent Card, A2A token or `a2a`
> Principal exists. This ADR records the decision only. It moves to `accepted`
> in the pull request that builds the A2A server.

Platypus will not build the messaging Gateway that ADR-0015 decided on. Instead, an Owner can expose an Agent as an **A2A server** (A2A 1.0). Messaging Surfaces are reached through projects that already maintain Gateways (Hermes Agent, OpenClaw) and through other A2A clients (Jira Rovo, other agents), which call the Agent the same way. The Gateway was a separate stateful app with an adapter for each Surface. For a project with one maintainer that is a permanent cost, and it duplicates work those projects already do. A2A is the emerging standard for "a client talks to a remote agent", and the integration cost it puts on Platypus is a single protocol, not one per Surface. Platypus runs are **long-running**: a turn can take minutes to hours of tool calls and sandbox work. So the server is designed around asynchronous Tasks, not a reply on a single held request.

## Considered Options

- **Build the Gateway (ADR-0015).** Rejected. It means N Surface adapters, plus identity linking, conversation binding, a second deployable and an outbound event type, all owned by one maintainer, to reproduce what Hermes and OpenClaw already ship and maintain.
- **Expose Agents as an MCP server** (a `chat_with_<agent>` tool, using the MCP 2026-07-28 Tasks extension for long calls). Deferred, not rejected. A2A comes first because, as of 2026-07-28, MCP models one tool call, not a conversation: it has no context id, and protocol sessions were removed. An MCP Task tracks one long call and has nothing equivalent to an A2A context with multiple turns. MCP is still evolving and has far wider client reach than A2A, so an MCP surface is likely later. It would sit on the same Chat, token and Principal model described below.
- **One A2A endpoint for the Workspace, routed by A2A's `tenant` field.** Rejected. Not every client sends `tenant` (OpenClaw doesn't), and an Agent per URL is how A2A clients address agents.
- **Hold the request open until the run finishes** (blocking `SendMessage` as the only mode). Rejected. Runs outlive proxy, load-balancer and client timeouts, and a dropped connection would lose the result even though the run continues server-side.
- **General-purpose API keys.** Rejected again, as in ADR-0030. The grant is "converse with this Agent", not the API.
- **Platypus as an A2A client** (remote A2A agents appearing as tools, much like sub-agents). Not rejected, and a separate decision. Nothing here depends on it.
- **Proactive messages to a Surface** (the Agent starts a message in an existing conversation). Out of scope. Neither A2A nor MCP has an operation for a server to start a message in a conversation the client didn't just open. Push notifications only report on a Task the client started. Delivering an unprompted message is the job of a Gateway's own inbound webhook (Hermes `deliver`, OpenClaw `/hooks/agent`), which a Workspace Webhook can call today.

## Consequences

- **One A2A endpoint per opted-in Agent**, at `/a2a/agents/:agentId` with its Agent Card beside it. The path lives outside `/organizations/...` so an Operator can expose `/a2a/*` alone, as with `/hooks/*` (ADR-0030). JSON-RPC binding only. gRPC and HTTP+JSON are deferred until a client needs them.
- **Credentials are per-client bearer tokens on the Agent.** An Agent can hold several, one per caller (Hermes, Rovo, …), so revoking one leaves the others working, and logs and Chats show which caller acted. Token handling follows ADR-0030: the token is shown once, stored as a hash, and expires after a period the Owner chooses. Tokens are created and regenerated only in the UI and never enter a model's context. The Agent Card declares HTTP bearer. OAuth is deferred until a client needs it.
- **An Organization gate, off by default**, with the same shape as the Inbound Trigger gate (off, all Workspaces, or selected Workspaces), checked on every call. Rejections follow ADR-0030's uniform `404`: an unknown Agent, an Agent that isn't opted in, a bad token or a gated Workspace all look the same. That applies to the Agent Card too, so the card is served only with a valid token. A client that fetches the card anonymously is told nothing.
- **`contextId` is a Chat id.** A message without one creates a Chat bound to the Agent, and the new Chat's id is returned as the `contextId`. A message with one appends to that Chat's active leaf, through the same submit path as the web UI (ADR-0026). The Chat is an ordinary Chat. It appears in the Owner's Chat list, tagged with the token's name, and the Owner can read or continue it from the UI.
- **A Task is one run.** Its id is the turn's assistant message id, so it stays unique across turns in the same context. Task state comes from the run: `submitted` → `working` → `completed` / `failed` / `canceled`. `input-required` and `auth-required` are unused until runs can pause for a human.
- **Long-running first.** `SendMessage` always returns the Task once the run has started, never the finished result. A client asking to block gets the finished Task only if the run ends within a short server-side cap; otherwise it gets the Task still `working`. Clients then follow the run in one of three ways:
  - `GetTask`, polling. It is read from the database, so any backend instance answers.
  - `SendStreamingMessage` / `SubscribeToTask`, over SSE. Token-level events stream only on the connection that started the run. A resubscribe, or a subscription served by another instance, gets status and artifact events, not token deltas. Resumable token streams are #686's concern, not this ADR's.
  - **Push notifications** (`TaskPushNotificationConfig`). On every terminal state the backend POSTs the Task to the URL the client registered, with the credentials the client supplied. Delivery reuses the Webhook transport, including its SSRF guard and retries. For runs that take hours, this is the mode that doesn't depend on a held connection or a polling loop.
- **`CancelTask` cancels the run** on whichever instance holds it. That depends on #1237 (cross-instance run lock and cancel), which is a hard prerequisite, as are the busy check and `GetTask` consistency.
- **One run per context.** A message to a context whose run is still active is rejected with an A2A error carrying the active Task's id. The caller can follow that Task and send again when it finishes. Queueing or steering mid-run is #1109's concern.
- **A new Principal kind, `a2a`**: `{ kind: "a2a", tokenId, name, onBehalfOfUserId }`. The run acts as the Workspace Owner, as Trigger runs do, because the Owner issued the token. The Principal still records which caller started it, for logs and attribution. The run is not interactive. A2A carries no end-user identity: when Hermes relays a Telegram user, Platypus sees only the Hermes token.
- **Memory is opt-in per token, defaulting to off on both sides.** `includeMemories` mirrors the Trigger setting (the run's System prompt gets the Workspace's Memories block). A separate `extractMemories` setting decides whether these Chats feed memory extraction. The defaults are off because the caller isn't necessarily the Owner: a group-chat stranger reached through a Gateway shouldn't read the Owner's memories or write into them.
- **Parts.** Inbound: text and data parts. Data parts are rendered as labelled JSON, like Inbound Trigger inputs. Outbound: the final assistant text as a Task artifact. File parts in either direction are deferred until a client needs them. Inbound would reuse the composer upload path (ADR-0028), and outbound would offer sandbox downloads as signed URLs.
- **Supersedes ADR-0015** in full. ADR-0030's reference to the Gateway as the interactive path is replaced by this ADR. CONTEXT.md's Gateway vocabulary (Surface, Gateway adapter, Identity link, Conversation binding) and the ROADMAP Messaging Gateway section are withdrawn with it.
