# The system prompt is a core-owned ordered fragment list whose first entry is the Agent's Instructions

Platypus, not the Agent author, composes the system prompt for a run. `renderSystemPrompt` in `apps/backend/src/system-prompt.ts` maps a module-private ordered `FRAGMENTS` array over a single `SystemPromptContext`, drops every fragment that returns null or empty, and joins the survivors with a blank line. Twelve fragments exist today. The **first** is the Agent's **Instructions** — the only fragment a User authors. The **last** is the run Provider's security guardrails. The ten between are Platypus-owned: Agent identity on headless runs, Organization identity Context, Workspace, User, User Contexts, retrieved Memories, memory-tool prose, the Skills catalogue, the Sub-Agent catalogue, and Sandbox orientation. Instructions are an **input to** the system prompt, never the system prompt itself, and they cannot suppress, reorder, replace, or opt out of anything after them — the only way a fragment is absent is that the fragment's own emission condition was not met. Neither can a Plugin: `FRAGMENTS` is private to the module and `PluginContributions` (ADR-0013) exposes `toolSets` and `sandboxBackends` only. Order is load-bearing rather than incidental — Instructions lead on primacy, guardrails close on recency to strengthen injection resistance, and the Organization Context sits early, beside the Workspace Context, precisely so it reads as framing rather than as a security control. Originates from [#364](https://github.com/willdady/platypus/issues/364) and [#368](https://github.com/willdady/platypus/issues/368).

## Considered Options

- **The Agent's text _is_ the system prompt; Platypus appends nothing** (what the pre-rename field name claimed). Rejected: the Workspace id and the User id are load-bearing — tools require them as arguments — and the Skills and Sub-Agent catalogues are the only way the model learns what `loadSkill` and the `delegateTo*` tools can reach. Under this option every Agent author would hand-maintain ids and catalogues that Platypus already knows, and get them wrong as soon as a Skill was added.
- **Per-Agent opt-out — a suppression list or per-fragment flags.** Rejected: the fragments an author would most want to drop are exactly the ones that must not be droppable (security guardrails, the Workspace id, the Organization Context an Org Admin set for reach across every Agent), and the fragments that are genuinely situational already self-suppress on their own conditions — an Agent without the `sandbox` tool set gets no Sandbox block, an Agent with no Skills gets no Skills catalogue, and a Provider with no security text gets no security block. Opt-out would buy control over the wrong half of the list while making the composed prompt unpredictable per Agent.
- **Author-controlled ordering, or a prompt template with fragment placeholders.** Rejected: the primacy and recency positions are the mechanism, not decoration, and a template makes every future fragment a breaking change to every Agent that already has one. Core adding a thirteenth fragment must not require touching a single Agent row.
- **Plugin-contributed fragments.** Rejected. Fragment composition is core's, in the same sense that the five-tool Sandbox core is core's (ADR-0002): a Plugin extends what an Agent can _do_, not what the model is _told_. A Plugin already influences the prompt at one remove, through the model-facing descriptions of the Tools it contributes, and that is the sanctioned surface. This is a decision about the current fragment list, not a permanent bar on the capability — see the append-only door in Consequences.
- **Route sub-agents through `renderSystemPrompt` so that delegation has no special-case prompt semantics.** Not adopted here, and named rather than left implicit: a sub-agent today receives its Instructions plus guardrails and none of the other ten fragments (see Consequences). Unifying the two paths would change what is sent to the model, which #364 put out of scope; this ADR records the split as it stands so that a future decision to close it is a deliberate one.
- **Surface the composed prompt in the product as an editable value.** Rejected, and this is the failure mode the contract exists to prevent: a composed prompt written back into the field that backs User input re-composes on the next turn and compounds every turn — the live defect fixed in [#373](https://github.com/willdady/platypus/pull/373). The composite is **derived per turn and never persisted as an input**. A read-only viewer remains possible (the renderer is pure) and was deferred, not refused.

## Consequences

- **The ordered list, with the condition under which each fragment appears.** Source of truth is `FRAGMENTS` in `apps/backend/src/system-prompt.ts`; this ADR fixes the shape, not the wording.
  1. **Instructions** — always. The Agent's `instructions`, or `fallbackInstructions` for a Chat with no Agent; falls back to `"You are a helpful AI assistant."` when both are empty or whitespace. This fragment is never absent, so the composed prompt always opens with the User's voice or Platypus's stand-in for it.
  2. **Agent identity** — headless runs with an Agent only. Names the Agent and prints its id, which tools require in order to assign work to it.
  3. **Organization identity Context** — when `organization.identityContext` is non-empty.
  4. **Workspace** — always. The Workspace id preamble is unconditional; a `<workspace>` block is added when the Workspace has Context.
  5. **User** — always, worded differently per run mode: the current user in an interactive run, an on-behalf-of owner with no live participant in a headless one.
  6. **User Contexts** — when the User has a global Context, a per-Workspace Context, or both.
  7. **Memories** — when retrieved Memories format to a non-empty block.
  8. **Memory-tool prose** — when the Agent has the `memory` tool set, worded differently according to whether a Memories block preceded it.
  9. **Skills catalogue** — when the Agent has Skills.
  10. **Sub-Agent catalogue** — when the Agent has Sub-Agents.
  11. **Sandbox orientation** — when the Agent has the `sandbox` tool set; names the Workspace-default env keys when any are set (keys only, per ADR-0004).
  12. **Security guardrails** — when the run Provider has non-empty `securityGuardrails`.
- **Non-suppressibility of guardrails is enforced in two independent places, not one.** `securityFragment` renders last in `renderSystemPrompt`, and `createSubAgentTool` in `apps/backend/src/tools/sub-agent.ts` appends the block itself, because **sub-agents never call `renderSystemPrompt`**. Identical wording across both paths comes from `renderSecurityGuardrails`, which lives alone in the leaf module `apps/backend/src/security-prompt.ts` for that reason and to avoid a circular import. Anyone changing the guarantee must change both call sites; changing only the renderer leaves every sub-agent unguarded.
- **Sub-agents are the stated exception to uniform composition.** A sub-agent gets its Instructions — or, when it has none, a canned "you are a specialized sub-agent named X" line — plus its **own** resolved Provider's guardrails, appended to whichever of the two applies so that an Instructions-less sub-agent cannot slip the guardrails. It gets none of the other ten fragments: no Workspace id, no User identity, no Organization Context, no Sandbox orientation. That is the current behaviour rather than a target state, and closing the gap is separate work.
- **A Plugin cannot contribute a fragment.** `FRAGMENTS` is a private const, and the Extension points of ADR-0013 do not include one for the prompt. Should a fragment Extension point ever be added it is core-owned and additive in the ADR-0013 sense: core fixes the slot and its position, and the invariants recorded here survive it — Instructions first, guardrails last, no suppression and no reordering of what core owns. A Plugin would fill a slot; it would never define one.
- **The two tool-set-keyed fragments key on core tool set ids** (`memory`, `sandbox`), so a Plugin Tool set does not light one up. A Plugin that wanted orientation prose of its own would be asking for the Extension point above; today it puts that guidance in its Tool descriptions.
- **Adding, removing or reordering a fragment is a core change with no per-Agent migration**, because no Agent row references the list. The cost is the other side of the same coin: a new fragment lands in every Agent's prompt at once, so it must be worth spending everyone's context on, and the renderer's ordering snapshots in `apps/backend/src/system-prompt.test.ts` are the regression guard for position.
- **The rename to Instructions follows from this contract rather than motivating it.** Because the User's text is one fragment of twelve, a field labelled "System prompt" misdescribes it; the field, the wire contract, the shared schemas, and the `agent`/`chat` columns are all `instructions`. Names that genuinely denote the composite keep saying system prompt — the renderer module, `renderSystemPrompt`, `SystemPromptContext`, and `ChatTurn["stream"].system` — and that split is the contract made visible in the code.
- **Composition happens once per turn, at one call site**: `prepareChatTurn` in `apps/backend/src/services/chat-execution.ts` calls `renderSystemPrompt(promptCtx)` directly. The renderer is a pure function of `SystemPromptContext`, which is what makes a future read-only "what will the model receive" view cheap.
