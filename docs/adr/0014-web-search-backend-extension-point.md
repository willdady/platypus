# Web-search backends are a fourth Extension point routed through the search toggle

Platypus gains a fourth core-owned Extension point — a **Web-search backend** — that fills the request-gated "web search" chat toggle for Providers without working native search (self-hosted OpenAI-compatible servers: vLLM, LiteLLM, SGLang…). A Web-search backend is a Plugin Contribution (ADR-0013) that supplies **executors** for a small, fixed pair of ephemeral tools — a mandatory `web_search` and an optional `read_url`. **Core**, not the backend, builds the `Tool` objects around those executors: core owns the input schemas, the model-facing descriptions, pagination, truncation, the per-call timeout, the error contract, and an egress guard on model-supplied URLs. The tools are injected **only when the toggle is on**, exactly like today's native provider search, and gone when it is off. Selection is **per-Provider** (a three-valued `searchSource` column), mirroring how native search is already resolved per-Provider; the backend's config/credentials live in deploy-time Plugin config (ADR-0013), not on the Provider row. This lets a self-hosted deployment get first-class web search + page reading — backed by whatever the Operator runs (e.g. SearXNG for search, a browser service for reading) — without baking vendor specifics into core and without the always-on tool-schema bloat of wiring those services as MCP servers. Originates from [#329](https://github.com/willdady/platypus/issues/329).

## Considered Options

### Shape of the Extension point

- **A single Provider-config field (hardcode one blessed search URL in the OpenAI-compatible branch).** Rejected: lightweight (one field, one branch) but loses swappability — every new backend (Brave, Tavily, a different self-hosted stack) is another core change, and it bakes one vendor's specifics into core. Sandbox backends (ADR-0001/0013) already set the pluggable precedent for a "swappable, deployment-chosen capability"; a config field is the less principled shape given that precedent exists.
- **Connect SearXNG / a browser service as MCP servers.** Rejected as the sanctioned path: works today with no core change, but MCP tools are **always-on** — injected into the tool schema every turn regardless of the toggle — which is the tool-schema bloat this point exists to avoid, and it has no tie-in to the request-gated toggle. MCP remains valid for anyone who just wants to wire a search service in without core support.
- **An always-on Plugin Tool set.** Rejected: minimises tool count vs full MCP but is still always-on and still cannot ride the ephemeral toggle — the defining trait of this capability.
- **Selection per-Workspace (mirror sandbox backends exactly).** Rejected in favour of per-Provider: native search is already resolved per-Provider, and a Web-search backend is precisely a _fallback for a Provider that lacks native search_, so it belongs next to the `nativeSearchEnabled` knob. Per-Workspace would split the "can this Provider search?" decision across two rows, forcing the toggle-visibility gate to fetch Workspace state. Per-Provider keeps that gate a pure function of the Provider. (The backend's config/credentials are deployment-wide in Plugin config regardless, so per-Workspace's "configure once" appeal is weaker than it looks.)
- **Backend contributes its own arbitrary named tool set.** Rejected: the Extension point defines **exactly** `web_search` and `read_url` and only those — no backend-invented tools. This is the ADR-0002 "fixed core" philosophy applied to the toggle slot, so an Agent prompt is not coupled to which backend an Operator configured.
- **Both tools mandatory.** Rejected: `read_url` is **optional**. A search-only Operator (SearXNG, no browser service) supplies just `web_search`; when `read_url` is absent the model only gets search that turn. Only `web_search` is mandatory — a Web-search backend that cannot search is meaningless.
- **Two independently-selected backends (a search slot and a read slot).** Rejected: more flexible but pushes selection from one id to a pair of slots. One backend wraps both services (their split is its internal detail), preserving the single per-Provider selection id.
- **Native-search-first resolution (`native ?? webBackend`, as the originating issue proposed).** Rejected: the OpenAI-compatible branch of `openProvider` returns a (dead) OpenAI-hosted `web_search` even for a vLLM endpoint that cannot service it, so a native-first `??` short-circuits and the configured backend is **never reached** — on exactly the Provider this feature targets. Resolution is therefore **explicit-plugin-first**: if a `webBackend` is set, use it; native search is the fallback. Explicit Operator selection beats implicit capability, and this needs no change to the existing native-search wiring.

### The tool contract

- **The backend supplies finished `Tool` objects (a `createTools(ctx, plugin?)` factory, as first proposed here).** Rejected in favour of `createExecutors`. The decisive reason is **enforceability, not swap-safety**: if the backend owns the `Tool`, core never sees the model-supplied URL, so there is nowhere to put the egress guard below, and every backend author independently reimplements truncation, timeouts, and error handling — get truncation wrong once and a multi-hundred-kilobyte search response lands in the context window. A secondary benefit is a stable model-facing signature: backend A's `web_search({ query })` and backend B's `web_search({ query, count, region })` would otherwise present different interfaces, so an Agent prompt naming a backend-specific param silently breaks when the Operator swaps backends or the Agent moves deployments. That benefit is real but modest, and Platypus does **not** hold this invariant elsewhere — Google's native search registers as `google_search`, and the Anthropic/OpenAI hosted tools have entirely different shapes, so the model-facing search surface already varies by Provider today. The cost accepted: web backends become a third factory shape in the SDK, alongside tool sets returning `Tool`s and sandbox backends returning an adapter.
- **A thin `read_url({ url })` returning `Promise<string>`.** Rejected: strictly weaker than the `fetchUrl` tool core already ships. It loses pagination (`fetchUrl` returns the first slice plus a `next_start_index` the model passes back, so a long internal wiki page stays readable to the end — the primary intranet case), loses the post-redirect final URL the model needs in order to cite where it actually landed, and cannot distinguish "here is the page" from "that fetch failed" when success is also a bare string. The fixed schema is therefore `read_url({ url, max_length?, start_index? })` with a structured return.
- **Executors return rendered markdown / free-form text.** Rejected: simpler for a backend author and lets each upstream present its best output, but core can then neither cap result counts nor lift citations into the UI, and prompts vary by backend. `web_search` returns `{ query, results: [{ title, url, snippet? }], answer? }` — the optional `answer` is an escape hatch for upstreams with an answer box (Brave, Tavily) so that content is not simply discarded.
- **Backends honour `start_index` / `max_length` themselves.** Rejected: executors return full content and **core** slices, so truncation is genuinely centralised and a backend stays a thin upstream call.
- **A global `PLATYPUS_WEB_TIMEOUT_MS` env var for the per-call timeout.** Rejected on two counts. It reintroduces the bespoke-env-var pattern deliberately migrated away from when `FETCH_TOOL_IGNORE_ROBOTS_TXT` became `@platypus/web-fetch` plugin config (ADR-0013's "one config namespace"). And one global number cannot serve both a LAN metasearch that should answer in ~2s and a headless-browser service that legitimately needs 60 — it makes the first hang far too long on a dead host and cuts the second off mid-render. Instead the **contribution declares `timeoutMs`** (its author knows their upstream), core defaults to 30000 when absent and refuses anything above a hard ceiling so a backend cannot pin a turn open indefinitely. An Operator override, if a backend wants to offer one, rides that plugin's own deploy-time config.
- **Per-contribution `configSchema` / `credentialsSchema` (as first proposed here).** Dropped for v1. On a sandbox backend those schemas validate real per-Workspace jsonb columns before `create()` runs; a web backend has no such row, so they would parse nothing. The asymmetry is principled — **the schema lives where the row lives**. A backend's API key and endpoint ride the **plugin-level** `configSchema`/`credentialsSchema` via `PLATYPUS_PLUGIN_CONFIG`, boot-validated fail-loud and injected into `createExecutors` as `plugin.credentials`; that is stronger than a per-contribution schema, which would not be consulted until a turn actually ran. The cost accepted: one key and one endpoint per **deployment**, so an Operator cannot point Provider A at `searx.internal` and Provider B at `searx.dmz`, nor bill two teams to two Brave keys. Re-adding the schemas plus a per-Provider config column later is append-only.
- **camelCase tool names (`webSearch` / `readUrl`) for consistency with every other Platypus-authored tool** (`fetchUrl`, `fsRead`, `fsWrite`, `fsEdit`, `fsList`, `shellExec`, `listSandboxes`). Rejected: `web_search` / `read_url` stay snake_case as a **deliberate, documented exception**. These fill the slot provider-native search occupies, where the vocabulary is already `web_search`, so an Agent prompt saying "use `web_search` to check current prices" reads correctly on Anthropic, OpenAI, and a plugin backend alike — imperfect, since Google's is `google_search`, but the only cross-path consistency available. Models also carry strong priors on `web_search` specifically from the OpenAI and Anthropic hosted tools. The cost is a permanent casing split in the tool namespace; recording it here is what keeps it a choice rather than drift.

### Egress from `read_url`

- **Silence on SSRF (the first draft of this ADR).** Rejected: `read_url` fetches a **model-supplied** URL in-process with no isolation (ADR-0013), so an unguarded implementation reaches cloud-metadata endpoints, loopback services, and internal hosts on a prompt-injected model's say-so.
- **Textbook default-deny of all private ranges.** Rejected: this Extension point exists for self-hosted and intranet deployments, so blanket-blocking RFC-1918 would break reading the internal wiki, which is the point of the feature. The posture is therefore **inverted**: block loopback (`127.0.0.0/8`, `::1`), link-local (`169.254.0.0/16`, `fe80::/10`), `100.64.0.0/10` (Alibaba's metadata service lives at `100.100.100.200`, which is CGNAT, not link-local), and any scheme other than `http`/`https`; **allow** RFC-1918 by default, with an Operator flip to deny for internet-facing deployments. Loopback is blocked despite the plausible bare-metal case of internal docs on `localhost:8080`, because loopback is also where Platypus's own API and Postgres listen.
- **String / regex matching on the URL.** Rejected as ineffective: `http://metadata.google.internal/`, `http://2852039166/`, `http://[::ffff:a9fe:a9fe]/`, and `http://169-254-169-254.nip.io/` all reach `169.254.169.254` while looking innocent to a pattern match. Core **resolves the hostname and rejects if any resolved address falls in a blocked range**.
- **An SDK `safeFetch` helper that re-checks every redirect hop, which backends are documented to use.** Rejected for v1: it is **advisory only** — plugins run in-process, so a backend author calling bare `fetch()` silently opts out and core cannot prevent that — and it adds SDK weight for a guarantee it cannot make. Core does a **pre-flight check only**. The accepted limitation, stated rather than implied: a backend whose HTTP client follows a 302 into a blocked range does so unobserved by core.
- **Treating a malicious backend as the threat.** Rejected as the frame. A plugin already has `process.env`, the database credentials, and unrestricted network egress (ADR-0013) — it does not need `read_url` to reach a metadata service. The guard defends against a **prompt-injected model** talking a well-behaved backend into fetching something internal, which is why partial enforcement is worth having rather than theatre.
- **Guarding `read_url` only, leaving `@platypus/web-fetch` as-is.** Rejected: `fetchUrl` performs the same class of fetch with no protection whatsoever, and is arguably the easier target since once attached to an Agent it needs no toggle and no Provider configuration. Closing the hole in one tool while leaving it open in another that does the same job is indefensible. **One shared core guard covers both.** Two consequences accepted: it is a behaviour change to a shipped tool, so it lands as a standalone `fix` with its own release note rather than buried in this feature; and its config knob sits at **core level**, a deliberate exception to "plugin knobs live in plugin config" now that the guard governs two tools in different plugins.

### Overlap with `@platypus/web-fetch`

- **Supersede or deprecate the `web-fetch` Tool set in favour of `read_url`.** Rejected: they **coexist**. `read_url` is ephemeral and backend-required; `fetchUrl` is always-on once attached and needs no Provider configuration. Folding them would mean either deprecating a shipped Tool set that Agents reference by id, or making an always-on tool depend on a Provider-level backend selection — both worse than a little redundancy, and both outside what #329 asked for.
- **Core auto-supplies `read_url` (reusing the `fetchUrl` implementation) when the backend omits it.** Rejected, tempting though it is — it would give search-only Operators page reading for free from code core already has. The blocker is **consent**: `@platypus/web-fetch` is deliberately excluded from the always-on core set because it is deny-worthy egress, so an Operator who left it out of `PLATYPUS_PLUGINS` has explicitly refused outbound fetching, and a core-default `read_url` would hand it back through another door. Append-only, so it can be revisited.
- **`read_url` honours robots.txt for parity with `fetchUrl`.** Rejected: robots.txt belongs to **`@platypus/web-fetch`'s own configuration surface**, not to core's tool contract — a backend author who needs it exposes an equivalent flag in their plugin's config. Forcing it into core would also drag `ignoreRobotsTxt` back out of plugin config and up to core level, a second migration of a flag that has already moved once and a breaking config change for anyone who set it. The accepted consequence: on a Provider whose Agent also has `web-fetch` attached, two page-readers sit in the same tool list and whichever the model reaches for decides whether robots.txt applies.

### Presenting results

- **Render plugin search results as a generic tool-result block.** Rejected: native search results surface as **Sources pills**, because a provider-executed search returns citations that the AI SDK turns into `source-url` message parts. A plugin backend's `web_search` is client-executed, so its output would otherwise render as a raw collapsible blob — the same toggle giving citations on Anthropic and JSON on a self-hosted vLLM box. Core owns the result shape, so the frontend reads it and feeds the existing `<Sources>` row; this ships **with** the feature rather than as a follow-up.

## Consequences

- **New Contribution type.** `packages/plugin-sdk` gains an optional `webBackends?: WebBackendContribution[]` key on `PluginContributions` (append-only, minor API bump per ADR-0013 — disturbs no existing Plugin). A `WebBackendContribution` carries a `backend` discriminator (auto-namespaced for third parties, flat for core, per ADR-0013), a display `name`, an optional `timeoutMs`, and a `createExecutors(ctx, plugin?)` factory. No per-contribution `configSchema` / `credentialsSchema`.
- **Executor contract.** `createExecutors` returns `{ web_search(input, options), read_url?(input, options) }` — plain async functions, not `Tool`s. `options` carries `{ signal }` and is appended, so a single-argument executor is still valid (see the timeout decision below). `web_search` resolves `{ query, results: [{ title, url, snippet? }], answer? }`; `read_url` resolves the page's full content plus its post-redirect URL. Backends do not paginate, truncate, time out, or format. The `query` a backend resolves is **ignored**: core echoes the model's own query into the Tool result, so a backend cannot substitute the text a reader sees above its results. It stays in the shape for symmetry with the model-facing return, and the SDK type says so.
- **Core-owned Tool construction.** Core builds the `Tool` objects: fixed input schemas (`web_search({ query })`, `read_url({ url, max_length?, start_index? })`), fixed model-facing descriptions, result-count capping and snippet truncation for search, `max_length`/`start_index` slicing plus a `next_start_index` continuation hint for reads, the per-call timeout from `timeoutMs` (default 30000, hard-capped), and a string/structured error contract so a backend throw does not surface as an AI-SDK tool error.

- **The model-facing failure text is fixed, and the cause is withheld from it.** A throw or a timeout returns text naming only the tool and the timeout value; the cause goes to the log line instead. Not tidiness — a hosted search API's error message routinely embeds the URL it called, and that URL routinely carries the Operator's API key as a query parameter, so passing an upstream message through would hand a credential to the model and persist it in the Chat transcript. The cost, stated because it is real: a backend author cannot improve what the model is told about their failure, and diagnosis is a log-reading exercise rather than something visible in the turn.

- **The timeout is two additive windows. ~~It abandons rather than cancels.~~ Superseded: whether it cancels is now the backend's choice.** `timeoutMs` bounds `createExecutors` **and** each executor call it returns, so the worst case a turn spends inside one backend is `(1 + calls) × timeoutMs` — 240s for a single search at the 120s ceiling. Bounded, which is the property the ceiling exists to protect, but not the single window "per-call timeout" implies.

  The original position, kept because the amendment below has to answer it: ~~The v1 executor contract also carries no `AbortSignal`: the loser of the race is dropped, not cancelled, so a hung upstream call keeps running until its own socket timeout. What is guaranteed is that the **turn** is not pinned open, not that work stops. Adding cancellation is append-only and belongs with the same PR that adds a teardown hook to both Extension points.~~ That pairing is what shipped — the teardown decision below is the same change — and the guarantee it named is unchanged: it is still a race, so a backend that ignores the signal is bounded exactly as before.

  Each executor call now receives `{ signal }` as an appended second argument, and the signal core hands over is the **combination** of the call's deadline and the caller's own abort — so an executor that forwards it stops its upstream work when the User cancels _or_ when the deadline passes. A backend that ignores it keeps the original behaviour exactly: the loser of the race is dropped, not cancelled, and a hung upstream call runs until its own socket timeout. That is why the timeout is still a **race** and not a bare signal — the guarantee that the **turn** is not pinned open cannot rest on a Contribution's cooperation. `createExecutors` itself is called with no caller signal; wiring the prepare phase's abort into the factory is a separate decision.

  The parameter is appended and optional to read, so an existing single-argument executor is unaffected — append-only within the major (ADR-0013), no `PLUGIN_API_VERSION` bump. The cost, stated: `AbortSignal` is a platform global the SDK does not declare, so a Plugin whose `tsconfig` has `"lib": ["esnext"]` and no `@types/node` fails to compile against the new types until it adds one.

- **Core-owned enforcement constants.** The bounds above are named constants in core, not inline literals, and the full set is fixed here because each is a decision a backend author and an Operator can observe. Backends never truncate: they return everything and core cuts, so getting truncation wrong once cannot drop a multi-hundred-kilobyte response into a context window.

- **Page size is a separate lever from the content cap, and is clamped rather than validated.** The two used to share `MAX_READ_URL_CONTENT_CHARS`, inherited from `fetchUrl`, which made the "bounds context" claim only half true: core held at most 1M chars and a single `max_length: 1_000_000` still put all of them (~250k tokens) into the window in one call. Core owns this Tool outright, so the levers need not share a number — the cap bounds what core holds **across** a paginated read, the slice bounds any **one** page of it. Enforcement is a clamp in the executor path and **not** a lower bound on the input schema, which still mirrors `fetchUrl` byte-for-byte: a lower schema bound would reject a model that learned `fetchUrl`'s ceiling as an AI-SDK input-validation error — the same failure mode a `url` length cap was reverted for. Clamping needs no error path, because the page simply comes back shorter and `next_start_index` already says there is more. Consequence to state: a 1M-character page is one `fetchUrl` call and ten `read_url` calls, while the pagination **contract** — defaults, `next_start_index`, the hint text — stays byte-identical.

- **Observability is a defined record, with one deliberate exception.** Every executor call emits one outcome record: `{ backend, plugin, tool, durationMs, outcome }`, `outcome ∈ ok | timeout | blocked | error | cancelled`, at `debug` for `ok` **and for `cancelled`**, `warn` otherwise. `cancelled` sits with `ok` rather than with the failures because a User pressing stop is the most ordinary way a long search ends, not a fault — warning on it would make healthy traffic the noisiest thing in the log and hide the outcomes that _are_ faults. It reuses the existing model-facing failure text rather than adding a third string: in practice the model never reads it, because the turn that would have read it is the turn being torn down. Queries and URLs are user content and can carry sensitive terms, so they stay off default-level lines — **except** on the two paths that cannot be diagnosed without them: an egress block carries the `url` and the policy `reason` on the record itself, and a content-cap hit is warned separately with the `url` and the length, since the call it happened on is an `ok` one whose own record stays at `debug`. Only the block was folded: it previously emitted this record **and** a second, `fetchUrl`-shaped warn line carrying the same reason, and one structured record per call is easier to consume. Two things the fold must not cost: the **message**, which is derived from the outcome so that a block reads as the policy event it is (byte-identical to `fetchUrl`'s, so one Operator alert keys on one string across both tools that fetch a model-supplied URL) rather than as an executor failure the executor was never called for; and the meaning of **`durationMs`**, which is therefore "time spent in this call so far" — on the `blocked` path, the egress guard's DNS resolution, since that is all that ran.

- **~~No teardown hook, by design.~~ Superseded: an optional per-turn closer registrar, on both Extension points.** The original decision, kept because its reasoning is what the amendment has to answer: `createExecutors` runs once per turn and whatever it opens was dropped when the turn ended — matching sandbox adapters, which are instantiated per turn and discarded, and ADR-0013's in-process posture. A backend needing a real lifecycle (a browser pool, a keep-alive connection) was named as the trigger to add teardown to **both** Extension points at once rather than making Web-search backends the only Contribution shape with a lifetime.

  **What shipped.** An optional `registerCloser?: (close) => void` on the runtime context of the two Extension points whose contribution is resolved **per Chat turn**: Web-search backends (`WebBackendContext`) and Tool sets (`ToolSetContext`). Registered closers feed the Tool session's existing closer list, so they run from the one `dispose` a turn already hands its caller — on a normal finish and on an abort alike. Deduped by identity **within a session**, so what collapses is one turn reaching the same teardown twice; across turns there is nothing to dedupe against, and a Contribution that registers a process-wide resource has it closed at the end of the first turn that registered it. Each closer is bounded by a core-owned `CLOSER_TIMEOUT_MS` (5s) and they run sequentially; a closer that throws or outruns its ceiling is logged at `warn` against its plugin — the level the sibling degrade paths use, because an unreleased connection is worth an Operator's attention and never worth paging for — and the rest still run. The ceiling exists because the run's `onTerminate` awaits `dispose` **before** the terminal write, so a hung closer delays the last thing a reader is waiting for. Side effect worth recording: MCP `client.close()` now goes through the same path, which bounds a hanging MCP close that previously stalled a run's finish indefinitely.

  Two limits of that ceiling, recorded rather than fixed. **It bounds a closer, not a teardown:** the ceiling is per closer on a sequential loop, so the delay before the terminal write is `closers × 5s`, which on an Agent with several MCP servers and a delegate or two is tens of seconds — the very symptom the ceiling was chosen against. Bounding `dispose` as a whole (a wall clock the loop checks, or one deadline over `Promise.allSettled`) is the shape that would deliver the stated property, and is deferred rather than dismissed. **A late registration is closed immediately, not awaited:** a closer handed over after `dispose` already ran is fire-and-forget, so it can still be running after the terminal write. That matches how a nested session opened during an abort is already handled, and it is the reason the property above is "teardown starts before the terminal write" rather than "finishes before it".

  Sandbox adapters are deliberately **not** folded in. A Sandbox adapter already has `destroy`, and its lifetime is the **Workspace's**, not the turn's — folding it into a per-turn registrar would redefine that contract rather than reuse this one. "Both Extension points" therefore means the two with per-turn contribution lifetime.

  The member is **optional**, and must stay so: a manifest declares a _major_ `apiVersion` only, so a Plugin cannot require a core new enough to have it, and on an older core it is genuinely absent. An unguarded `ctx.registerCloser!(...)` throws out of the factory, which costs the turn that Contribution's tools — the same degrade-with-a-warn path a throwing factory already took.

  **On the trigger this ADR named.** The stated trigger — "a backend needing a real lifecycle" — was **unobservable from a repository that ships no backend of its own**: every Contribution filling this point is authored out of tree, so core would never see the browser pool that was supposed to prompt the change. The decision was taken instead on the contract's cost to out-of-tree authors, which _is_ observable from here: an optional member on a context, with no new disposal mechanism and no API-major bump. Recorded because the shape of the original deferral, left as written, would defer the next contract gap the same way — behind a signal core cannot receive.

- **Egress guard.** A core guard resolves the hostname of every model-supplied URL and rejects any that resolves into loopback, link-local, `100.64.0.0/10`, or a non-`http(s)` scheme; RFC-1918 is allowed by default and deniable by Operator config at core level. It is a **pre-flight check only** — redirects followed inside a backend are unobserved. The same guard covers `@platypus/web-fetch`'s `fetchUrl`, which ships as a standalone `fix` ahead of this feature since it changes existing behaviour.
- **Backend context.** `WebBackendContext = { orgId, workspaceId, userId, registerCloser? }`, mirroring `SandboxContext` on the data it carries. `registerCloser` is the one capability on it — see the teardown decision below; everything else is a value to read. No `userEmail`, no signed token; a plain in-process call. `userEmail` (PII) is deferred to a separate enhancement if a backend genuinely needs per-user upstream identity — append-only, and it would then apply to `SandboxContext` too, keeping the two shapes uniform. A backend that wants to attribute to its _own_ upstream forwards identity as its own implementation detail, using its own Plugin credentials.
- **Registry & loader.** A `webBackends` registry with the same id-namespacing and boot-time collision handling as sandbox backends; the loader drives registration from the manifest (Plugin authors never call the internal registrar). Boot posture is fail-loud, runtime resolution graceful — a Provider pointing at a since-disabled backend degrades to no tools that turn, as any absent backend does today.
- **Selection.** A single three-valued `searchSource` column on the Provider row (`"none"` | `"native"` | a Web-search backend's `backend` discriminator), resolved against the registry at turn time. Config/credentials come from deploy-time Plugin config keyed by plugin name (ADR-0013), not the Provider row — so a backend's key and endpoint are deployment-wide. The stored value is bounded at **200 characters** — it is free text reaching a log line on every searching turn, and 200 is far above a namespaced plugin id — and `""` normalises to `"none"` at the schema boundary, so the column holds one representation of "no search" rather than two. It is **not** validated against the registry there: the registry is a backend-runtime concern, and a stale id degrades to no search tools plus a warn-log rather than blocking the form.

  `searchSource` replaces an earlier two-field shape (a `nativeSearchEnabled` switch plus a nullable `webBackend` column) that shipped first and was collapsed once both were in production use. That shape put one decision — "which of no-search / this provider's own tool / a plugin backend serves this turn" — behind two controls that could disagree: the switch's name predated Web-search backends and, in practice, gated both paths at once, so disabling it to turn off a native tool that never worked also silently killed a plugin backend selected later. One field with one precedence list removes that failure mode; there is no longer a state where two stored values contradict each other.

  **The pre-collapse shape is not accepted on the Provider API**, and no compatibility window maps it onto `searchSource`. One shipped briefly and was removed before this ADR was accepted: the Provider routes authenticate with a better-auth session cookie only — no bearer, api-key or JWT plugin is configured, and no middleware reads an `Authorization` header for them — and there is no OpenAPI document, no API reference for operators, and no published client. The backend and frontend are built from one commit under one tag and released as a pair, so the API's only writer is the Provider form shipped alongside it, which always sends `searchSource`. A window with no caller able to reach it is a second encoding of the decision this collapse exists to delete. The old columns are retained for one release for the separate, real reason recorded below: a backfill must not read a column its own migration drops.

- **Turn-time resolution (explicit-plugin-first).** When the toggle is on for a turn: `searchSource: "none"` (or absent) serves nothing; a value naming a Web-search backend serves that backend's executors, ahead of native search; `searchSource: "native"` serves the provider's own tool if it has one. Tools remain ephemeral and toggle-gated.
- **Capability gate.** A positive `providerHasNativeSearch(provider)` predicate — a pure function of `providerType` + `apiMode` (Anthropic, Google, OpenRouter, and OpenAI not in chat-completions mode → yes; Bedrock and OpenAI in chat-completions mode → no) — replaces the hardcoded `!== "Bedrock"` exclusion, and decides whether the built-in option is offered in the `searchSource` selector at all. The toggle is offered when `searchSource !== "none" && (searchSource === "native" ? providerHasNativeSearch(provider) : true)`, killing the current dead switch on no-native-search Providers. The **backend-side** injection gate applies the same logic, so a stale client sending `search: true` on a no-native-search Provider with `searchSource: "native"` (e.g. a stored value from before a Provider's capability changed) cannot inject the dead OpenAI-hosted tool. Accepted edge: OpenAI in chat-completions mode is treated as no-native-search — matching the existing documented assumption that chat mode is, in practice, only used against self-hosted OpenAI-compatible servers.
- **Citations.** Plugin search results render in the same `<Sources>` row as native `source-url` parts, by reading the core-owned `results[].url`. The frontend therefore depends on that result shape — loosening it later breaks this rendering.

  It depends on one more thing the bullet above understates. Because a plugin `web_search` and a Provider's native one register under the **same tool name**, the frontend must first decide _which_ `web_search` a message part is before it can read that shape at all. It does so on a **core-owned metadata marker** stamped on both Tools core builds, with the AI SDK's `providerExecuted` flag as the negative check and core's result shape as a back-compat fallback for parts stored before the marker existed. The marker exists rather than `providerExecuted` alone because that flag is each provider package's to set and `@openrouter/ai-sdk-provider` does not set it — a discriminator built only on it is as reliable as the least diligent vendor. Two consequences follow: **core must keep stamping that metadata**, since dropping it silently un-renders every plugin search's citations; and the snake_case tool-name exception this ADR argues for on prompt-portability grounds has this as its cost — sharing native search's name is what makes core unidentifiable by name and the marker necessary.

  The dependency is specifically on the SDK carrying that metadata from the **first streaming chunk**, not only at parse time: `ai@7.0.48` copies a Tool's metadata onto the `tool-input-start` chunk and forwards it onto the UI part, which is what lets an in-flight plugin search be recognised while its input is still streaming. Stated as the version-pinned assumption it is, with its failure mode, so nobody reads it as load-bearing: an SDK that stopped carrying it there would render a plugin search with the generic renderer mid-stream and correct itself once the input is complete. Cosmetic, no security edge — which is why it is pinned only on the side we own, by a test that core stamps the marker, rather than by a test asserting a third party's stream shape.

  The two citation sources merge into one row, so a page named by both is one pill, and **the plugin entry is the copy kept**. Search resolution cannot produce both in one turn — a turn resolves to a backend or to native search, never both — but a vendor emits `source-url` parts for citations that are not search results, and those can land in the same message as a backend search. The plugin copy wins because its URL has already been through core's own presentability rules on the way in, so where the two disagree the vetted one is the safer `href`. Compared as **exact strings**: a vendor URL differing by a trailing slash or a tracking parameter reads as a second page and gets a second pill. Deliberate — normalising URLs is a judgement call of its own, with its own failure modes, and belongs to whoever asks for it rather than being smuggled in under citation rendering.

  The render-side scheme check also covers **native** `source-url` parts, not only backend-supplied result URLs. The Citations decision scoped that re-check to plugin results, and it widened once the row began titling a pill by the vendor's own title, since the raw URL had until then been the only thing making an odd scheme visible on screen. Consequence to state rather than imply: an unpresentable native citation is **dropped from the row and from its count**, not degraded to unlinked text. No live loss — the vendors that emit citations emit `http(s)` only — but it is a core-owned predicate deciding what a vendor's citation renders as, which is a decision rather than implementation detail.

- **Boundary vs MCP (ADR-0013 non-goal #4).** A Plugin Tool set that merely proxies HTTP is an MCP smell. A Web-search backend is different on two counts: it fills core's own **request-gated toggle slot** — a slot no MCP or Tool set can fill — and it is the same category as sandbox backends, a swappable deployment-chosen capability, not a duplication of MCP's always-on per-Agent tool exposure.
- **Coexistence.** `read_url` and `@platypus/web-fetch`'s `fetchUrl` both remain. `read_url` does not check robots.txt.
- **Out of tree.** No SearXNG / browser-service code ships in core; those are out-of-tree Plugins. Core ships the Extension point, registry, selection, resolution, Tool construction, guard, and gate only.

## Amendment — an unavailable search is reported to the User (#522)

The **Selection** consequence above ends "a stale id degrades to no search tools
plus a warn-log rather than blocking the form". That outcome is now
**reported to the User** as well as logged. It is the **Unavailable capability**
of `CONTEXT.md`: a turn that asked for search and was served none carries a flag
on its reply's metadata, and the Chat renders a notice under the answer. The
model is never told, so nothing about the prompt or the tool set changes — a turn
where search was unavailable is indistinguishable, to the model, from one that
never asked for it.

The flag is **outcome-based**: search was asked for, resolution had somewhere to
send it, and no tools came back. So a stale id, a factory that threw or outran
its timeout, and a malformed executor object all report the same thing to the
User, while the Operator's log keeps naming the specific fault. What it does
**not** cover is a `searchSource` that resolves to no search at all, including
`"native"` on a Provider with no native tool: nothing was promised, so nothing
was missing. A direct API caller can still reach that case unreported; the UI
cannot, because the toggle's gate and Turn resolution consult the same
`providerHasNativeSearch` predicate.

The reporting path is deliberately the whole of the fix. Hiding the toggle on a
Provider whose backend is missing was considered and **rejected**: the toggle's
visibility stays a pure function of the Provider row, as the **Capability gate**
consequence specifies, so the frontend needs no mirror of a registry that lives
in the backend and no per-turn catalogue fetch. See
`.out-of-scope/hiding-the-search-toggle-on-a-missing-backend.md`.

The three warns keep their distinct messages and each names the **Provider row**,
which is the field an Operator edits — an org-scoped Shared Provider (ADR-0007)
is one row serving many Workspaces, so the Workspace alone names a symptom. This
does **not** widen the **Backend context** consequence above:
`WebBackendContext` remains `{ orgId, workspaceId, userId }` for Plugin authors.
Core passes its own `buildTurnTools` a `TurnToolsContext` that adds `providerId`
and strips it again before the plugin-facing `createExecutors` call, so the
published SDK contract is untouched.
